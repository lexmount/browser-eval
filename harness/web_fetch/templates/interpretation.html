正常返回，是内容验收的起点

给一个 URL，得到一段文本，看起来是一项足够明确的工作。做知识库时，这段文本应当是目标文章；做商品目录时，还需要商品名称对应正确的详情入口；下载附件时，链接甚至算不上交付完成。同一个“抓取成功”，会因下游要求不同而失效。

这轮评测比较的是给定 URL 的取回接口：普通 HTTP 和文本提取、浏览器型实现，以及托管抓取 API。每条记录对应一个方法对一个任务的调用，评测侧保存参考与验收规则，再检查实际返回。这里没有让 Agent 自主搜索、规划或反复尝试，也没有用大模型给任务打分。

历史组包含 ${historical_cases} 个任务、${historical_providers} 种方法，${historical_records} 次调用中 ${request_ok} 次正常返回，${task_pass} 次满足任务规则。所含调用开始于 ${time_window}。${supplement_note}当前合计 ${cases} 个任务、${records} 条记录，不把不同参评范围混成一个完整矩阵。

${failure_figure}

${failure_interpretation}：正常返回但任务未通过，占历史组全部失败的 ${post_response_share}。单看接口错误率，会漏掉相当一部分未交付任务。它们也不全是同一种抓取故障：返回错误页面、缺少正文或资源，以及尚未形成完整验收证据，都可能落在这里。接入服务后，应检查下游所需的内容，并保留可定位的失败原因。

历史样本由${track_mix}组成。网页组占了主要份额，直接混成总分会把“取正文”放到较高权重。后面的排名逆转发生在同一网页组内；文档、媒体、复杂网站和动态补测则用来检验这套选择能否延伸到别的交付任务。${results_link}保留了每次调用的状态与结果。

通过更多网页的方法，未必交付更干净的正文

${rank_reversal} ${quality_figure}

正文验收检查长度、预登记事实组、显著标记、错误页标记和个别结构规则。一个事实组内可以接受不同表达，命中其中一种即可；正文是否通过由该例门槛决定。错误页词语如果本来就在参考文章中，会得到豁免，避免把介绍访问错误的技术文档判成错误页。F1 没有被放进正文通过条件。

F1 使用另一套计算。英文按词、中文按字，统计输出与参考各词出现次数的重合。完整度是重合数占参考词数的比例，纯净度是重合数占输出词数的比例；F1 取二者的调和平均。表中只对有全文指标的记录逐例求算术平均，保留请求成功但规则失败的实际分数。先平均完整度、纯净度再算 F1，会得到不同的量。

${low_f1_case}

这个反例让排名逆转有了具体含义：允许更多非正文文字进入输出，可能更容易保住被抽查的关键点，却会拉低纯净度。对于需要长文检索的应用，额外导航和目录会占据检索候选或模型上下文；对于只需定位少量字段的应用，这些附带文字未必足以让结果不可用。该不该清理，取决于下游是否依赖整段内容。

F1 本身也不能认证语义。它不保留句子顺序，无法证明某个价格属于某件商品；参考正文范围较窄，也会把读者认为有用的附录计为额外文字。因此，这里的判断是保留两个轴：用任务规则守住必需交付，再用全文重合定位遗漏和噪声。选型时强行压成一个分数，会隐藏本来需要做出的取舍。

改错一个价格，足以让正常返回变成失败

${price_case}

这项实验说明，规则能识别已登记的内容错误，而长度正常无法替代事实核对。它也暴露了抽查的边界：如果输出保留被检查的书名、价格和库存，却漏掉另一条未登记书目，仍可能通过。事实组匹配同样不能自动验证整张表里的逐行归属。对商品采集应用，需要继续把名称、价格、库存和详情链接绑定到同一条目，而不是仅要求这些字符串散落在返回值中。

规则匹配会规范 Unicode、空白和部分 Markdown 排版，但保留数字、正负号和英文词边界。未登记的同义表达可能漏判，参考选取也可能不完整。遇到高全文分却失败的输出，应先核对原文与具体规则，再判断该修提取还是修验收；仅凭一个好看的 F1 改成通过，会把问题藏起来。${rules_link}给出了可复核的实现口径。

保留更多文字，也意味着保留更多负担

${cow_result} ${initial_audit}

当前核对到的网页提取函数先删除 script 和 style 内容，再删除 HTML 标签、整理空白。这条文本路线没有借助大模型理解页面，也不会因为网页里包含脚本就自动执行脚本。对已经出现在响应 HTML 中的正文，它可能足够；对藏在脚本或运行时响应中的内容，同样的操作就可能把所需信息留在文本之外。

${probe_figure}

合成实验把一个具体取舍暴露出来：标签间的文字留下来，属性里的地址消失了。导航和页脚与正文一样保留；详情链接的可见名称仍在，href 已经没有了。把这种输出送去正文规则，可能有足够的关键字；送去资源入口规则，信息却已经缺失。媒体验收所需的差异发生在输出接口上，后续再提高关键词匹配精度也找不回已被丢弃的地址。

这与低纯净度的实测案例相符，但实验只验证合成输入上的当前提取函数。历史 CowAgent 记录没有逐次源码指纹，也没有把同一份历史响应字节交给多个提取算法做对照。因此，还不能把每次成功或失败都归因于这段函数，更不能量化“保留更多文字”贡献了多少通过率。

比再排一次名更有用的，是比较失败是否重叠

${overlap_analysis} ${rescue_mechanism}

生产系统通常没有随每个新 URL 提供的完整参考答案。这里用于事后比较的“任务未通过”，不能原样变成一个已经可用的线上开关。受控试验需要先明确哪些内容错误可被检测：空壳可以用最低内容量和页面身份检查，已知文档可以检查标题与关键段落，列表则要核验条目名称和详情关系。判定器如果漏掉一份看似充足的错误正文，后备方法即使有能力也不会被调用。

对技术文档采集，CowAgent 可以进入基线候选；Moli 可以进入后备候选。接下来应在同一时间窗执行完整链路，记录首方法失败、触发原因、后备结果和整条调用耗时，并单独统计错误触发与漏触发。只有这一层通过，离线互补才可能转成服务收益。对以正文纯净度为主要约束的应用，则应先比较清理后输出和业务质量，不能仅凭通过数量决定首方法。

换成文件或媒体，交付边界先于方法排名

${other_tasks_figure}

文档组包含 PDF、DOCX、文档查看器与规范原文，目标是取回登记的文字。文档文字的通过可以说明这条接口交付了需要的文本，不能顺带证明表格版式、扫描页识别或原文件下载都合格。返回一份长文与返回一份可重新打开的文件，是需要分别验收的结果。

图片与视频的资源任务则检查登记地址或允许的地址规则。候选可以来自返回文本，也可以来自接口的原生附加字段；请求时输入的 URL 本身不算“发现”。一个保留链接的输出可能通过，而更易读的纯文本输出可能失败，这并不与网页正文的高分矛盾。地址通过也不表示实际下载、播放或内容理解已经验证。视频组还包含文字信息与原文件任务，不能把整组分数统称为视频理解能力。

原文件任务尤其需要区分缺测与产品失败。本轮共有 ${raw_file_records} 条记录，${raw_file_missing} 条没有写入 raw_file_pass，只有 ${raw_file_verified} 条形成已验证通过记录。缺失标记在当前判定中不算通过，但不能据此宣称参评产品不支持文件下载。要做有效比较，需要实际字节或受控附件证据，再验 MIME、字节数和 SHA-256。对于以文件为最终产物的业务，这条验收链路应先接通，正文榜单无法代替它。

复杂热门网站：多接几个方法，也有共同空白

复杂热门网站组中，单方法最好通过 ${challenge_best}/${challenge_cases}，所有方法成功集的离线并集也只有 ${challenge_union}/${challenge_cases}。仍无任何已验证通过记录的 ${challenge_missing_count} 个任务是：${challenge_unpassed}。这与网页正文组的互补现象形成对照：切换方法有机会补上独立失败，却无法从现有记录中补出共同缺失的交付。

这一组要求至少三个去重后的具名详情入口，并核对返回顺序中前三条的名称与详情身份是否有独立证据。它没有固定旧榜单的标题、名次和价格，因为实时列表本来就会变化。可见列表、可访问详情和可证明条目身份是不同环节；返回了新条目而没有足够独立证据时，会记为未通过，但这不等于条目是编造的。本轮没有认证实时排名和价格的事实正确性。

访问限制也不自动使任务无效。登录提示、地区差异或拦截页面，可能恰好是目标应用必须面对的工作条件。有效性要回到任务是否定义清楚、是否存在可核验的目标内容；方法失败要回到本次请求和输出。把受限任务直接剔除会提高分数，却无法回答系统在这些网站上如何交付。

这里得到的接入决策与普通文档不同：先验证目标网站的访问条件、输出的名称与详情关系，以及独立核验覆盖，再决定是否引入更多接口。各方法调用并非全部同时发生，Moli 属于后续批次；页面版本、网络和会话变化都可能影响结果。${environment_link}说明了这些运行条件。一次网页样本上的成功并集，不应成为另一个任务组的覆盖承诺。
