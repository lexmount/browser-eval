普通文本提取能覆盖哪些任务

${cow_result} ${initial_audit}

当前核对到的网页提取函数先删除 script 和 style 内容，再删除 HTML 标签、整理空白。这条文本路线没有借助大模型理解页面，也不会因为网页里包含脚本就自动执行脚本。对已经出现在响应 HTML 中的正文，它可能足够；对藏在脚本或运行时响应中的内容，同样的操作就可能把所需信息留在文本之外。

${probe_figure}

同一次去标签操作，既保住了文字，也丢掉了地址。它能满足某些正文任务，却无法替下游决定哪些部分值得保留；文字要清理到什么程度、链接是否必须保留，应由交付目标决定。属性已经从输出中消失之后，再提高关键词匹配精度也找不回地址。

这个实验只验证合成输入上的当前提取函数。已保存的 CowAgent 调用没有逐次源码指纹，也没有把同一份响应字节交给多个提取算法做对照。因此，还不能把每次成功或失败都归因于这段函数，更不能量化保留文字范围对通过率的贡献。

比再排一次名更有用的，是比较失败是否重叠

${overlap_analysis} ${rescue_mechanism}

后备方法能否发挥作用，取决于系统是否识别出了首方法的错误。生产环境通常没有每个新 URL 的完整参考，不能照搬这里的事后判分；页面身份、最低内容量和业务必需字段才是需要试验的触发条件。若判定器接受了一份看似充足的错误正文，后备方法即使有能力也不会被调用。

这使 CowAgent 作为技术文档基线、Moli 作为后备成为值得验证的组合。试验应在同一时间窗跑完整链路，记录错误触发、漏触发、后备结果和总耗时，而不能只重放已经知道会失败的案例。正文噪声还应单独验收，以免提高了交付覆盖，却降低了检索质量。

换成文件或媒体，交付边界先于方法排名

${media_case}

这也解释了为什么不能把正文选型直接用于文档与媒体交付。PDF、DOCX 的文字可用，不代表版式或原文件已保留；图片与视频入口可用，也不代表文件已经下载或画面已被理解。若下游需要地址，就应核验地址；若下游需要文件，就必须收到可核验的字节。纯文本输出是否更易读，无法代替这项检查。

原文件任务尤其需要区分缺测与产品失败。本轮共有 ${raw_file_records} 条记录，${raw_file_missing} 条没有写入 raw_file_pass，只有 ${raw_file_verified} 条形成已验证通过记录。缺失验收的记录显示为未测，不进入任务通过率分母或失败数；不能据此宣称参评产品不支持文件下载。后续调用通过统一文件入口核验返回字节、格式特征、长度及 SHA-256，已有独立文件哈希时还须匹配目标。历史调用没有这些证据，不能补认证为测过。

热门网站正文：内容可以变化，交付契约仍然稳定

${popular_scope}

剧集榜单的名字和顺序可以更新，页面身份、稳定栏目和说明内容仍可作为核对点；条目部分则检查规定数量、非空名称和符合要求的详情地址。标题正确但列表为空，或条目齐全却来自错误栏目，都可能不满足这份混合契约。可重复的是问题与规则，不是某天的全部答案。

通过率衡量已登记的内容与结构要求。只数卡片会接受空占位，只查非空字段也可能接受错配或虚假条目；即使稳定内容命中、字段齐全，也不证明所有事实准确、数据最新或整页无遗漏。参考范围明确时再看文本重合，缺少参考不抹去已完成的内容与结构检查，也不把 F1 记成零分。

统计按实际调用记录计算，未运行和缺少验收证据的项目不记为失败。静态网站正文、动态网站正文与热门网站正文分别陈述，文档、资源地址和原文件按各自契约验收。${web_sample_scope}；每个方法与案例组合只有一次观察，不能估计波动或外推为全网成功率。调用日期相邻不构成同时间对照，公开练习站也不能代表生产网站分布。

客户端计时从调用开始到最终内容及必要转换完成，涵盖下载、渲染和本地解析。离线评分和报告生成不计入调用耗时。超过原调用登记预算的记录保留实际内容和耗时，但不算按时交付；历史调用的硬截止执行和运行时审计开销没有重新测量。主结果里各方法自身通过项的耗时均值不能当作同题速度排名；如有同窗速度子集，应同时阅读固定分母的全调用耗时、各方法条件成功耗时和共同通过诊断。
