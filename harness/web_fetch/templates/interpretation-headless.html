“各显神通”比统一转换器更接近真实选型

Kitesurf 使用 Cloudflare 账号版 Browser Run /markdown?browser=kitesurf；Lightpanda、Obscura、Moli 使用本地 CLI 的 fetch --dump markdown。这四条路径直接交付 Markdown。Chromium 152 由 Playwright 1.58 取得完整渲染 DOM，再用 node-html-markdown 2.0.0 转换；五种方法都不调用模型。

Chromium/CDP 的 Page 接口没有 Markdown 输出。Reader Mode 生成的是简化 HTML，并且会主动选择正文范围，不适合作为覆盖全部任务的通用 Markdown 接口。候选转换器在同一批已保存 DOM 上复评分：node-html-markdown 得到 98/100 的普通网页验收结果，Xberg 92/100，Turndown 58/100，Defuddle 47/100；旧 pyhtml2md 路线为 97/100，且大页转换明显更慢。最终选择 node-html-markdown，是因为它在这批输入上同时给出更好的交付结果和更短的转换时间，而不是因为所有方法必须经过它。

Kitesurf 目前不能按开源本地浏览器来测

截至本轮核对，Kitesurf 是 Cloudflare Browser Run 中的托管预览；Cloudflare 公开表达了未来开源意向，但尚未发布可供本地部署的源码或独立发行物。因此本报告测试当前可获得的账号版 /markdown，不把未来计划写成现有能力，也不伪造“本地 Kitesurf”成绩。

复现只需要列出 Cloudflare 账号、Browser Rendering / Browser Run 权限、账号 ID 和 API Token 的官方获取入口。真实值只从仓库本地、被忽略的 .env 读取；HTML、接口示例和 Git 中都只有变量名与占位符。

公平边界：输入输出对齐，不代表部署与等待机制相同

Kitesurf 运行在 Cloudflare 远端，耗时包含公网往返、远端排队和执行；其余四种方法在本机运行，包含本地进程启动和资源竞争。Kitesurf 使用 networkidle2，Chromium 使用 domcontentloaded，三种 CLI 使用各自内建完成条件。把这些差异抹成同一个标签不会使内部实现相同，只会隐藏真实产品路径。

因此本报告能比较“从这台客户端提交同一 URL，到拿到满足同一任务规则的 Markdown，需要多久”；不能比较同机纯内核 CPU/RSS、网络剥离后的执行速度、长期吞吐或生产 SLA。每个 URL 每种方法仅一次调用，也没有置信区间。

文档和媒体成绩只约束当前 Markdown 路线

PDF、Office、图片和视频任务不等于普通正文抓取。当前五条路径没有额外接入 PDF/Office 解析、OCR、媒体理解或通用下载器；找到资源 URL 也不等于取得原文件。相关成绩描述这次 Markdown 接口的交付边界，不能反推产品不存在其他可选能力。

可复验范围

150 题 × 5 种方法全部执行，共 750 次唯一调用。每次新进程或新会话，不复用个人登录状态，不启用 Obscura stealth，不按失败分数重试或切换实现。精确正文参考在调用前由独立来源冻结，并在调用后按同一范围核验；稳定契约检查长期不变的文字与记录形状，不把每日变化的排名和价格冻结成永久答案。

报告保存任务 ID、原始输出、哈希、运行 ID、方法版本、参数、分阶段计时与参考来源。两处现场参考无法独立取得时，浏览器调用照常保存并按稳定事实判定，但不伪造实时全文质量结论。完整证据可以从任务页和逐次调用页逐项核对。
