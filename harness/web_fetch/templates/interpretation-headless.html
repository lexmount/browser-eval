普通网页先比验收，再比速度

网站正文任务通过数为：${web_summary}。每个任务给定一个 URL，要求取回登记范围的正文；接口返回正常还不够，内容必须满足原任务的必需事实、文字或结构规则。这里没有让 Agent 自主搜索、重试或根据答案修改抓取方式，也没有使用大模型裁判。

本轮沿用仓库全部 150 题：100 个普通网页，以及动态网页、热门网站、文档、图片、视频各 10 题。后三类包含不同交付目标，不能把六类通过率相加，就声称得到了通用浏览器能力排名。

${overview}

原有 Moli WebFetch 适配器直接取浏览器的 Markdown；本轮 Moli 与其他四者一样，先输出 HTML，再经 pyhtml2md 1.7.0 转换。因此，这份报告评估的是五条统一 HTML→Markdown 链路，不把它与原报告的原生提取器分数混排。

同一批成功网页，才有可比的耗时

一种方法可能快速返回错误页，另一种可能花更多时间交付正确正文。直接比较“各自成功请求”的中位数，会混入不同的样本。下面以 Chromium 为基线，只取每一对方法共同通过的普通网页；同一行的两个耗时来自相同 URL 集合。

${pairs}

这是单次冷启动调用的端到端观察：包含客户端进程、浏览器生命周期、取 HTML 和转换；不含调用前节流等待及事后评分。每题只调用一次，P50 与 P95 描述跨页面的耗时分布，不是同一页面反复测量的稳定性或置信区间。

${latency}

Kitesurf 使用公共远程 CDP 测试端点，其余四者运行在本机。网络距离、远端负载及本地并发竞争都没有被隔离。因而，这轮可以回答“从这台客户端得到结果用了多久”，不能回答五种引擎在相同硬件上的纯执行效率，更不能据此计算 CPU、内存或每千页成本。

一个百科页面，把取页和转换的差距拉开了

Wikipedia 英文百科任务中，Moli、Lightpanda、Chromium 都在约 2—3 秒完成取 HTML 阶段，但随后转换各花了约 40 秒，端到端耗时接近 45 秒预算。原始 HTML、最终 Markdown 和两段计时都保留在这三次记录中。

${stages}

这三次调用直接支持一个局部结论：该页的耗时主要落在统一转换阶段。它们没有证明所有长页面都如此，也不能解释另外两次超时究竟卡在取页还是转换，因为超时进程没有返回完整分段数据。若应用经常处理大页面，优先试验转换前的正文范围选择，可能比只替换浏览器更有价值；这仍需另做同输入对照，不能从本次记录推算优化后的加速倍数。

统一输出格式，并没有统一正文范围

五种方法都把所取 DOM 交给同一转换器，并未额外选择 article 或 main。导航、目录、推荐链接可能与正文一起进入 Markdown。命中必需事实能够通过任务，但不保证文字干净，也不保证整篇参考都被取回。

${quality}

纯净度看输出词语有多少属于参考，完整度看参考词语取回了多少，F1 综合两者。三项是词级重合诊断，不验证逐句含义或事实新鲜度。参考只覆盖稳定文字片段时，只能解释片段覆盖；无完整参考的任务不记成满分或零分。任务验收与文本重合独立保留，避免用一个分数同时回答两个问题。

动态任务改变了普通网页上的排序

动态任务通过数为：${dynamic_summary}。Kitesurf 和 Obscura 在普通网页上的端到端耗时较长，却在这组动态任务中交付了更多合格结果。普通网页的配对耗时不能直接拿来替动态目录选型。

本轮统一等待 DOMContentLoaded，不滚动、不点击、不另设针对答案的等待条件。这个生命周期事件并不表示异步记录、延迟组件或子框架已经完成加载；各引擎相同名称的等待选项也不保证内部实现完全相同。

${dynamic}

异步商品题提供了一个具体对照：Moli 的已存档 Markdown 留下空商品卡片和商品名称模板片段，Kitesurf 的输出则包含实际商品名称、售价与详情链接。两份输出都出现了页面的“Enable JavaScript to see products”提示。只抓住这句提示，就断言某个浏览器没有运行脚本，会错过真正有区分度的证据：要求的商品记录是否已经出现并满足契约。

例如延迟引文任务要求首次自动呈现的 10 条记录，内嵌目录任务要求 iframe 中全部 14 个龟类科名称。前者需要等到记录实际出现；后者还要求读到子文档。对顶层 documentElement 取 outerHTML，不会自动把子文档正文拼进父页。页面上有 iframe 地址与交付其中 14 个名称，是不同结果。

成功与失败的差异说明，本轮固定策略在各引擎上取得了不同的页面状态；记录本身没有隔离等待实现、额外停留与脚本兼容性的贡献。面向这类业务，下一项应验证的改动是有界的业务完成条件与子文档处理，而非把等待时间无限拉长。任务允许渲染、内嵌状态或公开接口等实现；评测并未规定 JavaScript 是唯一正确路径。

热门站点和媒体，需要各自的交付契约

热门网站会更新榜单、价格和成员。仓库的稳定任务契约保留有独立依据的标题、栏目和说明，再检查条目数量、字段类型、非空值与唯一性；不会把某天的榜单名字永久定为答案。字段齐全仍不证明名称和价格属于同一条记录，也不证明数据最新。缺少独立标题证据的条目保持未测，不从浏览器输出反推标准答案。

文档、图片与视频任务则暴露了 HTML 适配器的范围：PDF 或 Office 文件需要解析器，资源地址需要保留，原文件需要可核验的字节。直接把二进制按 UTF-8 解码并不能完成这些任务。本轮保留遇到的二进制标准输出作证据，但没有把它偷偷切换成专用文件解析路线。

因此，表中的文档和媒体成绩描述当前调用模式的交付结果，不代表浏览器产品的全部功能。需要文档文字的系统应显式接入文档解析；需要原文件的系统应验证 MIME、字节数与 SHA-256。把这些步骤加入完整链路后，须重新测量其耗时，不能沿用 HTML 路线的成绩。

后备方法的价值，取决于它补到了哪些失败

配对表同时给出了“仅本方法通过”和“仅 Chromium 通过”的数量。这比总通过数更接近后备选型：通过数相同，也可能失败在不同页面。通过集合的离线并集只是已观察到的覆盖上限，尚未运行顺序回退、错误触发和两次请求的完整服务链路。

对于常见技术文档，可先在共同通过页面上选择耗时较低的实现，再用必需内容检查触发后备；对于异步目录，先定义加载完成与条目完整性；对于文件任务，先补齐解析或下载交付。三者要改的是不同环节。没有定义“什么时候算拿到了需要的内容”，换浏览器无法替应用作出这个判断。

测量范围与可复验边界

五种方法每题保留一次有效批次调用，子进程取页与转换共用 45 秒预算；外围启动、哈希与回收开销可能使端到端时间略长。主批次各方法内部顺序执行、方法间最多五路并行；另有参考核验失败后重跑的单路短批次。后完成的方法会在不同的实际站点时刻取页。每次使用新进程或新浏览器上下文，不复用登录状态，不启用 Obscura stealth，不为任务失败切换输出模式。CLI 取不到可靠 HTTP 状态或最终地址时保持空值，不伪造 200。

精确正文参考来自独立采集，在调用前冻结并在调用后按相同范围核验；这能约束观察到的漂移，不能排除两次采集之间未被观察到的变化。动态与热门站点的稳定契约不套用排名或价格的快照有效期。输出哈希、原始调用身份、规则来源、运行参数与参考证据共同保留，哈希本身不证明内容正确。

本轮未测持续吞吐、暖启动、隔离硬件资源、登录后的工作流或商业计费。公共价格与本轮实际开销分开列示，未知价格保持未知。公开代码采用统计沿用原样本；未登记这五个接口专用检索签名的项目显示“—”，不将缺少统计误写成零采用。
