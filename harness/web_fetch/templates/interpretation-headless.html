浏览器与 AI

AI 读到的网页，取决于浏览器交回什么

给 AI 一个论文链接，并不等于把论文交给了它。程序需要访问网址、取得响应，再把正文提取出来。遇到动态网页，正文可能要等页面脚本执行后才出现；遇到 PDF，还要从文件里解析文字。这一段从 URL 到所需内容的工作，通常称为 Web Fetch。

这里比较的是供程序调用的浏览器及其内容提取配置。Moli 面向 AI Agent，Chromium 是通用浏览器，本轮以不显示窗口的无头模式运行。它们通常将网页转换成 Markdown，也就是带少量格式标记的文字，交给 AI 使用。

Web Fetch：读取内容

输入论文地址，返回可供总结的正文。任务也可以要求商品列表、图片下载地址或原始文件。

给定 URL→读取与提取→正文或文件

Browser Use：操作网页

让 AI 搜索商品、筛选规格，再加入购物车。它需要看当前页面，决定点击或填写什么，操作后再继续观察。

观察页面→点击或填写→继续下一步

这次的 150 道任务评测 Web Fetch：同样的网址、同样的内容要求，每题给 45 秒，检查交回的结果并记录耗时。浏览器是否适合连续操作网页，需要用 Browser Use 任务另外评测。

主要结果

150 道任务，Moli 通过 135 道

Moli 的任务通过率为 90.0%，高于 Chromium 的 83.3%、Lightpanda 的 79.3%、Obscura 的 78.0% 和 Kitesurf 的 74.7%。这里的“通过”是按每题要求取得合格结果，失败和超时仍计入总题数。

完整报告包含三个 Moli 版本。本文选取总通过数最高的 1.1.1，所有任务统一使用该版本结果。

文档与媒体：Moli 通过 24/30，Chromium 通过 14/30

把 150 道题按内容拆开，净增的 10 道全部来自文档、图片和视频。120 道网页任务中，两者各通过 111 道。

其中六道 PDF 题只有 Moli 的本轮配置通过。Moli 先取得 PDF 文件，再交给本地 pypdf 解析器提取正文；其余四款使用本轮配置的 Markdown 输出路线，未能交回合格正文。对需要读论文的 AI 来说，这一步决定了后续有没有内容可读。成绩属于这条完整处理路径，PDF 解析时间也计入耗时。

网页类的得失则发生在不同站点。普通网页中，Moli 通过 97/100，Chromium 通过 99/100；热门站点中，Moli 为 6/10，Chromium 为 4/10。只看合计的 111 道，会漏掉这两种差异。

98 道共同成功任务，Moli 的平均耗时为 3.01 秒

150 道主任务中，五款浏览器都通过的有 98 道：普通网页 79 道、动态网页 8 道、热门站点 2 道、文档 1 道、图片 5 道、视频 3 道。比较同一组成功任务，能排除“很快返回空内容”或各自只完成简单任务的影响。

这 98 道中，Moli 的均值为 3.01 秒、P50 为 2.44 秒、P95 为 6.03 秒，三项都是五款中最低。但网络和运行时间不同，不能仅凭这组记录确定差距有多少来自浏览器实现。

9 道同窗测速：Moli 的 P50 为 2.82 秒

为进一步观察速度，我们从主评测的普通网页中预选 20 道，另行安排在同一个时间窗口执行。其中五款都成功读取的有 9 道，下面比较这 9 个相同网页。

Moli 的 P50 为 2.82 秒，Chromium 为 3.87 秒，Lightpanda 为 3.51 秒。均值与 P95 则是 Lightpanda 更低：分别为 3.82 秒和 6.03 秒，Moli 为 4.45 秒和 12.84 秒。

差异集中在一张 Sponsors 页面：Moli 成功取得内容，但花了 12.84 秒，Lightpanda 用了 5.59 秒。这次慢调用把 Moli 的均值和 P95 拉高，却没有改变 P50 最低的结果。对通常要等多久、偶尔会等多长，两类指标给出了不同的信息。

任务与验收

网页、列表和文件，怎样交给 AI

Web Fetch 的输入都是地址，交付物却不一样。读论文要正文，整理商品要记录，下载图片可能要地址，也可能要文件本身。五种常见任务分别经过下面的处理步骤；浏览器可以采用不同实现，最后按同样的交付要求验收。

网页正文

网页 URL→取页、等待内容→提取正文

例如 Example Domain：标题、用途说明和更多信息入口都要保留。

文档正文

PDF URL→取得文件→解析文字

例如论文 PDF：正文要覆盖指定区域，只有文件地址不够。

列表记录

列表页→提取名称与字段→检查完整、去重

例如商品页：每条需要名称和详情链接，重复条目不增加数量。

资源地址

媒体页面→定位目标资源→返回可用 URL

例如视频演示页：找到指定视频地址，不能用导航链接代替。

原始文件

文件直链→获取字节→校验并交付

例如 PNG：取得图片文件，后续工具才能识别或保存；图片说明不能代替文件。

评测集与判定规则

150 道任务按来源分为普通网页、动态网页、热门站点、文档、图片、视频六组。同类来源也可能有不同的交付要求：图片页面可以只要求找到原图地址，直接图片链接则可以要求下载原文件。

正文与文件参考来自独立获取的来源；商品列表检查经独立确认的稳定文字与结构，不把每天变化的商品名单固定成答案。正文覆盖阈值是本评测采用的工程验收下限，尚未通过阈值敏感性实验校准。

每款配置每题保留一次主结果。参考内容在被测输出之外独立准备，浏览器可以采用不同获取与转换路径，最后按同一题目要求判定。完整报告保留每道题的运行记录、原始输出、文件指纹及逐项判定，可从结论追溯到具体返回内容。

正文与列表还检查明显乱码：替代字符同时达到 20 个、占输出至少 2%，会导致该文本任务失败。文本规范化、逐项阈值、完整参考与原始返回均保存在完整报告中。

浏览器与配置

五款浏览器的实现与实测差异

浏览器怎样把内容交出来，会直接影响成绩。本轮四款在本地运行，Kitesurf 通过远端服务调用；Chromium 需要将页面结构转换为 Markdown，Moli 的 PDF 路线另有本地解析步骤。

Moli 1.1.1 135 / 150 · 90.0%

Moli 是面向 AI Agent 的 Rust 浏览器，提供网页获取与浏览器自动化接口。本轮网页输出原生 Markdown；直接文档与媒体可交付原始响应，PDF 再由本地 pypdf 提取文字。

文档 7/10、图片 10/10、视频 7/10，说明这条配置能处理网页之外的输入。普通网页为 97/100；三个 W3C 标准停在安全验证页，DOCX 和嵌入式文档查看器也有未完成任务。

Chromium 125 / 150 · 83.3%

Chromium 是通用开源浏览器，也是许多浏览器产品的基础。本轮以无头模式运行，读取 DOM（浏览器维护的页面结构），再用 node-html-markdown 2.0.0 转成 Markdown。

普通网页通过 99/100，参考正文词语找回比例为 99.8%。文档为 1/10，这对应当前页面转文本路线；若增加文件下载与 PDF 解析，需要重新评测那条组合配置。

Lightpanda 119 / 150 · 79.3%

Lightpanda 是用 Zig 开发、面向 AI 与自动化的无头浏览器，并非 Chromium 分支。本轮在本地调用，直接取得原生 Markdown。

普通网页通过 92/100，三篇 Moli 未完成的 W3C 标准都取得了正文，IMDb 题只有它通过。9 道同窗测速的均值为 3.82 秒、P95 为 6.03 秒，均为五款最低；文档则通过 1/10。

Obscura 117 / 150 · 78.0%

Obscura 是采用 V8 执行 JavaScript 的 Rust 无头浏览器。本轮使用本地标准模式的原生 Markdown，没有启用 stealth 模式或备用引擎。

普通网页通过 90/100，热门站点通过 5/10，也取得了 Moli 未交回的 Blender 下载资源入口。9 道同窗测速 P50 为 13.72 秒；这一等待时间只对应受测标准模式。

Kitesurf 112 / 150 · 74.7%

Kitesurf 是 Cloudflare 面向 Agent 的浏览器方案。本轮通过远端 Browser Run 接口提交 URL、返回 Markdown，浏览器在云端运行。

普通网页通过 88/100，动态网页通过 8/10，YouTube 题只有它通过。9 道同窗测速 P50 为 6.21 秒，包含网络往返与远端处理；本轮未测试托管成本、扩容和生产并发。

任务构成会改变这张榜单的意义。文档与媒体占本轮题量的 20%，Moli 在这 30 道里比 Chromium 多通过 10 道；如果应用只读普通网页，对应成绩就是 97/100 与 99/100。选择时应把自己的输入类型，与对应分组和失败案例一起看。

未通过的任务

长网页的验证页，动态页面的等待

三份 W3C 标准，返回的都是 475 字符验证页

Moli 未通过的三个普通网页都是 W3C 长标准：CSS 2.1、WCAG 2.1、XML 1.0。它们返回了同样的 475 字符安全验证页，Chromium 和 Lightpanda 则取到了正文。

正文质量另看 98 道有完整可比参考的普通网页。这与前面跨类型、共同成功的 98 道耗时样本不是同一集合。在这组普通网页中，Moli 平均找回 95.3% 的参考正文词语，Chromium 为 99.8%。这个比例称为 Recall。另一个指标 Precision 检查输出词语中有多少与参考重合，F1 综合两者；它们衡量文字重合，不判断文字中的事实是否正确。

${quality}

任务通过与正文完整度因此要分开看：结果可以满足题目要求，同时夹带多余导航；也可能找回部分正文，却漏掉必需段落而未通过。只有完整参考可用的任务才参与上表统计，缺少参考的任务不按零分或满分处理。

动态内容：延迟出现的列表和 iframe

五款浏览器的动态任务均通过 8/10，共同未通过的是延迟列表和 iframe 目录。iframe 是嵌在网页里的子页面；主页面读取成功，子页面的内容仍可能缺失。

网页加载完成的信号也不同：Chromium 使用页面结构就绪事件，Kitesurf 等待网络活动趋于空闲，Moli 与 Lightpanda 使用各自的 done 状态，Obscura 在加载事件后继续等待页面稳定。这些信号不保证目标内容已经出现，因此最终仍要检查实际交回的列表和正文。

内容晚 3 秒出现

0 秒：页面框架→3 秒：目标列表

Moli 交回了页面框架，目标列表缺失。对此类页面，读取何时结束会影响最终能否拿到记录。

目录在 iframe 里

外围页面
iframe 子页面：目标目录

Moli 达到 45 秒仍无结果；Chromium、Lightpanda 和 Kitesurf 只取得外围页面。

这些样本能告诉我们缺了什么，还不足以将原因完全归于浏览器内核。等待策略、子页面获取和网络条件，需要用受控实验进一步分开。

后续评测

从 150 道读取任务，走向连续网页操作

PDF 和原文件交付解释了 Moli 在这轮混合任务中的增益。下一步需要验证：增加站点与文档类型后，这些成功能否重复，现有的读取缺口能否补齐。

延迟列表、iframe，以及本轮未通过的 DOCX 和嵌入式文档查看器，需要在迭代后重新验证；热门站点需要重复运行，速度比较也需要更多共同成功样本。

Moli 也在继续迭代：1.1.2、1.1.3、1.1.4 分别于 9 月 4 日、5 日、8 日发布。1.1.4 包含页面重定向处理修复。是否改善这里的延迟列表、iframe 或文档问题，仍需同题复测。查看公开版本记录。

随后还会用独立的浏览器自动化评测，比较搜索、点击、翻页和填写等连续操作，检验 Agent 能否完成整段网页任务。
