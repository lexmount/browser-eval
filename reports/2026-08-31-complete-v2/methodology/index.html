评测方法与公平性

主问题是“给定公开 URL，能否稳定返回正确、完整、可供 Agent 使用的正文”。搜索召回、登录交互、反机器人解锁和结构化 AI extraction 不混入主分数。

执行顺序

  1. 冻结数据集 v2 ground truth，再运行任何供应商。
  2. 每个方法按相同 URL、timeout、run 数执行；保存完整响应或异常。
  3. 先判 transport，再按事实组、最小长度和反向标记判 strict content。
  4. 聚合成功率、事实覆盖率、P50/P95、输出长度、失败类型和可观测 credits。
  5. HTML 仅由 artifacts/JSONL 生成；不手工填写供应商分数。

Cloudflare 端点为何这样分

/markdown 进入主表

官方定义是把浏览器加载后的页面转为 Markdown，并去掉样式和脚本；与 Lexmount main_text、Firecrawl Markdown、Tavily Extract、Exa text 的“可读正文”输出目标最接近。

/content 单列诊断

官方定义是 JavaScript 执行后的完整 HTML（包括 head）。它适合判断浏览器是否渲染成功，但 HTML 标签、脚本和模板噪声不能和清洗正文的字符数直接比较。

官方 Content 文档 →
/json 需要 AI schema/prompt，属于结构化 extraction；它的质量、时延和模型成本应在另一数据集评测。

正确性与完整性

主裁判：版本化人工 ground truth。每个事实组代表一个必须保留的语义单元，组内同义字符串均可接受；所有组命中才通过。另设最小长度防止只返回标题，反向标记防止 CAPTCHA/Access denied 被算作正文。

LLM judge：不进入主榜。若后续启用，只做二级语义审阅：供应商名盲化、固定 rubric 与 JSON schema、记录模型/提示版本、引用 ground truth 和原始 artifact，并抽样人工复核。单一 LLM 的分数不可替代冻结标注。
