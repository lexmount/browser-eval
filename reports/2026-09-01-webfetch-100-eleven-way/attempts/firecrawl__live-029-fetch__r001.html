## 1\. Preface

At a high level, fetching a resource is a fairly simple operation. A request goes in, a
response comes out. The details of that operation are
however quite involved and used to not be written down carefully and differ from one API
to the next.

Numerous APIs provide the ability to fetch a resource, e.g. HTML’s `img` and
`script` element, CSS' `cursor` and `list-style-image`,
the `navigator.sendBeacon()` and `self.importScripts()` JavaScript
APIs. The Fetch Standard provides a unified architecture for these features so they are
all consistent when it comes to various aspects of fetching, such as redirects and the
CORS protocol.

The Fetch Standard also defines the [`fetch()`](https://fetch.spec.whatwg.org/#dom-global-fetch) JavaScript API, which
exposes most of the networking functionality at a fairly low level of abstraction.

### 2.2. HTTP

While [fetching](https://fetch.spec.whatwg.org/#concept-fetch) encompasses more than just HTTP, it
borrows a number of concepts from HTTP and applies these to resources obtained via other
means (e.g., `data` URLs).

An HTTP tab or space is U+0009 TAB or U+0020 SPACE.

HTTP whitespace is U+000A LF, U+000D CR, or an [HTTP tab or space](https://fetch.spec.whatwg.org/#http-tab-or-space).

[HTTP whitespace](https://fetch.spec.whatwg.org/#http-whitespace) is only useful for specific constructs that are reused outside
the context of HTTP headers (e.g., [MIME types](https://mimesniff.spec.whatwg.org/#mime-type)). For HTTP header values, using
[HTTP tab or space](https://fetch.spec.whatwg.org/#http-tab-or-space) is preferred, and outside that context [ASCII whitespace](https://infra.spec.whatwg.org/#ascii-whitespace) is
preferred. Unlike [ASCII whitespace](https://infra.spec.whatwg.org/#ascii-whitespace) this excludes U+000C FF.

An HTTP newline byte is 0x0A (LF) or 0x0D (CR).

An HTTP tab or space byte is 0x09 (HT) or 0x20 (SP).

An HTTP whitespace byte is an [HTTP newline byte](https://fetch.spec.whatwg.org/#http-newline-byte) or
[HTTP tab or space byte](https://fetch.spec.whatwg.org/#http-tab-or-space-byte).

#### 2.2.1. Methods

A method is a [byte sequence](https://infra.spec.whatwg.org/#byte-sequence) that matches the
[method](https://httpwg.org/specs/rfc9110.html#method.overview) token production.

A CORS-safelisted method is a
[method](https://fetch.spec.whatwg.org/#concept-method) that is \``GET`\`,
\``HEAD`\`, or \``POST`\`.

A forbidden method is a [method](https://fetch.spec.whatwg.org/#concept-method) that is a
[byte-case-insensitive](https://infra.spec.whatwg.org/#byte-case-insensitive) match for \``CONNECT`\`,
\``TRACE`\`, or \``TRACK`\`.
[\[HTTPVERBSEC1\]](https://fetch.spec.whatwg.org/#biblio-httpverbsec1 "Multiple vendors' web servers enable HTTP TRACE method by default."), [\[HTTPVERBSEC2\]](https://fetch.spec.whatwg.org/#biblio-httpverbsec2 "Microsoft Internet Information Server (IIS) vulnerable to cross-site scripting via HTTP TRACK method."), [\[HTTPVERBSEC3\]](https://fetch.spec.whatwg.org/#biblio-httpverbsec3 "HTTP proxy default configurations allow arbitrary TCP connections.")

To normalize a
[method](https://fetch.spec.whatwg.org/#concept-method), if it is a [byte-case-insensitive](https://infra.spec.whatwg.org/#byte-case-insensitive)
match for \``DELETE`\`, \``GET`\`,
\``HEAD`\`, \``OPTIONS`\`, \``POST`\`, or
\``PUT`\`, [byte-uppercase](https://infra.spec.whatwg.org/#byte-uppercase) it.

[Normalization](https://fetch.spec.whatwg.org/#concept-method-normalize) is done for backwards compatibility and
consistency across APIs as [methods](https://fetch.spec.whatwg.org/#concept-method) are actually "case-sensitive".

Using \``patch`\` is highly likely to result in a
\``405 Method Not Allowed`\`. \``PATCH`\` is much more likely to
succeed.

There are no restrictions on [methods](https://fetch.spec.whatwg.org/#concept-method). \``CHICKEN`\` is perfectly
acceptable (and not a misspelling of \``CHECKIN`\`). Other than those that are
[normalized](https://fetch.spec.whatwg.org/#concept-method-normalize) there are no casing restrictions either.
\``Egg`\` or \``eGg`\` would be fine, though uppercase is encouraged for
consistency.

To
get, decode, and split
a [header value](https://fetch.spec.whatwg.org/#header-value) value, run these steps. They return a [list](https://infra.spec.whatwg.org/#list) of
[strings](https://infra.spec.whatwg.org/#string).

1. Let input be the result of [isomorphic decoding](https://infra.spec.whatwg.org/#isomorphic-decode) value.



2. Let position be a [position variable](https://infra.spec.whatwg.org/#string-position-variable) for input,
    initially pointing at the start of input.



3. Let values be a [list](https://infra.spec.whatwg.org/#list) of [strings](https://infra.spec.whatwg.org/#string), initially « ».



4. Let temporaryValue be the empty string.



5. While true:


1. Append the result of [collecting a sequence of code points](https://infra.spec.whatwg.org/#collect-a-sequence-of-code-points) that are not U+0022 (") or
       U+002C (,) from input, given position, to temporaryValue.



      The result might be the empty string.



2. If position is not past the end of input and the
       [code point](https://infra.spec.whatwg.org/#code-point) at position within input is U+0022 ("):


      1. Append the result of [collecting an HTTP quoted string](https://fetch.spec.whatwg.org/#collect-an-http-quoted-string) from input,
          given position, to temporaryValue.



      2. If position is not past the end of input, then
          [continue](https://infra.spec.whatwg.org/#iteration-continue).
3. Remove all [HTTP tab or space](https://fetch.spec.whatwg.org/#http-tab-or-space) from the start and end of temporaryValue.



4. [Append](https://infra.spec.whatwg.org/#list-append) temporaryValue to values.



5. Set temporaryValue to the empty string.



6. If position is past the end of input, then return values.



7. [Assert](https://infra.spec.whatwg.org/#assert): the [code point](https://infra.spec.whatwg.org/#code-point) at position within
       input is U+002C (,).



8. Advance position by 1.

directly. Use [get, decode, and split](https://fetch.spec.whatwg.org/#concept-header-list-get-decode-split) instead.

A header is a [tuple](https://infra.spec.whatwg.org/#tuple) that consists of a
name (a [header name](https://fetch.spec.whatwg.org/#header-name)) and
value (a [header value](https://fetch.spec.whatwg.org/#header-value)).

A header name is a [byte sequence](https://infra.spec.whatwg.org/#byte-sequence) that matches the
[field-name](https://httpwg.org/specs/rfc9110.html#fields.names) token production.

A header value is a [byte sequence](https://infra.spec.whatwg.org/#byte-sequence) that matches the following
conditions:

- Has no leading or trailing [HTTP tab or space bytes](https://fetch.spec.whatwg.org/#http-tab-or-space-byte).


- Contains no 0x00 (NUL) or [HTTP newline bytes](https://fetch.spec.whatwg.org/#http-newline-byte).


The definition of [header value](https://fetch.spec.whatwg.org/#header-value) is not defined in terms of the
[field-value](https://httpwg.org/specs/rfc9110.html#fields.values) token production as it is
[not compatible with deployed content](https://github.com/httpwg/http-core/issues/215 "field-value value space").

To normalize a
[byte sequence](https://infra.spec.whatwg.org/#byte-sequence) potentialValue, remove any leading and trailing
[HTTP whitespace bytes](https://fetch.spec.whatwg.org/#http-whitespace-byte) from potentialValue.

rangeEnd, and an integer fullLength, run these steps:

1. Let contentRange be \``bytes`\`.

    [isomorphic encoded](https://infra.spec.whatwg.org/#isomorphic-encode), to contentRange.



3. Append 0x2D (-) to contentRange.



4. Append rangeEnd, [serialized](https://fetch.spec.whatwg.org/#serialize-an-integer) and
    [isomorphic encoded](https://infra.spec.whatwg.org/#isomorphic-encode) to contentRange.



5. Append 0x2F (/) to contentRange.



6. Append fullLength, [serialized](https://fetch.spec.whatwg.org/#serialize-an-integer) and

7. Return contentRange.


To parse a single range header value from a
[byte sequence](https://infra.spec.whatwg.org/#byte-sequence) value and a boolean allowWhitespace, run these steps:

01. Let data be the [isomorphic decoding](https://infra.spec.whatwg.org/#isomorphic-decode) of value.



02. If data does not [start with](https://infra.spec.whatwg.org/#string-starts-with) "`bytes`", then return
     failure.



03. Let position be a [position variable](https://infra.spec.whatwg.org/#string-position-variable) for data, initially
     pointing at the 5th [code point](https://infra.spec.whatwg.org/#code-point) of data.



04. If allowWhitespace is true, [collect a sequence of code points](https://infra.spec.whatwg.org/#collect-a-sequence-of-code-points) that are
     [HTTP tab or space](https://fetch.spec.whatwg.org/#http-tab-or-space), from data given position.



05. If the [code point](https://infra.spec.whatwg.org/#code-point) at position within data is not U+003D (=),
     then return failure.



06. Advance position by 1.



07. If allowWhitespace is true, [collect a sequence of code points](https://infra.spec.whatwg.org/#collect-a-sequence-of-code-points) that are
     [HTTP tab or space](https://fetch.spec.whatwg.org/#http-tab-or-space), from data given position.



08. Let rangeStart be the result of [collecting a sequence of code points](https://infra.spec.whatwg.org/#collect-a-sequence-of-code-points) that
     are [ASCII digits](https://infra.spec.whatwg.org/#ascii-digit), from data given position.



09. Let rangeStartValue be rangeStart, interpreted as decimal number, if
     rangeStart is not the empty string; otherwise null.



10. If allowWhitespace is true, [collect a sequence of code points](https://infra.spec.whatwg.org/#collect-a-sequence-of-code-points) that are
     [HTTP tab or space](https://fetch.spec.whatwg.org/#http-tab-or-space), from data given position.



11. If the [code point](https://infra.spec.whatwg.org/#code-point) at position within data is not U+002D (-),
     then return failure.



12. Advance position by 1.



13. If allowWhitespace is true, [collect a sequence of code points](https://infra.spec.whatwg.org/#collect-a-sequence-of-code-points) that are
     [HTTP tab or space](https://fetch.spec.whatwg.org/#http-tab-or-space), from data given position.



14. Let rangeEnd be the result of [collecting a sequence of code points](https://infra.spec.whatwg.org/#collect-a-sequence-of-code-points) that
     are [ASCII digits](https://infra.spec.whatwg.org/#ascii-digit), from data given position.



15. Let rangeEndValue be rangeEnd, interpreted as decimal number, if
     rangeEnd is not the empty string; otherwise null.



16. If position is not past the end of data, then return failure.



17. If rangeEndValue and rangeStartValue are null, then return failure.



18. If rangeStartValue and rangeEndValue are numbers, and
     rangeStartValue is greater than rangeEndValue, then return failure.



19. Return (rangeStartValue, rangeEndValue).



    The range end or start can be omitted, e.g., \``bytes=0-`\` or
     \``bytes=-500`\` are valid ranges.

#### 2.2.3. Statuses

A status is an integer in the range 0 to 999, inclusive.

Various edge cases in mapping HTTP/1’s `status-code` to this concept are
worked on in [issue #1156](https://github.com/whatwg/fetch/issues/1156).

A null body status is a [status](https://fetch.spec.whatwg.org/#concept-status) that is 101, 103, 204, 205, or 304.

An ok status is a [status](https://fetch.spec.whatwg.org/#concept-status) in the range 200 to 299, inclusive.

A range status is a [status](https://fetch.spec.whatwg.org/#concept-status) that is 206 or 416.

A redirect status is a [status](https://fetch.spec.whatwg.org/#concept-status) that is 301, 302, 303, 307, or 308.

"`default`"

[Fetch](https://fetch.spec.whatwg.org/#concept-fetch) will inspect the HTTP cache on the way to the network. If the HTTP cache

To compute the redirect-taint of a
[request](https://fetch.spec.whatwg.org/#concept-request) request, perform the following steps. They return
"`same-origin`", "`same-site`", or "`cross-site`".

1. [Assert](https://infra.spec.whatwg.org/#assert): request’s [origin](https://fetch.spec.whatwg.org/#concept-request-origin) is not
    "`client`".



2. Let lastURL be null.



3. Let taint be "`same-origin`".



4. [For each](https://infra.spec.whatwg.org/#list-iterate) url of request’s [URL list](https://fetch.spec.whatwg.org/#concept-request-url-list):


1. If lastURL is null, then set lastURL to url and
       [continue](https://infra.spec.whatwg.org/#iteration-continue).



2. If url’s [origin](https://url.spec.whatwg.org/#concept-url-origin) is not [same site](https://html.spec.whatwg.org/multipage/browsers.html#same-site) with
       lastURL’s [origin](https://url.spec.whatwg.org/#concept-url-origin) and request’s [origin](https://fetch.spec.whatwg.org/#concept-request-origin) is
       not [same site](https://html.spec.whatwg.org/multipage/browsers.html#same-site) with lastURL’s [origin](https://url.spec.whatwg.org/#concept-url-origin), then return
       "`cross-site`".



3. If url’s [origin](https://url.spec.whatwg.org/#concept-url-origin) is not [same origin](https://html.spec.whatwg.org/multipage/browsers.html#same-origin) with
       lastURL’s [origin](https://url.spec.whatwg.org/#concept-url-origin) and request’s [origin](https://fetch.spec.whatwg.org/#concept-request-origin) is
       not [same origin](https://html.spec.whatwg.org/multipage/browsers.html#same-origin) with lastURL’s [origin](https://url.spec.whatwg.org/#concept-url-origin), then set
       taint to "`same-site`".



4. Set lastURL to url.
5. Return taint.

[request](https://fetch.spec.whatwg.org/#concept-request) request, with an integer first, and an optional integer
last, run these steps:

1. [Assert](https://infra.spec.whatwg.org/#assert): last is not given, or first is less than or equal
    to last.



2. Let rangeValue be \``bytes=`\`.



3. [Serialize](https://fetch.spec.whatwg.org/#serialize-an-integer) and [isomorphic encode](https://infra.spec.whatwg.org/#isomorphic-encode) first,
    and append the result to rangeValue.



4. Append 0x2D (-) to rangeValue.



5. If last is given, then [serialize](https://fetch.spec.whatwg.org/#serialize-an-integer) and
    [isomorphic encode](https://infra.spec.whatwg.org/#isomorphic-encode) it, and append the result to rangeValue.



6. [Append](https://fetch.spec.whatwg.org/#concept-header-list-append) (\``Range`\`, rangeValue) to
    request’s [header list](https://fetch.spec.whatwg.org/#concept-request-header-list).


A range header denotes an inclusive byte range. There a range header where
first is 0 and last is 500, is a range of 501 bytes.

Features that combine multiple responses into one logical resource are historically a
source of security bugs. Please seek security review for features that deal with partial responses.

* * *

To serialize a response URL for reporting, given a [response](https://fetch.spec.whatwg.org/#concept-response) response, run these steps:

1. [Assert](https://infra.spec.whatwg.org/#assert): response’s [URL list](https://fetch.spec.whatwg.org/#concept-response-url-list) [is not empty](https://infra.spec.whatwg.org/#list-is-empty).



2. Let url be a copy of response’s [URL list](https://fetch.spec.whatwg.org/#concept-response-url-list)\[0\].



This is not response’s [URL](https://fetch.spec.whatwg.org/#concept-response-url) in order to avoid
    leaking information about redirect targets (see
    [similar considerations for CSP reporting](https://w3c.github.io/webappsec-csp/#security-violation-reports)
    too). [\[CSP\]](https://fetch.spec.whatwg.org/#biblio-csp "Content Security Policy Level 3")

3. [Set the username](https://url.spec.whatwg.org/#set-the-username) given url and the empty string.



4. [Set the password](https://url.spec.whatwg.org/#set-the-password) given url and the empty string.



5. Return the [serialization](https://url.spec.whatwg.org/#concept-url-serializer) of url with
    [_exclude fragment_](https://url.spec.whatwg.org/#url-serializer-exclude-fragment) set to true.


To check if Cross-Origin-Embedder-Policy allows credentials, given a
[request](https://fetch.spec.whatwg.org/#concept-request) request, run these steps:

1. [Assert](https://infra.spec.whatwg.org/#assert): request’s [origin](https://fetch.spec.whatwg.org/#concept-request-origin) is not
    "`client`".



2. If request’s [mode](https://fetch.spec.whatwg.org/#concept-request-mode) is not "`no-cors`", then return
    true.



3. If request’s [client](https://fetch.spec.whatwg.org/#concept-request-client) is null, then return true.



4. If request’s [client](https://fetch.spec.whatwg.org/#concept-request-client)’s
    [policy container](https://html.spec.whatwg.org/multipage/webappapis.html#concept-settings-object-policy-container)’s
    [embedder policy](https://html.spec.whatwg.org/multipage/browsers.html#policy-container-embedder-policy)’s [value](https://html.spec.whatwg.org/multipage/browsers.html#embedder-policy-value-2) is not
    " [`credentialless`](https://html.spec.whatwg.org/multipage/browsers.html#coep-credentialless)", then return true.



5. If request’s [origin](https://fetch.spec.whatwg.org/#concept-request-origin) is [same origin](https://html.spec.whatwg.org/multipage/browsers.html#same-origin) with
    request’s [current URL](https://fetch.spec.whatwg.org/#concept-request-current-url)’s [origin](https://url.spec.whatwg.org/#concept-url-origin) and request’s
    [redirect-taint](https://fetch.spec.whatwg.org/#concept-request-tainted-origin) is not "`same-origin`", then return true.



6. Return false.


#### 2.2.6. Responses

The result of [fetch](https://fetch.spec.whatwg.org/#concept-fetch) is a
response. A [response](https://fetch.spec.whatwg.org/#concept-response)
evolves over time. That is, not all its fields are available straight away.

A [response](https://fetch.spec.whatwg.org/#concept-response) has an associated
type which is
"`basic`",
"`cors`",
"`default`",
"`error`",
"`opaque`", or
"`opaqueredirect`".
Unless stated otherwise, it is "`default`".

A [response](https://fetch.spec.whatwg.org/#concept-response) can have an associated
aborted flag, which is initially unset.

This indicates that the request was intentionally aborted by the developer or
end-user.

A [response](https://fetch.spec.whatwg.org/#concept-response) has an associated
URL. It is a pointer to the last
[URL](https://url.spec.whatwg.org/#concept-url) in [response](https://fetch.spec.whatwg.org/#concept-response)’s [URL list](https://fetch.spec.whatwg.org/#concept-response-url-list) and null if
[response](https://fetch.spec.whatwg.org/#concept-response)’s [URL list](https://fetch.spec.whatwg.org/#concept-response-url-list) [is empty](https://infra.spec.whatwg.org/#list-is-empty).

A [response](https://fetch.spec.whatwg.org/#concept-response) has an associated
URL list (a [list](https://infra.spec.whatwg.org/#list) of zero or
more [URLs](https://url.spec.whatwg.org/#concept-url)). Unless stated otherwise, it is « ».

Except for the first and last [URL](https://url.spec.whatwg.org/#concept-url), if any, a [response](https://fetch.spec.whatwg.org/#concept-response)’s
[URL list](https://fetch.spec.whatwg.org/#concept-response-url-list) is not directly exposed to script as that would violate
[atomic HTTP redirect handling](https://fetch.spec.whatwg.org/#atomic-http-redirect-handling).

A [response](https://fetch.spec.whatwg.org/#concept-response) has an associated
status, which is a [status](https://fetch.spec.whatwg.org/#concept-status).
Unless stated otherwise it is 200.

A [response](https://fetch.spec.whatwg.org/#concept-response) has an associated
status message. Unless stated
otherwise it is the empty byte sequence.

Responses over an HTTP/2 connection will always have the empty byte sequence as status
message as HTTP/2 does not support them.

A [response](https://fetch.spec.whatwg.org/#concept-response) has an associated
header list (a
[header list](https://fetch.spec.whatwg.org/#concept-header-list)). Unless stated otherwise it is « ».

A [response](https://fetch.spec.whatwg.org/#concept-response) has an associated
body (null or a
[body](https://fetch.spec.whatwg.org/#concept-body)). Unless stated otherwise it is null.

The [source](https://fetch.spec.whatwg.org/#concept-body-source) and [length](https://fetch.spec.whatwg.org/#concept-body-total-bytes) concepts of a network’s
[response](https://fetch.spec.whatwg.org/#concept-response)’s [body](https://fetch.spec.whatwg.org/#concept-response-body) are always null.

A [response](https://fetch.spec.whatwg.org/#concept-response) has an associated
cache state (the empty string,
"`local`", or "`validated`"). Unless stated otherwise, it is the empty
string.

This is intended for usage by Service Workers and
Resource Timing. [\[SW\]](https://fetch.spec.whatwg.org/#biblio-sw "Service Workers Nightly") [\[RESOURCE-TIMING\]](https://fetch.spec.whatwg.org/#biblio-resource-timing "Resource Timing")

A [response](https://fetch.spec.whatwg.org/#concept-response) has an associated
CORS-exposed header-name list
(a list of zero or more [header](https://fetch.spec.whatwg.org/#concept-header) [names](https://fetch.spec.whatwg.org/#concept-header-name)). The list is empty unless otherwise specified.

A [response](https://fetch.spec.whatwg.org/#concept-response) will typically get its
[CORS-exposed header-name list](https://fetch.spec.whatwg.org/#concept-response-cors-exposed-header-name-list) set by [extracting header values](https://fetch.spec.whatwg.org/#extract-header-values) from the
\` [`Access-Control-Expose-Headers`](https://fetch.spec.whatwg.org/#http-access-control-expose-headers) \` header. This list is used by a
[CORS filtered response](https://fetch.spec.whatwg.org/#concept-filtered-response-cors) to determine which headers to expose.

A [response](https://fetch.spec.whatwg.org/#concept-response) has an associated
range-requested flag, which is
initially unset.

This is used to prevent a partial response from an earlier ranged request being
provided to an API that didn’t make a range request. See the flag’s usage for a detailed description
of the attack.

A [response](https://fetch.spec.whatwg.org/#concept-response) has an associated request-includes-credentials
(a boolean), which is initially true.

A [response](https://fetch.spec.whatwg.org/#concept-response) has an associated
timing allow passed flag, which is
initially unset.

This is used so that the caller to a fetch can determine if sensitive timing data is
allowed on the resource fetched by looking at the flag of the response returned. Because the flag on
the response of a redirect has to be set if it was set for previous responses in the redirect chain,
this is also tracked internally using the request’s [timing allow failed flag](https://fetch.spec.whatwg.org/#timing-allow-failed).

A [response](https://fetch.spec.whatwg.org/#concept-response) has an associated
navigation timing allow values list (a [list](https://infra.spec.whatwg.org/#list) of
[lists](https://infra.spec.whatwg.org/#list) of [strings](https://infra.spec.whatwg.org/#string)). Unless stated otherwise, it is « ».

This holds the \``Timing-Allow-Origin`\` values of each redirect
[response](https://fetch.spec.whatwg.org/#concept-response) in a navigation’s redirect chain. It is used so that callers can determine,
once the navigation’s destination origin is known, whether that origin is allowed by every redirect
in the redirect chain.

A [response](https://fetch.spec.whatwg.org/#concept-response) has an associated
body info
(a [response body info](https://fetch.spec.whatwg.org/#response-body-info)). Unless stated otherwise, it is a new
[response body info](https://fetch.spec.whatwg.org/#response-body-info).

A [response](https://fetch.spec.whatwg.org/#concept-response) has an associated
service worker timing info (null or a
[service worker timing info](https://w3c.github.io/ServiceWorker/#service-worker-timing-info)), which is initially null.

A [response](https://fetch.spec.whatwg.org/#concept-response) has an associated redirect taint
("`same-origin`", "`same-site`", or "`cross-site`"), which is
initially "`same-origin`".

* * *

A network error is a [response](https://fetch.spec.whatwg.org/#concept-response) whose
[type](https://fetch.spec.whatwg.org/#concept-response-type) is "`error`", [status](https://fetch.spec.whatwg.org/#concept-response-status) is 0,
[status message](https://fetch.spec.whatwg.org/#concept-response-status-message) is the empty byte sequence,
[header list](https://fetch.spec.whatwg.org/#concept-response-header-list) is « », [body](https://fetch.spec.whatwg.org/#concept-response-body) is null, and
[body info](https://fetch.spec.whatwg.org/#concept-response-body-info) is a new [response body info](https://fetch.spec.whatwg.org/#response-body-info).

An aborted network error is a
[network error](https://fetch.spec.whatwg.org/#concept-network-error) whose [aborted flag](https://fetch.spec.whatwg.org/#concept-response-aborted) is set.

To create the appropriate network error given [fetch params](https://fetch.spec.whatwg.org/#fetch-params) fetchParams:

1. [Assert](https://infra.spec.whatwg.org/#assert): fetchParams is [canceled](https://fetch.spec.whatwg.org/#fetch-params-canceled).



2. Return an [aborted network error](https://fetch.spec.whatwg.org/#concept-aborted-network-error) if fetchParams is
    [aborted](https://fetch.spec.whatwg.org/#fetch-params-aborted); otherwise return a [network error](https://fetch.spec.whatwg.org/#concept-network-error).


* * *

A filtered response is a [response](https://fetch.spec.whatwg.org/#concept-response)
that offers a limited view on an associated [response](https://fetch.spec.whatwg.org/#concept-response). This associated
[response](https://fetch.spec.whatwg.org/#concept-response) can be accessed through [filtered response](https://fetch.spec.whatwg.org/#concept-filtered-response)’s
internal response (a
[response](https://fetch.spec.whatwg.org/#concept-response) that is neither a [network error](https://fetch.spec.whatwg.org/#concept-network-error) nor a
[filtered response](https://fetch.spec.whatwg.org/#concept-filtered-response)).

Unless stated otherwise a [filtered response](https://fetch.spec.whatwg.org/#concept-filtered-response)’s associated concepts (such as its
[body](https://fetch.spec.whatwg.org/#concept-response-body)) refer to the associated concepts of its
[internal response](https://fetch.spec.whatwg.org/#concept-internal-response). (The exceptions to this are listed below as part
of defining the concrete types of [filtered responses](https://fetch.spec.whatwg.org/#concept-filtered-response).)

The [fetch](https://fetch.spec.whatwg.org/#concept-fetch) algorithm by way of [_processResponse_](https://fetch.spec.whatwg.org/#process-response) and
equivalent parameters exposes [filtered responses](https://fetch.spec.whatwg.org/#concept-filtered-response) to callers to ensure they do not
accidentally leak information. If the information needs to be revealed for legacy reasons, e.g., to
feed image data to a decoder, the associated [internal response](https://fetch.spec.whatwg.org/#concept-internal-response) can
be used by specification algorithms.



New specifications ought not to build further on [opaque filtered responses](https://fetch.spec.whatwg.org/#concept-filtered-response-opaque) or
[opaque-redirect filtered responses](https://fetch.spec.whatwg.org/#concept-filtered-response-opaque-redirect). Those are legacy constructs and cannot always be
adequately protected given contemporary computer architecture.

A basic filtered response is a
[filtered response](https://fetch.spec.whatwg.org/#concept-filtered-response) whose
[type](https://fetch.spec.whatwg.org/#concept-response-type) is "`basic`" and
[header list](https://fetch.spec.whatwg.org/#concept-response-header-list) excludes any
[headers](https://fetch.spec.whatwg.org/#concept-header) in
[internal response](https://fetch.spec.whatwg.org/#concept-internal-response)’s
[header list](https://fetch.spec.whatwg.org/#concept-response-header-list) whose
[name](https://fetch.spec.whatwg.org/#concept-header-name) is a
[forbidden response-header name](https://fetch.spec.whatwg.org/#forbidden-response-header-name).

A CORS filtered response is a
[filtered response](https://fetch.spec.whatwg.org/#concept-filtered-response) whose
[type](https://fetch.spec.whatwg.org/#concept-response-type) is "`cors`" and
[header list](https://fetch.spec.whatwg.org/#concept-response-header-list) excludes any
[headers](https://fetch.spec.whatwg.org/#concept-header) in
[internal response](https://fetch.spec.whatwg.org/#concept-internal-response)’s
[header list](https://fetch.spec.whatwg.org/#concept-response-header-list) whose
[name](https://fetch.spec.whatwg.org/#concept-header-name) is _not_ a
[CORS-safelisted response-header name](https://fetch.spec.whatwg.org/#cors-safelisted-response-header-name), given
[internal response](https://fetch.spec.whatwg.org/#concept-internal-response)’s
[CORS-exposed header-name list](https://fetch.spec.whatwg.org/#concept-response-cors-exposed-header-name-list).

An opaque filtered response is a
[filtered response](https://fetch.spec.whatwg.org/#concept-filtered-response) whose
[type](https://fetch.spec.whatwg.org/#concept-response-type) is "`opaque`",
[URL list](https://fetch.spec.whatwg.org/#concept-response-url-list) is « »,
[status](https://fetch.spec.whatwg.org/#concept-response-status) is 0,
[status message](https://fetch.spec.whatwg.org/#concept-response-status-message) is the empty byte sequence,
[header list](https://fetch.spec.whatwg.org/#concept-response-header-list) is « »,
[body](https://fetch.spec.whatwg.org/#concept-response-body) is null, and
[body info](https://fetch.spec.whatwg.org/#concept-response-body-info) is a new [response body info](https://fetch.spec.whatwg.org/#response-body-info).

An
opaque-redirect filtered response
is a [filtered response](https://fetch.spec.whatwg.org/#concept-filtered-response) whose
[type](https://fetch.spec.whatwg.org/#concept-response-type) is "`opaqueredirect`",
[status](https://fetch.spec.whatwg.org/#concept-response-status) is 0,
[status message](https://fetch.spec.whatwg.org/#concept-response-status-message) is the empty byte sequence,
[header list](https://fetch.spec.whatwg.org/#concept-response-header-list) is « »,
[body](https://fetch.spec.whatwg.org/#concept-response-body) is null, and
[body info](https://fetch.spec.whatwg.org/#concept-response-body-info) is a new [response body info](https://fetch.spec.whatwg.org/#response-body-info).

Exposing the [URL list](https://fetch.spec.whatwg.org/#concept-response-url-list) for
[opaque-redirect filtered responses](https://fetch.spec.whatwg.org/#concept-filtered-response-opaque-redirect) is harmless since
no redirects are followed.



In other words, an [opaque filtered response](https://fetch.spec.whatwg.org/#concept-filtered-response-opaque) and an
[opaque-redirect filtered response](https://fetch.spec.whatwg.org/#concept-filtered-response-opaque-redirect) are nearly indistinguishable from a [network error](https://fetch.spec.whatwg.org/#concept-network-error).
When introducing new APIs, do not use the [internal response](https://fetch.spec.whatwg.org/#concept-internal-response) for
internal specification algorithms as that will leak information.



This also means that JavaScript APIs, such as
[`response.ok`](https://fetch.spec.whatwg.org/#dom-response-ok), will return rather useless results.

The [type](https://fetch.spec.whatwg.org/#concept-response-type) of a [response](https://fetch.spec.whatwg.org/#concept-response) is exposed to script through the
`type` getter:



```javascript
console.log(new Response().type); // "default"

console.log((await fetch("/")).type); // "basic"

console.log((await fetch("https://api.example/status")).type); // "cors"

console.log((await fetch("https://crossorigin.example/image", { mode: "no-cors" })).type); // "opaque"

console.log((await fetch("/surprise-me", { redirect: "manual" })).type); // "opaqueredirect"
```

(This assumes that the various resources exist, `https://api.example/status` has the
appropriate CORS headers, and `/surprise-me` uses a [redirect status](https://fetch.spec.whatwg.org/#redirect-status).)

To clone a
[response](https://fetch.spec.whatwg.org/#concept-response) response, run these steps:

1. If response is a [filtered response](https://fetch.spec.whatwg.org/#concept-filtered-response), then return a new identical
    [filtered response](https://fetch.spec.whatwg.org/#concept-filtered-response) whose [internal response](https://fetch.spec.whatwg.org/#concept-internal-response) is a
    [clone](https://fetch.spec.whatwg.org/#concept-response-clone) of response’s
    [internal response](https://fetch.spec.whatwg.org/#concept-internal-response).



2. Let newResponse be a copy of response, except for its
    [body](https://fetch.spec.whatwg.org/#concept-response-body).



3. If response’s [body](https://fetch.spec.whatwg.org/#concept-response-body) is non-null, then set
    newResponse’s [body](https://fetch.spec.whatwg.org/#concept-response-body) to the result of [cloning](https://fetch.spec.whatwg.org/#concept-body-clone) response’s [body](https://fetch.spec.whatwg.org/#concept-response-body).



4. Return newResponse.

A fresh response is a [response](https://fetch.spec.whatwg.org/#concept-response) whose
[current age](https://httpwg.org/specs/rfc9111.html#age.calculations) is within its [freshness lifetime](https://httpwg.org/specs/rfc9111.html#calculating.freshness.lifetime).

A stale-while-revalidate response is a
[response](https://fetch.spec.whatwg.org/#concept-response) that is not a [fresh response](https://fetch.spec.whatwg.org/#concept-fresh-response) and whose [current age](https://httpwg.org/specs/rfc9111.html#age.calculations) is within the
[stale-while-revalidate lifetime](https://httpwg.org/specs/rfc5861.html#n-the-stale-while-revalidate-cache-control-extension). [\[HTTP-CACHING\]](https://fetch.spec.whatwg.org/#biblio-http-caching "HTTP Caching") [\[STALE-WHILE-REVALIDATE\]](https://fetch.spec.whatwg.org/#biblio-stale-while-revalidate "HTTP Cache-Control Extensions for Stale Content")

A stale response is a [response](https://fetch.spec.whatwg.org/#concept-response) that is
not a [fresh response](https://fetch.spec.whatwg.org/#concept-fresh-response) or a [stale-while-revalidate response](https://fetch.spec.whatwg.org/#concept-stale-while-revalidate-response).

The location URL of a
[response](https://fetch.spec.whatwg.org/#concept-response) response, given null or an [ASCII string](https://infra.spec.whatwg.org/#ascii-string) requestFragment, is the value returned by the following steps. They return null, failure,
or a [URL](https://url.spec.whatwg.org/#concept-url).

1. If response’s [status](https://fetch.spec.whatwg.org/#concept-response-status) is not a [redirect status](https://fetch.spec.whatwg.org/#redirect-status), then
    return null.



2. Let location be the result of [extracting header list values](https://fetch.spec.whatwg.org/#extract-header-list-values) given
    \``Location`\` and response’s [header list](https://fetch.spec.whatwg.org/#concept-response-header-list).



3. If location is a [header value](https://fetch.spec.whatwg.org/#header-value), then set location to the
    result of [parsing](https://url.spec.whatwg.org/#concept-url-parser) location with response’s
    [URL](https://fetch.spec.whatwg.org/#concept-response-url).



If response was constructed through the `Response` constructor,
    response’s [URL](https://fetch.spec.whatwg.org/#concept-response-url) will be null, meaning that location will
    only parse successfully if it is an [absolute-URL-with-fragment string](https://url.spec.whatwg.org/#absolute-url-with-fragment-string).



4. If location is a [URL](https://url.spec.whatwg.org/#concept-url) whose [fragment](https://url.spec.whatwg.org/#concept-url-fragment) is null, then set
    location’s [fragment](https://url.spec.whatwg.org/#concept-url-fragment) to requestFragment.



This ensures that synthetic (indeed, all) responses follow the processing model for
    redirects defined by HTTP. [\[HTTP\]](https://fetch.spec.whatwg.org/#biblio-http "HTTP Semantics")

5. Return location.


The [location URL](https://fetch.spec.whatwg.org/#concept-response-location-url) algorithm is exclusively used for redirect
handling in this standard and in HTML’s navigate algorithm which handles redirects
manually. [\[HTML\]](https://fetch.spec.whatwg.org/#biblio-html "HTML Standard")

 deferred fetch recordsA [list](https://infra.spec.whatwg.org/#list) of [deferred fetch records](https://fetch.spec.whatwg.org/#deferred-fetch-record).

requestA [request](https://fetch.spec.whatwg.org/#concept-request).


 notify invokedAn algorithm accepting no arguments.

 "`pending`", "`sent`", or "`aborted`".

    false, [terminate](https://fetch.spec.whatwg.org/#fetch-controller-terminate) record’s
    [controller](https://fetch.spec.whatwg.org/#concept-fetch-record-fetch).

### 2.5. Resolving domains

[![(This is a tracking vector.)](https://resources.whatwg.org/tracking-vector.svg)](https://infra.spec.whatwg.org/#tracking-vector) To

[network partition key](https://fetch.spec.whatwg.org/#network-partition-key) key and an [origin](https://html.spec.whatwg.org/multipage/browsers.html#concept-origin) origin:

1. If origin’s [host](https://html.spec.whatwg.org/multipage/browsers.html#concept-origin-host) is an [IP address](https://url.spec.whatwg.org/#ip-address), then return

    `127.0.0.1` ».

    connection information beyond just [IP addresses](https://url.spec.whatwg.org/#ip-address). For example, if origin’s

be used as part of the cache key.

Typically this operation would involve DNS and as such caching can happen on DNS servers without
key being taken into account. Depending on the implementation it might also not be
possible to take key into account locally. [\[RFC1035\]](https://fetch.spec.whatwg.org/#biblio-rfc1035 "Domain names - implementation and specification")

The order of the [IP addresses](https://url.spec.whatwg.org/#ip-address) that the [resolve an origin](https://fetch.spec.whatwg.org/#resolve-an-origin) algorithm can return
can differ between invocations.



The particulars (apart from the cache key) are not tied down as they are not pertinent to the
system the Fetch Standard establishes. Other documents ought not to build on this primitive without
having a considered discussion with the Fetch Standard community first.

- timingInfo’s [connection end time](https://fetch.spec.whatwg.org/#connection-timing-info-connection-end-time) should be the
[unsafe shared current time](https://w3c.github.io/hr-time/#dfn-unsafe-shared-current-time) immediately after establishing the connection to the
server or proxy, as follows:




  - The returned time must include the time interval to establish the transport connection, as
     well as other time intervals such as SOCKS authentication. It must include the time interval to
     complete enough of the TLS handshake to request the resource.



  - If the user agent used TLS False Start for this connection, this interval must not include
     the time needed to receive the server’s Finished message. [\[RFC7918\]](https://fetch.spec.whatwg.org/#biblio-rfc7918 "Transport Layer Security (TLS) False Start")

  - If the user agent sends the request with early data without waiting for the full handshake
     to complete, this interval must not include the time needed to receive the server’s ServerHello
     message. [\[RFC8470\]](https://fetch.spec.whatwg.org/#biblio-rfc8470 "Using Early Data in HTTP")

     includes the full TLS handshake even if other requests were sent using early data on
     connection.



Suppose the user agent establishes an HTTP/2
connection over TLS 1.3 to send a `GET` request and a `POST` request. It
sends the ClientHello at time t1 and then sends the `GET` request with early
data. The `POST` request is not safe ( [\[HTTP\]](https://fetch.spec.whatwg.org/#biblio-http "HTTP Semantics"), section 9.2.1), so the user
agent waits to complete the handshake at time t2 before sending it. Although both
requests used the same connection, the `GET` request reports a connection end time of
t1, while the `POST` request reports t2.

[connection start time](https://fetch.spec.whatwg.org/#connection-timing-info-connection-start-time) and timingInfo’s
[secure connection start time](https://fetch.spec.whatwg.org/#connection-timing-info-secure-connection-start-time) must be equal. (In HTTP/3
the secure transport handshake process is performed as part of the initial connection setup.)
[\[HTTP3\]](https://fetch.spec.whatwg.org/#biblio-http3 "HTTP/3")

#### 3.1.1. \``Cookie`\` header

To append a request \``Cookie`\` header, given a [request](https://fetch.spec.whatwg.org/#concept-request) request:

    return.



2. Let sameSite be the result of [determining the same-site mode](https://fetch.spec.whatwg.org/#determine-the-same-site-mode) for request.



3. Let isSecure be true if request’s [current URL](https://fetch.spec.whatwg.org/#concept-request-current-url)’s
    [scheme](https://url.spec.whatwg.org/#concept-url-scheme) is "`https`"; otherwise false.



4. Let httpOnlyAllowed be true.



True follows from this being invoked from [fetch](https://fetch.spec.whatwg.org/#concept-fetch), as opposed to the
    `document.cookie` getter steps for instance.



5. Let cookies be the result of running [retrieve cookies](https://datatracker.ietf.org/doc/html/draft-ietf-httpbis-layered-cookies#name-retrieve-cookies) given isSecure,

The cookie store returns an ordered list of cookies



6. If cookies [is empty](https://infra.spec.whatwg.org/#list-is-empty), then return.



7. Let value be the result of running [serialize cookies](https://datatracker.ietf.org/doc/html/draft-ietf-httpbis-layered-cookies#name-serialize-cookies) given cookies.



8. [Append](https://fetch.spec.whatwg.org/#concept-header-list-append) (\``Cookie`\`, value) to

#### 3.1.2. \``Set-Cookie`\` header

To parse and store response \``Set-Cookie`\` headers, given a
[request](https://fetch.spec.whatwg.org/#concept-request) request and a [response](https://fetch.spec.whatwg.org/#concept-response) response:

1. If the user agent is configured to disable cookies for request, then it should
    return.



2. Let allowNonHostOnlyCookieForPublicSuffix be false.



3. Let isSecure be true if request’s [current URL](https://fetch.spec.whatwg.org/#concept-request-current-url)’s

4. Let httpOnlyAllowed be true.

1. If header’s [name](https://fetch.spec.whatwg.org/#concept-header-name) is not a [byte-case-insensitive](https://infra.spec.whatwg.org/#byte-case-insensitive) match
       for \``Set-Cookie`\`, then [continue](https://infra.spec.whatwg.org/#iteration-continue).



2. [Parse and store a cookie](https://datatracker.ietf.org/doc/html/draft-ietf-httpbis-layered-cookies#name-parse-and-store-a-cookie) given header’s [value](https://fetch.spec.whatwg.org/#concept-header-value),
       isSecure, request’s [current URL](https://fetch.spec.whatwg.org/#concept-request-current-url)’s [host](https://url.spec.whatwg.org/#concept-url-host),
       request’s [current URL](https://fetch.spec.whatwg.org/#concept-request-current-url)’s [path](https://url.spec.whatwg.org/#concept-url-path), httpOnlyAllowed,
       allowNonHostOnlyCookieForPublicSuffix, and sameSiteStrictOrLaxAllowed.



3. [Garbage collect cookies](https://datatracker.ietf.org/doc/html/draft-ietf-httpbis-layered-cookies#name-garbage-collect-cookies) given request’s [current URL](https://fetch.spec.whatwg.org/#concept-request-current-url)’s
       [host](https://url.spec.whatwg.org/#concept-url-host).



As noted elsewhere the \``Set-Cookie`\` header cannot be combined and
therefore each occurrence is processed independently. This is not allowed for any other header.

### 3.2. \``Origin`\` header

The \``Origin`\`
request [header](https://fetch.spec.whatwg.org/#concept-header) indicates where a
[fetch](https://fetch.spec.whatwg.org/#concept-fetch) originates from.

The \` [`Origin`](https://fetch.spec.whatwg.org/#http-origin) \` header is a version of the
\``Referer`\` \[sic\] header that does not reveal a [path](https://url.spec.whatwg.org/#concept-url-path). It is used for all
[HTTP fetches](https://fetch.spec.whatwg.org/#concept-http-fetch) whose [request](https://fetch.spec.whatwg.org/#concept-request)’s
[response tainting](https://fetch.spec.whatwg.org/#concept-request-response-tainting) is "`cors`", as well as those where
[request](https://fetch.spec.whatwg.org/#concept-request)’s [method](https://fetch.spec.whatwg.org/#concept-request-method) is neither \``GET`\` nor
\``HEAD`\`. Due to compatibility constraints it is not included in all
[fetches](https://fetch.spec.whatwg.org/#concept-fetch).

Its possible [values](https://fetch.spec.whatwg.org/#concept-header-value) are all the return values of
[byte-serializing a request origin](https://fetch.spec.whatwg.org/#byte-serializing-a-request-origin), given a [request](https://fetch.spec.whatwg.org/#concept-request). These are represented by
the following [ABNF](https://fetch.spec.whatwg.org/#abnf):

```abnf
serialized-ipv4   = dec-octet "." dec-octet "." dec-octet "." dec-octet
dec-octet         = DIGIT                 ; 0-9
                  / %x31-39 DIGIT         ; 10-99
                  / "1" 2DIGIT            ; 100-199
                  / "2" %x30-34 DIGIT     ; 200-249
                  / "25" %x30-35          ; 250-255

serialized-ipv6   =                            7( h16 ":" ) h16
                  /                       "::" 5( h16 ":" ) h16
                  / [               h16 ] "::" 4( h16 ":" ) h16
                  / [ *1( h16 ":" ) h16 ] "::" 3( h16 ":" ) h16
                  / [ *2( h16 ":" ) h16 ] "::" 2( h16 ":" ) h16
                  / [ *3( h16 ":" ) h16 ] "::"    h16 ":"   h16
                  / [ *4( h16 ":" ) h16 ] "::"              h16
                  / [ *5( h16 ":" ) h16 ] "::"
h16               = "0" / ( non-zero-hex 0*3hex )
non-zero-hex      = %x31-39 / %x61-66 ; '1'-'9' or lowercase 'a'-'f'
hex               = %x30-39 / %x61-66 ; '0'-'9' or lowercase 'a'-'f

lower-alpha       = %x61-7A
lower-alphanum    = lower-alpha / DIGIT
domain-label      = lower-alphanum / ( lower-alphanum *( lower-alphanum / "-" ) lower-alphanum )
serialized-domain = *( domain-label "." ) domain-label

serialized-scheme = lower-alpha *( lower-alphanum / "+" / "-" / "." )
serialized-host   = serialized-ipv4 / "[" serialized-ipv6 "]" / serialized-domain
serialized-port   = 1*5DIGIT

serialized-origin = serialized-scheme "://" serialized-host [ ":" serialized-port ]
origin-or-null    = serialized-origin / %s"null" ; case-sensitive

Origin = origin-or-null
```

This supplants the definition in The Web Origin Concept. [\[ORIGIN\]](https://fetch.spec.whatwg.org/#biblio-origin "The Web Origin Concept")

The origin serialization defined here is more constrained than [\[RFC3986\]](https://fetch.spec.whatwg.org/#biblio-rfc3986 "Uniform Resource Identifier (URI): Generic Syntax")’s grammar in two
substantial ways. First, scheme and domains serializations are all lower case ASCII, without
percent encoding. Second, following the recommendations of [URL § 3.6 Host serializing](https://url.spec.whatwg.org/#host-serializing) and [\[RFC5952\]](https://fetch.spec.whatwg.org/#biblio-rfc5952 "A Recommendation for IPv6 Address Text Representation"),
IPv6 addresses are limited as follows:

- The least-significant digits cannot be represented as an IPv4 address.


- Leading zeros are forbidden.


- All hex characters are lowercase.


- "::" can’t elide only a single "0" block, so we allow at most 6 blocks when "::" is present.



* * *

To append a request \``Origin`\` header,
given a [request](https://fetch.spec.whatwg.org/#concept-request) request, run these steps:

1. [Assert](https://infra.spec.whatwg.org/#assert): request’s [origin](https://fetch.spec.whatwg.org/#concept-request-origin) is not
    "`client`".



2. Let serializedOrigin be the result of [byte-serializing a request origin](https://fetch.spec.whatwg.org/#byte-serializing-a-request-origin)
    with request.



3. If request’s [response tainting](https://fetch.spec.whatwg.org/#concept-request-response-tainting) is "`cors`" or
    request’s [mode](https://fetch.spec.whatwg.org/#concept-request-mode) is either "`websocket`" or "`webtransport`", then
    [append](https://fetch.spec.whatwg.org/#concept-header-list-append) (\``Origin`\`, serializedOrigin) to
    request’s [header list](https://fetch.spec.whatwg.org/#concept-request-header-list).



4. Otherwise, if request’s [method](https://fetch.spec.whatwg.org/#concept-request-method) is neither \``GET`\` nor
    \``HEAD`\`, then:


1. If request’s [mode](https://fetch.spec.whatwg.org/#concept-request-mode) is not "`cors`",
       then switch on request’s [referrer policy](https://fetch.spec.whatwg.org/#concept-request-referrer-policy):


      "`no-referrer`"



      Set serializedOrigin to \``null`\`.



      "`no-referrer-when-downgrade`"

       "`strict-origin`"

       "`strict-origin-when-cross-origin`"



      If request’s [origin](https://fetch.spec.whatwg.org/#concept-request-origin) is a [tuple origin](https://html.spec.whatwg.org/multipage/browsers.html#concept-origin-tuple), its
      scheme is "`https`", and request’s
      [current URL](https://fetch.spec.whatwg.org/#concept-request-current-url)’s scheme is not "`https`", then set
      serializedOrigin to \``null`\`.



      "`same-origin`"



      If request’s [origin](https://fetch.spec.whatwg.org/#concept-request-origin) is not [same origin](https://html.spec.whatwg.org/multipage/browsers.html#same-origin) with
      request’s [current URL](https://fetch.spec.whatwg.org/#concept-request-current-url)’s [origin](https://url.spec.whatwg.org/#concept-url-origin), then set
      serializedOrigin to \``null`\`.



      Otherwise

       Do nothing.


2. [Append](https://fetch.spec.whatwg.org/#concept-header-list-append) (\``Origin`\`, serializedOrigin) to
       request’s [header list](https://fetch.spec.whatwg.org/#concept-request-header-list).

A [request](https://fetch.spec.whatwg.org/#concept-request)’s [referrer policy](https://fetch.spec.whatwg.org/#concept-request-referrer-policy) is taken into account for
all fetches where the fetcher did not explicitly opt into sharing their [origin](https://html.spec.whatwg.org/multipage/browsers.html#concept-origin) with the
server, e.g., via using the [CORS protocol](https://fetch.spec.whatwg.org/#cors-protocol).

### 3.3. CORS protocol

To allow sharing responses cross-origin and allow for more versatile
[fetches](https://fetch.spec.whatwg.org/#concept-fetch) than possible with HTML’s
`form` element, the CORS protocol exists. It
is layered on top of HTTP and allows responses to declare they can be shared with other
[origins](https://html.spec.whatwg.org/multipage/browsers.html#concept-origin).

It needs to be an opt-in mechanism to prevent leaking data from responses behind a
firewall (intranets). Additionally, for [requests](https://fetch.spec.whatwg.org/#concept-request) including
[credentials](https://fetch.spec.whatwg.org/#credentials) it needs to be opt-in to prevent leaking potentially-sensitive data.

This section explains the [CORS protocol](https://fetch.spec.whatwg.org/#cors-protocol) as it pertains to server developers.
Requirements for user agents are part of the [fetch](https://fetch.spec.whatwg.org/#concept-fetch) algorithm,
except for the [new HTTP header syntax](https://fetch.spec.whatwg.org/#http-new-header-syntax).

#### 3.3.1. General

The [CORS protocol](https://fetch.spec.whatwg.org/#cors-protocol) consists of a set of headers that indicates whether a response can
be shared cross-origin.

For [requests](https://fetch.spec.whatwg.org/#concept-request) that are more involved than what is possible with HTML’s `form`
element, a [CORS-preflight request](https://fetch.spec.whatwg.org/#cors-preflight-request) is performed, to ensure [request](https://fetch.spec.whatwg.org/#concept-request)’s
[current URL](https://fetch.spec.whatwg.org/#concept-request-current-url) supports the [CORS protocol](https://fetch.spec.whatwg.org/#cors-protocol).

#### 3.3.2. HTTP requests

A CORS request is an HTTP request that includes an
\` [`Origin`](https://fetch.spec.whatwg.org/#http-origin) \` header. It cannot be reliably identified as participating
in the [CORS protocol](https://fetch.spec.whatwg.org/#cors-protocol) as the \` [`Origin`](https://fetch.spec.whatwg.org/#http-origin) \` header is also included
for all [requests](https://fetch.spec.whatwg.org/#concept-request) whose [method](https://fetch.spec.whatwg.org/#concept-request-method) is neither \``GET`\` nor
\``HEAD`\`.

A CORS-preflight request is a [CORS request](https://fetch.spec.whatwg.org/#cors-request)
that checks to see if the [CORS protocol](https://fetch.spec.whatwg.org/#cors-protocol) is understood. It uses \``OPTIONS`\` as
[method](https://fetch.spec.whatwg.org/#concept-method) and includes the following [header](https://fetch.spec.whatwg.org/#concept-header):

\``Access-Control-Request-Method`\`



Indicates which [method](https://fetch.spec.whatwg.org/#concept-method) a future
[CORS request](https://fetch.spec.whatwg.org/#cors-request) to the same resource might use.

A [CORS-preflight request](https://fetch.spec.whatwg.org/#cors-preflight-request) can also include the following [header](https://fetch.spec.whatwg.org/#concept-header):

\``Access-Control-Request-Headers`\`



Indicates which [headers](https://fetch.spec.whatwg.org/#concept-header) a future
[CORS request](https://fetch.spec.whatwg.org/#cors-request) to the same resource might use.

#### 3.3.3. HTTP responses

An HTTP response to a [CORS request](https://fetch.spec.whatwg.org/#cors-request) can include the following
[headers](https://fetch.spec.whatwg.org/#concept-header):

\``Access-Control-Allow-Origin`\`



Indicates whether the response can be shared, via returning the literal
[value](https://fetch.spec.whatwg.org/#concept-header-value) of the
\` [`Origin`](https://fetch.spec.whatwg.org/#http-origin) \` request [header](https://fetch.spec.whatwg.org/#concept-header)
(which can be \``null`\`) or \``*`\` in a response.



\``Access-Control-Allow-Credentials`\`



Indicates whether the response can be shared when [request](https://fetch.spec.whatwg.org/#concept-request)’s
[credentials mode](https://fetch.spec.whatwg.org/#concept-request-credentials-mode) is
"`include`".



For a [CORS-preflight request](https://fetch.spec.whatwg.org/#cors-preflight-request), [request](https://fetch.spec.whatwg.org/#concept-request)’s
[credentials mode](https://fetch.spec.whatwg.org/#concept-request-credentials-mode) is always "`same-origin`", i.e., it excludes
credentials, but for any subsequent [CORS requests](https://fetch.spec.whatwg.org/#cors-request) it might not be. Support therefore needs
to be indicated as part of the HTTP response to the [CORS-preflight request](https://fetch.spec.whatwg.org/#cors-preflight-request) as well.

An HTTP response to a [CORS-preflight request](https://fetch.spec.whatwg.org/#cors-preflight-request) can include the following
[headers](https://fetch.spec.whatwg.org/#concept-header):

\``Access-Control-Allow-Methods`\`



Indicates which [methods](https://fetch.spec.whatwg.org/#concept-method) are supported by the [response](https://fetch.spec.whatwg.org/#concept-response)’s
[URL](https://fetch.spec.whatwg.org/#concept-response-url) for the purposes of the [CORS protocol](https://fetch.spec.whatwg.org/#cors-protocol).



The \``Allow`\` [header](https://fetch.spec.whatwg.org/#concept-header) is
not relevant for the purposes of the [CORS protocol](https://fetch.spec.whatwg.org/#cors-protocol).



\``Access-Control-Allow-Headers`\`



Indicates which [headers](https://fetch.spec.whatwg.org/#concept-header) are supported by the [response](https://fetch.spec.whatwg.org/#concept-response)’s
[URL](https://fetch.spec.whatwg.org/#concept-response-url) for the purposes of the [CORS protocol](https://fetch.spec.whatwg.org/#cors-protocol).



\``Access-Control-Max-Age`\`



Indicates the number of seconds (5 by default) the information provided by the
\` [`Access-Control-Allow-Methods`](https://fetch.spec.whatwg.org/#http-access-control-allow-methods) \` and
\` [`Access-Control-Allow-Headers`](https://fetch.spec.whatwg.org/#http-access-control-allow-headers) \` [headers](https://fetch.spec.whatwg.org/#concept-header) can be cached.

An HTTP response to a [CORS request](https://fetch.spec.whatwg.org/#cors-request) that is not a
[CORS-preflight request](https://fetch.spec.whatwg.org/#cors-preflight-request) can also include the following
[header](https://fetch.spec.whatwg.org/#concept-header):

\``Access-Control-Expose-Headers`\`



Indicates which [headers](https://fetch.spec.whatwg.org/#concept-header) can be exposed as part
of the response by listing their [names](https://fetch.spec.whatwg.org/#concept-header-name).

* * *

A successful HTTP response, i.e., one where the server developer intends to share it, to a
[CORS request](https://fetch.spec.whatwg.org/#cors-request) can use any [status](https://fetch.spec.whatwg.org/#concept-status), as long as it includes the [headers](https://fetch.spec.whatwg.org/#concept-header)
stated above with [values](https://fetch.spec.whatwg.org/#concept-header-value) matching up with the request.

A successful HTTP response to a [CORS-preflight request](https://fetch.spec.whatwg.org/#cors-preflight-request) is similar, except it is restricted
to an [ok status](https://fetch.spec.whatwg.org/#ok-status), e.g., 200 or 204.

Any other kind of HTTP response is not successful and will either end up not being shared or fail
the [CORS-preflight request](https://fetch.spec.whatwg.org/#cors-preflight-request). Be aware that any work the server performs might nonetheless leak
through side channels, such as timing. If server developers wish to denote this explicitly, the 403
[status](https://fetch.spec.whatwg.org/#concept-status) can be used, coupled with omitting the relevant [headers](https://fetch.spec.whatwg.org/#concept-header).

If desired, “failure” could also be shared, but that would make it a successful HTTP
response. That is why for a successful HTTP response to a [CORS request](https://fetch.spec.whatwg.org/#cors-request) that is not a
[CORS-preflight request](https://fetch.spec.whatwg.org/#cors-preflight-request) the [status](https://fetch.spec.whatwg.org/#concept-status) can be anything, including 403.

Ultimately server developers have a lot of freedom in how they handle HTTP responses and these
tactics can differ between the response to the [CORS-preflight request](https://fetch.spec.whatwg.org/#cors-preflight-request) and the
[CORS request](https://fetch.spec.whatwg.org/#cors-request) that follows it:

- They can provide a static response. This can be helpful when working with caching
   intermediaries. A static response can both be successful and not successful depending on the
   [CORS request](https://fetch.spec.whatwg.org/#cors-request). This is okay.



- They can provide a dynamic response, tuned to [CORS request](https://fetch.spec.whatwg.org/#cors-request). This can be helpful when
   the response body is to be tailored to a specific origin or a response needs to have credentials
   and be successful for a set of origins.


#### 3.3.4. HTTP new-header syntax

[ABNF](https://fetch.spec.whatwg.org/#abnf) for the [values](https://fetch.spec.whatwg.org/#concept-header-value) of the
[headers](https://fetch.spec.whatwg.org/#concept-header) used by the [CORS protocol](https://fetch.spec.whatwg.org/#cors-protocol):

```abnf
Access-Control-Request-Method    = method
Access-Control-Request-Headers   = 1#field-name

wildcard                         = "*"
Access-Control-Allow-Origin      = origin-or-null / wildcard

Access-Control-Allow-Credentials = %s"true" ; case-sensitive
Access-Control-Expose-Headers    = #field-name
Access-Control-Max-Age           = delta-seconds
Access-Control-Allow-Methods     = #method
Access-Control-Allow-Headers     = #field-name
```

For \``Access-Control-Expose-Headers`\`,
\``Access-Control-Allow-Methods`\`, and \``Access-Control-Allow-Headers`\`
response [headers](https://fetch.spec.whatwg.org/#concept-header), the [value](https://fetch.spec.whatwg.org/#concept-header-value) \``*`\` counts as a wildcard for
[requests](https://fetch.spec.whatwg.org/#concept-request) without [credentials](https://fetch.spec.whatwg.org/#credentials). For such [requests](https://fetch.spec.whatwg.org/#concept-request) there is no
way to solely match a [header name](https://fetch.spec.whatwg.org/#header-name) or [method](https://fetch.spec.whatwg.org/#concept-method) that is \``*`\`.

#### 3.3.5. CORS protocol and credentials

When [request](https://fetch.spec.whatwg.org/#concept-request)’s
[credentials mode](https://fetch.spec.whatwg.org/#concept-request-credentials-mode) is "`include`" it
has an impact on the functioning of the [CORS protocol](https://fetch.spec.whatwg.org/#cors-protocol) other than including
[credentials](https://fetch.spec.whatwg.org/#credentials) in the [fetch](https://fetch.spec.whatwg.org/#concept-fetch).

In the old days, `XMLHttpRequest` could be used to set
[request](https://fetch.spec.whatwg.org/#concept-request)’s
[credentials mode](https://fetch.spec.whatwg.org/#concept-request-credentials-mode) to "`include`":



```javascript
var client = new XMLHttpRequest()
client.open("GET", "./")
client.withCredentials = true
/* … */
```

Nowadays, `fetch("./", { credentials:"include" }).then(/* … */)`
suffices.

A [request](https://fetch.spec.whatwg.org/#concept-request)’s
[credentials mode](https://fetch.spec.whatwg.org/#concept-request-credentials-mode) is not necessarily observable
on the server; only when [credentials](https://fetch.spec.whatwg.org/#credentials) exist for a
[request](https://fetch.spec.whatwg.org/#concept-request) can it be observed by virtue of the
[credentials](https://fetch.spec.whatwg.org/#credentials) being included. Note that even so, a [CORS-preflight request](https://fetch.spec.whatwg.org/#cors-preflight-request)
never includes [credentials](https://fetch.spec.whatwg.org/#credentials).

The server developer therefore needs to decide whether or not responses "tainted" with
[credentials](https://fetch.spec.whatwg.org/#credentials) can be shared. And also needs to decide if
[requests](https://fetch.spec.whatwg.org/#concept-request) necessitating a [CORS-preflight request](https://fetch.spec.whatwg.org/#cors-preflight-request) can
include [credentials](https://fetch.spec.whatwg.org/#credentials). Generally speaking, both sharing responses and allowing requests
with [credentials](https://fetch.spec.whatwg.org/#credentials) is rather unsafe, and extreme care has to be taken to avoid the
[confused deputy problem](https://en.wikipedia.org/wiki/Confused_deputy_problem).

To share responses with [credentials](https://fetch.spec.whatwg.org/#credentials), the
\` [`Access-Control-Allow-Origin`](https://fetch.spec.whatwg.org/#http-access-control-allow-origin) \` and
\` [`Access-Control-Allow-Credentials`](https://fetch.spec.whatwg.org/#http-access-control-allow-credentials) \` [headers](https://fetch.spec.whatwg.org/#concept-header) are
important. The following table serves to illustrate the various legal and illegal combinations for a
request to `https://rabbit.invalid/`:

| Request’s credentials mode | \` [`Access-Control-Allow-Origin`](https://fetch.spec.whatwg.org/#http-access-control-allow-origin) \` | \` [`Access-Control-Allow-Credentials`](https://fetch.spec.whatwg.org/#http-access-control-allow-credentials) \` | Shared? | Notes |
| --- | --- | --- | --- | --- |
| "`omit`" | \``*`\` | Omitted | ✅ | —​ |
| "`omit`" | \``*`\` | \``true`\` | ✅ | If credentials mode is not "`include`", then<br> \` [`Access-Control-Allow-Credentials`](https://fetch.spec.whatwg.org/#http-access-control-allow-credentials) \` is ignored. |
| "`omit`" | \``https://rabbit.invalid/`\` | Omitted | ❌ | A [serialized](https://html.spec.whatwg.org/multipage/browsers.html#ascii-serialisation-of-an-origin) origin has no trailing slash. |
| "`omit`" | \``https://rabbit.invalid`\` | Omitted | ✅ | —​ |
| "`include`" | \``*`\` | \``true`\` | ❌ | If credentials mode is "`include`", then<br> \` [`Access-Control-Allow-Origin`](https://fetch.spec.whatwg.org/#http-access-control-allow-origin) \` cannot be<br> \``*`\`. |
| "`include`" | \``https://rabbit.invalid`\` | \``true`\` | ✅ | —​ |
| "`include`" | \``https://rabbit.invalid`\` | \``True`\` | ❌ | \``true`\` is (byte) case-sensitive. |

Similarly, \` [`Access-Control-Expose-Headers`](https://fetch.spec.whatwg.org/#http-access-control-expose-headers) \`,
\` [`Access-Control-Allow-Methods`](https://fetch.spec.whatwg.org/#http-access-control-allow-methods) \`, and
\` [`Access-Control-Allow-Headers`](https://fetch.spec.whatwg.org/#http-access-control-allow-headers) \` response headers can only use
\``*`\` as value when [request](https://fetch.spec.whatwg.org/#concept-request)’s [credentials mode](https://fetch.spec.whatwg.org/#concept-request-credentials-mode) is not
"`include`".

#### 3.3.6. Examples

A script at `https://foo.invalid/` wants to fetch some data from
`https://bar.invalid/`. (Neither [credentials](https://fetch.spec.whatwg.org/#credentials) nor response header access is
important.)



```javascript
var url = "https://bar.invalid/api?key=730d67a37d7f3d802e96396d00280768773813fbe726d116944d814422fc1a45&data=about:unicorn";
fetch(url).then(success, failure)
```

This will use the [CORS protocol](https://fetch.spec.whatwg.org/#cors-protocol), though this is entirely transparent to the
developer from `foo.invalid`. As part of the [CORS protocol](https://fetch.spec.whatwg.org/#cors-protocol), the user agent
will include the \` [`Origin`](https://fetch.spec.whatwg.org/#http-origin) \` header in the request:



```http
Origin: https://foo.invalid
```

Upon receiving a response from `bar.invalid`, the user agent will verify the
\` [`Access-Control-Allow-Origin`](https://fetch.spec.whatwg.org/#http-access-control-allow-origin) \` response header. If its value is
either \``https://foo.invalid`\` or \``*`\`, the user agent will invoke the
`success` callback. If it has any other value, or is missing, the user agent will invoke
the `failure` callback.

The developer of `foo.invalid` is back, and now wants to fetch some data from
`bar.invalid` while also accessing a response header.



```javascript
fetch(url).then(response => {
  var hsts = response.headers.get("strict-transport-security"),
      csp = response.headers.get("content-security-policy")
  log(hsts, csp)
})
```

`bar.invalid` provides a correct
\` [`Access-Control-Allow-Origin`](https://fetch.spec.whatwg.org/#http-access-control-allow-origin) \` response header per the earlier
example. The values of `hsts` and `csp` will depend on the
\` [`Access-Control-Expose-Headers`](https://fetch.spec.whatwg.org/#http-access-control-expose-headers) \` response header. For example, if
the response included the following headers



```http
Content-Security-Policy: default-src 'self'
Strict-Transport-Security: max-age=31536000; includeSubdomains; preload
Access-Control-Expose-Headers: Content-Security-Policy
```

then `hsts` would be null and `csp` would be
"`default-src 'self'`", even though the response did include both headers. This is
because `bar.invalid` needs to explicitly share each header by listing their names in
the \` [`Access-Control-Expose-Headers`](https://fetch.spec.whatwg.org/#http-access-control-expose-headers) \` response header.



Alternatively, if `bar.invalid` wanted to share all its response headers, for
requests that do not include [credentials](https://fetch.spec.whatwg.org/#credentials), it could use \``*`\` as value for
the \` [`Access-Control-Expose-Headers`](https://fetch.spec.whatwg.org/#http-access-control-expose-headers) \` response header. If the request
would have included [credentials](https://fetch.spec.whatwg.org/#credentials), the response header names would have to be listed
explicitly and \``*`\` could not be used.

The developer of `foo.invalid` returns, now fetching some data from
`bar.invalid` while including [credentials](https://fetch.spec.whatwg.org/#credentials). This time around the
[CORS protocol](https://fetch.spec.whatwg.org/#cors-protocol) is no longer transparent to the developer as [credentials](https://fetch.spec.whatwg.org/#credentials)
require an explicit opt-in:



```javascript
fetch(url, { credentials:"include" }).then(success, failure)
```

This also makes any \``Set-Cookie`\` response headers `bar.invalid`
includes fully functional (they are ignored otherwise).



The user agent will make sure to include any relevant [credentials](https://fetch.spec.whatwg.org/#credentials) in the request.
It will also put stricter requirements on the response. Not only will `bar.invalid` need
to list \``https://foo.invalid`\` as value for the
\` [`Access-Control-Allow-Origin`](https://fetch.spec.whatwg.org/#http-access-control-allow-origin) \` header (\``*`\` is not
allowed when [credentials](https://fetch.spec.whatwg.org/#credentials) are involved), the
\` [`Access-Control-Allow-Credentials`](https://fetch.spec.whatwg.org/#http-access-control-allow-credentials) \` header has to be present too:



```http
Access-Control-Allow-Origin: https://foo.invalid
Access-Control-Allow-Credentials: true
```

If the response does not include those two headers with those values, the `failure`
callback will be invoked. However, any \``Set-Cookie`\` response headers will be
respected.

#### 3.3.7. CORS protocol exceptions

Specifications have allowed limited exceptions to the CORS safelist for non-safelisted
\``Content-Type`\` header values. These exceptions are made for requests that can be
triggered by web content but whose headers and bodies can be only minimally controlled by the web
content. Therefore, servers should expect cross-origin web content to be allowed to trigger
non-preflighted requests with the following non-safelisted \``Content-Type`\` header
values:

- \``application/csp-report`\` [\[CSP\]](https://fetch.spec.whatwg.org/#biblio-csp "Content Security Policy Level 3")
- \``application/expect-ct-report+json`\` [\[RFC9163\]](https://fetch.spec.whatwg.org/#biblio-rfc9163 "Expect-CT Extension for HTTP")
- \``application/xss-auditor-report`\`


- \``application/ocsp-request`\` [\[RFC6960\]](https://fetch.spec.whatwg.org/#biblio-rfc6960 "X.509 Internet Public Key Infrastructure Online Certificate Status Protocol - OCSP")

Specifications should avoid introducing new exceptions and should only do so with careful
consideration for the security consequences. New exceptions can be proposed by
[filing an issue](https://github.com/whatwg/fetch/issues/new).

### 3.5. \``Content-Type`\` header

The \``Content-Type`\` header is largely defined in HTTP. Its processing model is
defined here as the model defined in HTTP is not compatible with web content. [\[HTTP\]](https://fetch.spec.whatwg.org/#biblio-http "HTTP Semantics")

To
extract a MIME type
from a [header list](https://fetch.spec.whatwg.org/#concept-header-list) headers, run these steps. They return failure or a
[MIME type](https://mimesniff.spec.whatwg.org/#mime-type).

1. Let charset be null.



2. Let essence be null.



3. Let mimeType be null.



4. Let values be the result of
    [getting, decoding, and splitting](https://fetch.spec.whatwg.org/#concept-header-list-get-decode-split) \``Content-Type`\` from
    headers.



5. If values is null, then return failure.



6. [For each](https://infra.spec.whatwg.org/#list-iterate) value of values:


1. Let temporaryMimeType be the result of [parsing](https://mimesniff.spec.whatwg.org/#parse-a-mime-type) value.



2. If temporaryMimeType is failure or its [essence](https://mimesniff.spec.whatwg.org/#mime-type-essence) is
       "`*/*`", then [continue](https://infra.spec.whatwg.org/#iteration-continue).



3. Set mimeType to temporaryMimeType.



4. If mimeType’s [essence](https://mimesniff.spec.whatwg.org/#mime-type-essence) is not essence, then:


      1. Set charset to null.



      2. If mimeType’s [parameters](https://mimesniff.spec.whatwg.org/#parameters)\["`charset`"\]
          [exists](https://infra.spec.whatwg.org/#map-exists), then set charset to mimeType’s
          [parameters](https://mimesniff.spec.whatwg.org/#parameters)\["`charset`"\].



      3. Set essence to mimeType’s [essence](https://mimesniff.spec.whatwg.org/#mime-type-essence).
5. Otherwise, if mimeType’s
       [parameters](https://mimesniff.spec.whatwg.org/#parameters)\["`charset`"\] does not [exist](https://infra.spec.whatwg.org/#map-exists), and
       charset is non-null, set mimeType’s
       [parameters](https://mimesniff.spec.whatwg.org/#parameters)\["`charset`"\] to charset.
7. If mimeType is null, then return failure.



8. Return mimeType.


When [extract a MIME type](https://fetch.spec.whatwg.org/#concept-header-extract-mime-type) returns failure or a [MIME type](https://mimesniff.spec.whatwg.org/#mime-type) whose
[essence](https://mimesniff.spec.whatwg.org/#mime-type-essence) is incorrect for a given format, treat this as a fatal error.
Existing web platform features have not always followed this pattern, which has been a major source
of security vulnerabilities in those features over the years. In contrast, a
[MIME type](https://mimesniff.spec.whatwg.org/#mime-type)’s [parameters](https://mimesniff.spec.whatwg.org/#parameters) can typically be safely ignored.

This is how [extract a MIME type](https://fetch.spec.whatwg.org/#concept-header-extract-mime-type) functions in practice:

| ```http<br>Content-Type: text/html;charset=gbk;a=b, text/html;x=y<br>``` | `text/html;x=y;charset=gbk` |
| ```http<br>Content-Type: text/html;charset=gbk;a=b<br>Content-Type: text/html;x=y<br>``` |

1. If mimeType is failure, then return fallbackEncoding.



2. If mimeType\["`charset`"\] does not [exist](https://infra.spec.whatwg.org/#map-exists), then return
    fallbackEncoding.



3. Let tentativeEncoding be the result of [getting an encoding](https://encoding.spec.whatwg.org/#concept-encoding-get) from
    mimeType\["`charset`"\].



4. If tentativeEncoding is failure, then return fallbackEncoding.
