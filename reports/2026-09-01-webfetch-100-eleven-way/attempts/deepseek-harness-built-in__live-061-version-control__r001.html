**Version control** (also known as **revision control**, **source control**, and **source code management**) is the [software engineering](https://en.wikipedia.org/wiki/Software_engineering_management "Software engineering management") practice of controlling, organizing, and tracking different versions in history of [computer files](https://en.wikipedia.org/wiki/Computer_file "Computer file") – primarily [source code](https://en.wikipedia.org/wiki/Source_code "Source code") [text files](https://en.wikipedia.org/wiki/Text_files "Text files"), but generally any type of file.

Version control is a component of [software configuration management](https://en.wikipedia.org/wiki/Software_configuration_management "Software configuration management").[\[1\]](#cite_note-Mercurial-1)

A **version control system** is a [software tool](https://en.wikipedia.org/wiki/Software_tool "Software tool") that automates version control. Alternatively, version control is embedded as a feature of some systems such as [word processors](https://en.wikipedia.org/wiki/Word_processor "Word processor"), [spreadsheets](https://en.wikipedia.org/wiki/Spreadsheet "Spreadsheet"), collaborative [web docs](https://en.wikipedia.org/wiki/Groupware "Groupware"),[\[2\]](#cite_note-2) and [content management systems](https://en.wikipedia.org/wiki/Content_management_system "Content management system"), such as [Wikipedia's page history](https://en.wikipedia.org/wiki/Help:Page_history "Help:Page history").

Version control includes options to view old versions and to [revert](https://en.wikipedia.org/wiki/Reversion_\(software_development\) "Reversion (software development)") a file to a previous version.

## Overview

\[[edit](/w/index.php?title=Version_control&action=edit&section=1 "Edit section: Overview")\]

As teams develop software, it is common to [deploy](https://en.wikipedia.org/wiki/Software_deployment "Software deployment") multiple versions of the same software, and for different developers to work on one or more different versions simultaneously. [Bugs](https://en.wikipedia.org/wiki/Software_bug "Software bug") or features of the software are often only present in certain versions (because of the fixing of some problems and the introduction of others as the program develops). Therefore, for the purposes of locating and fixing bugs, it is vitally important to be able to retrieve and run different versions of the software to determine in which version(s) the problem occurs. It may also be necessary to develop two versions of the software concurrently: for instance, where one version has bugs fixed, but no new features ([branch](https://en.wikipedia.org/wiki/Branching_\(revision_control\) "Branching (revision control)")), while the other version is where new features are worked on ([trunk](https://en.wikipedia.org/wiki/Trunk_\(software\) "Trunk (software)")).

At the simplest level, developers could simply retain multiple copies of the different versions of the program, and label them appropriately. This simple approach has been used in many large software projects. While this method can work, it is inefficient as many near-identical copies of the program have to be maintained. This requires a lot of self-discipline on the part of developers and often leads to mistakes. Since the code base is the same, it also requires granting read-write-execute permission to a set of developers, and this adds the pressure of someone managing permissions so that the code base is not compromised, which adds more complexity. Consequently, systems to automate some or all of the revision control process have been developed. This [abstracts](https://en.wikipedia.org/wiki/Abstraction_\(computer_science\) "Abstraction (computer science)") most operational steps (hides them from ordinary users).

Moreover, in software development, legal and business practice, and other environments, it has become increasingly common for a single document or snippet of code to be edited by a team, the members of which may be geographically dispersed and may pursue different and even contrary interests. Sophisticated revision control that tracks and accounts for ownership of changes to documents and code may be extremely helpful or even indispensable in such situations.

Revision control may also track changes to [configuration files](https://en.wikipedia.org/wiki/Configuration_files "Configuration files"), such as those typically stored in `/etc` or `/usr/local/etc` on [Unix](https://en.wikipedia.org/wiki/Unix "Unix") systems. This gives system administrators another way to easily track changes made and a way to roll back to earlier versions should the need arise.

Many version control systems identify the version of a file as a number or letter, called the _version number_, _version_, _revision number_, _revision_, or _revision level_. For example, the first version of a file might be version _1_. When the file is changed the next version is _2_. Each version is associated with a [timestamp](https://en.wikipedia.org/wiki/Timestamp "Timestamp") and the person making the change. Revisions can be compared, restored, and, with some types of files, merged.[\[3\]](#cite_note-3)

## History

\[[edit](/w/index.php?title=Version_control&action=edit&section=2 "Edit section: History")\]

See also: [Comparison of version control software § History and adoption](https://en.wikipedia.org/wiki/Comparison_of_version_control_software#History_and_adoption "Comparison of version control software")

IBM's OS/360 [IEBUPDTE](https://en.wikipedia.org/wiki/Support_programs_for_OS/360_and_successors#IEBUPDTE "Support programs for OS/360 and successors") software update tool dates back to 1962, arguably a precursor to version control system tools. Two source management and version control packages that were heavily used by IBM 360/370 installations were [The Librarian](https://en.wikipedia.org/wiki/The_Librarian_\(version_control_system\) "The Librarian (version control system)") and [Panvalet](https://en.wikipedia.org/wiki/Panvalet "Panvalet").[\[4\]](#cite_note-4)[\[5\]](#cite_note-5)

A full system designed for source code control was started in 1972: the [Source Code Control System](https://en.wikipedia.org/wiki/Source_Code_Control_System "Source Code Control System") (SCCS), again for the OS/360. SCCS's user manual, especially the introduction, which was published on December 4, 1975, implied that it was the first deliberate revision control system.[\[6\]](#cite_note-6) The [Revision Control System](https://en.wikipedia.org/wiki/Revision_Control_System "Revision Control System") (RCS) followed in 1982[\[7\]](#cite_note-7) and, later, [Concurrent Versions System](https://en.wikipedia.org/wiki/Concurrent_Versions_System "Concurrent Versions System") (CVS) added network and concurrent development features to RCS. After CVS, a dominant successor was [Subversion](https://en.wikipedia.org/wiki/Apache_Subversion "Apache Subversion"),[\[8\]](#cite_note-8) followed by the rise of [distributed version control](https://en.wikipedia.org/wiki/Distributed_version_control "Distributed version control") tools such as [Git](https://en.wikipedia.org/wiki/Git "Git").[\[9\]](#cite_note-9)

## Structure

\[[edit](/w/index.php?title=Version_control&action=edit&section=3 "Edit section: Structure")\]

Revision control manages changes to a set of data over time. These changes can be structured in various ways.

Often the data is thought of as a collection of many individual items, such as files or documents, and changes to individual files are tracked. This is in line with the notion of keeping files separate but causes problems when identity changes, which happens when files are renamed, split or merged. Accordingly, some systems such as [Git](https://en.wikipedia.org/wiki/Git "Git"), consider changes to the data as a whole instead, which is less intuitive for simple changes but simplifies more complex changes.

When data that is under revision control is modified, after being retrieved by _checking out,_ this is not in general immediately reflected in the revision control system (in the _[repository](https://en.wikipedia.org/wiki/Repository_\(version_control\) "Repository (version control)")_), but must instead be _checked in_ or _committed._ A copy outside of revision control is known as a "working copy". As a simple example, when editing a computer file, the data stored in memory by the editing program is the working copy, which is committed by saving the file. Concretely, one may print out a document, edit it by hand, and only later manually input the changes into a computer and save it. For source code control, the working copy is instead a copy of all files in a particular revision, generally stored locally on the developer's computer;[\[note 1\]](#cite_note-10) in this case saving the file only changes the working copy, and checking into the repository is a separate step.

If multiple people are working on a single data set or document, they are implicitly creating branches of the data (in their working copies), and thus issues of merging arise, as discussed below. For simple collaborative document editing, this can be prevented by using [file locking](https://en.wikipedia.org/wiki/File_locking "File locking") or simply avoiding working on the same document that someone else is working on.

Revision control systems are often centralized, with a single authoritative data store, the _repository,_ and check-outs and check-ins done with reference to this central repository. Alternatively, in [distributed revision control](https://en.wikipedia.org/wiki/Distributed_revision_control "Distributed revision control"), no single repository is authoritative, and data can be checked out and checked into any repository. When checking into a different repository, this is interpreted as a merge or patch.

### Graph structure

\[[edit](/w/index.php?title=Version_control&action=edit&section=4 "Edit section: Graph structure")\]

[![](//upload.wikimedia.org/wikipedia/commons/thumb/a/af/Revision_controlled_project_visualization-2010-24-02.svg/250px-Revision_controlled_project_visualization-2010-24-02.svg.png?utm_source=en.wikipedia.org&utm_campaign=parser&utm_content=thumbnail)](https://en.wikipedia.org/wiki/File:Revision_controlled_project_visualization-2010-24-02.svg)

Example history graph of a revision-controlled project, with the trunk in green and the branches in yellow; the graph is not a tree, however, due to presence of merges (the red arrows).

In terms of [graph theory](https://en.wikipedia.org/wiki/Graph_theory "Graph theory"), revisions are generally thought of as a line of development (the _trunk_) with branches off of this, forming a directed tree, visualized as one or more parallel lines of development (the "mainlines" of the branches) branching off a trunk. In reality the structure is more complicated, forming a [directed acyclic graph](https://en.wikipedia.org/wiki/Directed_acyclic_graph "Directed acyclic graph"), but for many purposes "tree with merges" is an adequate approximation.

Revisions occur in sequence over time, and thus can be arranged in order, either by revision number or timestamp.[\[note 2\]](#cite_note-11) Revisions are based on past revisions, though it is possible to largely or completely replace an earlier revision, such as "delete all existing text, insert new text". In the simplest case, with no branching or undoing, each revision is based on its immediate predecessor alone, and they form a simple line, with a single latest version, the "HEAD" revision or _tip_. In [graph theory](https://en.wikipedia.org/wiki/Graph_theory "Graph theory") terms, drawing each revision as a point and each "derived revision" relationship as an arrow (conventionally pointing from older to newer, in the same direction as time), this is a [linear graph](https://en.wikipedia.org/wiki/Linear_graph "Linear graph"). If there is branching, so multiple future revisions are based on a past revision, or undoing, so a revision can depend on a revision older than its immediate predecessor, then the resulting graph is instead a [directed tree](https://en.wikipedia.org/wiki/Directed_tree "Directed tree") (each node can have more than one child), and has multiple tips, corresponding to the revisions without children ("latest revision on each branch").[\[note 3\]](#cite_note-12) In principle the resulting tree need not have a preferred tip ("main" latest revision) – just various different revisions – but in practice one tip is generally identified as HEAD. When a new revision is based on HEAD, it is either identified as the new HEAD, or considered a new branch.[\[note 4\]](#cite_note-13) The list of revisions from the start to HEAD (in graph theory terms, the unique path in the tree, which forms a linear graph as before) is the _trunk_ or _mainline._[\[note 5\]](#cite_note-14) Conversely, when a revision can be based on more than one previous revision (when a node can have more than one _parent_), the resulting process is called a _[merge](https://en.wikipedia.org/wiki/Merge_\(revision_control\) "Merge (revision control)"),_ and is one of the most complex aspects of revision control. This most often occurs when changes occur in multiple branches (most often two, but more are possible), which are then merged into a single branch incorporating both changes. If these changes overlap, it may be difficult or impossible to merge, and require manual intervention or rewriting.

In the presence of merges, the resulting graph is no longer a tree, as nodes can have multiple parents, but is instead a rooted [directed acyclic graph](https://en.wikipedia.org/wiki/Directed_acyclic_graph "Directed acyclic graph") (DAG). The graph is acyclic since parents are always backwards in time, and rooted because there is an oldest version. Assuming there is a trunk, merges from branches can be considered as "external" to the tree – the changes in the branch are packaged up as a _patch,_ which is applied to HEAD (of the trunk), creating a new revision without any explicit reference to the branch, and preserving the tree structure. Thus, while the actual relations between versions form a DAG, this can be considered a tree plus merges, and the trunk itself is a line.

In distributed revision control, in the presence of multiple repositories these may be based on a single original version (a root of the tree), but there need not be an original root - instead there can be a separate root (oldest revision) for each repository. This can happen, for example, if two people start working on a project separately. Similarly, in the presence of multiple data sets (multiple projects) that exchange data or merge, there is no single root, though for simplicity one may think of one project as primary and the other as secondary, merged into the first with or without its own revision history.

## Specialized strategies

\[[edit](/w/index.php?title=Version_control&action=edit&section=5 "Edit section: Specialized strategies")\]

Engineering revision control developed from formalized processes based on tracking revisions of early [blueprints](https://en.wikipedia.org/wiki/Blueprint "Blueprint") or [bluelines](https://en.wikipedia.org/wiki/Whiteprint "Whiteprint")["MIL-STD-100G: Department of Defense Standard Practice for Engineering Drawings"](https://apps.dtic.mil/sti/tr/pdf/ADA361444.pdf) (PDF). United States Department of Defense. 9 June 1997. Retrieved 2026-05-16.. This system of control implicitly allowed returning to an earlier state of the design, for cases in which an engineering dead-end was reached in the development of the design. A revision table was used to keep track of the changes made. Additionally, the modified areas of the drawing were highlighted using revision clouds.

### In business and law

\[[edit](/w/index.php?title=Version_control&action=edit&section=6 "Edit section: In business and law")\]

Version control is widespread in business and law. Indeed, "contract redline" and "legal blackline" are some of the earliest forms of revision control,[\[10\]](#cite_note-15) and are still employed in business and law with varying degrees of sophistication. The most sophisticated techniques are beginning to be used for the electronic tracking of changes to [CAD files](https://en.wikipedia.org/wiki/CAD_file "CAD file") (see [product data management](https://en.wikipedia.org/wiki/Product_data_management "Product data management")), supplanting the "manual" electronic implementation of traditional revision control. [\[11\]](#cite_note-16)

### In game development

\[[edit](/w/index.php?title=Version_control&action=edit&section=7 "Edit section: In game development")\]

Game development often involves large binary files and teams working together across different disciplines. As a result, game studios use version control systems with good support for large binary files, file locking, and fast synchronization. Common tools include Perforce and several newer cloud-based systems.[\[12\]](#cite_note-17)[\[13\]](#cite_note-18)

## Source-management models

\[[edit](/w/index.php?title=Version_control&action=edit&section=8 "Edit section: Source-management models")\]

Traditional revision control systems use a centralized model where all the revision control functions take place on a shared [server](https://en.wikipedia.org/wiki/Server_\(computing\) "Server (computing)"). If two developers try to change the same file at the same time, without some method of managing access the developers may end up overwriting each other's work. Centralized revision control systems solve this problem in one of two different "source management models": file locking and version merging.

### Atomic operations

\[[edit](/w/index.php?title=Version_control&action=edit&section=9 "Edit section: Atomic operations")\]

Main article: [Atomic commit](https://en.wikipedia.org/wiki/Atomic_commit "Atomic commit")

An operation is _atomic_ if the system is left in a consistent state even if the operation is interrupted. The _commit_ operation is usually the most critical in this sense. Commits tell the revision control system to make a group of changes final, and available to all users. Not all revision control systems have atomic commits; Concurrent Versions System lacks this feature.[\[14\]](#cite_note-19)

### File locking

\[[edit](/w/index.php?title=Version_control&action=edit&section=10 "Edit section: File locking")\]

The simplest method of preventing "[concurrent access](https://en.wikipedia.org/wiki/Concurrent_access "Concurrent access")" problems involves [locking files](https://en.wikipedia.org/wiki/File_locking "File locking") so that only one developer at a time has write access to the central "[repository](https://en.wikipedia.org/wiki/Repository_\(version_control\) "Repository (version control)")" copies of those files. Once one developer "checks out" a file, others can read that file, but no one else may change that file until that developer "checks in" the updated version (or cancels the checkout).

File locking has both merits and drawbacks. It can provide some protection against difficult [merge conflicts](https://en.wikipedia.org/wiki/Edit_conflict "Edit conflict") when a user is making radical changes to many sections of a large file (or group of files). If the files are left exclusively locked for too long, other developers may be tempted to bypass the revision control software and change the files locally, forcing a difficult manual merge when the other changes are finally checked in. In a large organization, files can be left "checked out" and locked and forgotten about as developers move between projects - these tools may or may not make it easy to see who has a file checked out.

### Version merging

\[[edit](/w/index.php?title=Version_control&action=edit&section=11 "Edit section: Version merging")\]

Main article: [Merge (version control)](https://en.wikipedia.org/wiki/Merge_\(version_control\) "Merge (version control)")

Most version control systems allow multiple developers to edit the same file at the same time. The first developer to "check in" changes to the central repository always succeeds. The system may provide facilities to [merge](https://en.wikipedia.org/wiki/Merge_\(revision_control\) "Merge (revision control)") further changes into the central repository, and preserve the changes from the first developer when other developers check in.

Merging two files can be a very delicate operation, and usually possible only if the [data structure](https://en.wikipedia.org/wiki/Data_structure "Data structure") is simple, as in [text files](https://en.wikipedia.org/wiki/Text_file "Text file"). The result of a merge of two [image files](https://en.wikipedia.org/wiki/Image_file "Image file") might not result in an image file at all. The second developer checking in files will need to take care with the merge, to make sure that the changes are compatible and that the merge operation does not introduce its own [logic](https://en.wikipedia.org/wiki/Logic "Logic") errors within the files. These problems limit the availability of automatic or semi-automatic merge operations mainly to simple text-based documents, unless a specific merge [plugin](https://en.wikipedia.org/wiki/Plug-in_\(computing\) "Plug-in (computing)") is available for the file types.

The concept of a _reserved edit_ can provide an optional means to explicitly lock a file for exclusive write access, even when a merging capability exists.

### Baselines, labels and tags

\[[edit](/w/index.php?title=Version_control&action=edit&section=12 "Edit section: Baselines, labels and tags")\]

Most revision control tools will use only one of these similar terms (baseline, label, tag) to refer to the action of identifying a snapshot ("label the project") or the record of the snapshot ("try it with baseline _X_"). Typically only one of the terms _baseline_, _label_, or _tag_ is used in documentation or discussion[\[15\]](#cite_note-20) ; they can be considered synonyms.

In most projects, some snapshots are more significant than others, such as those used to indicate published releases, branches, or milestones.

When both the term _baseline_ and either of _label_ or _tag_ are used together in the same context, _label_ and _tag_ usually refer to the mechanism within the tool of identifying or making the record of the snapshot, and _baseline_ indicates the increased significance of any given label or tag.

Most formal discussion of [configuration management](https://en.wikipedia.org/wiki/Configuration_management "Configuration management") uses the term [_baseline_](https://en.wikipedia.org/wiki/Baseline_\(configuration_management\) "Baseline (configuration management)").

## Distributed revision control

\[[edit](/w/index.php?title=Version_control&action=edit&section=13 "Edit section: Distributed revision control")\]

Main article: [Distributed version control](https://en.wikipedia.org/wiki/Distributed_version_control "Distributed version control")

Distributed revision control systems (DRCS) take a peer-to-peer approach, as opposed to the [client–server](https://en.wikipedia.org/wiki/Client–server_model "Client–server model") approach of centralized systems. Rather than a single, central repository on which clients synchronize, each peer's working copy of the codebase is a [bona-fide](https://en.wikipedia.org/wiki/Good_faith "Good faith") repository.[\[16\]](#cite_note-21) Distributed revision control conducts synchronization by exchanging [patches](https://en.wikipedia.org/wiki/Patch_\(computing\) "Patch (computing)") (change-sets) from peer to peer. This results in some important differences from a centralized system:

-   No canonical, reference copy of the codebase exists by default; only working copies.
-   Common operations (such as commits, viewing history, and reverting changes) are fast, because there is no need to communicate with a central server.[\[1\]](#cite_note-Mercurial-1): 7

Rather, communication is only necessary when pushing or pulling changes to or from other peers.

-   Each working copy effectively functions as a remote backup of the codebase and of its change-history, providing inherent protection against data loss.[\[1\]](#cite_note-Mercurial-1): 4

## Best practices

\[[edit](/w/index.php?title=Version_control&action=edit&section=14 "Edit section: Best practices")\]

Following best practices is necessary to obtain the full benefits of version control. Best practice may vary by version control tool and the field to which version control is applied. The generally accepted best practices in [software development](https://en.wikipedia.org/wiki/Software_development "Software development") include: making small/incremental changes; making [commits](https://en.wikipedia.org/wiki/Commit_\(version_control\) "Commit (version control)") which involve only one task or fix -- a corollary to this is to commit only code which works and does not knowingly break existing functionality; using branching to complete functionality before release; writing clear and descriptive commit messages, making what, why, and how clear in either the commit description or the code; and using a consistent branching strategy.[\[17\]](#cite_note-22) Other software development best practices such as [code review](https://en.wikipedia.org/wiki/Code_review "Code review") and automated [regression testing](https://en.wikipedia.org/wiki/Regression_testing "Regression testing") may assist in the following of version control best practices.

## Costs and benefits

\[[edit](/w/index.php?title=Version_control&action=edit&section=15 "Edit section: Costs and benefits")\]

Costs and benefits will vary dependent upon the version control tool chosen and the field in which it is applied. This section speaks to the field of software development, where version control is widely applied.

### Costs

\[[edit](/w/index.php?title=Version_control&action=edit&section=16 "Edit section: Costs")\]

In addition to the costs of licensing the version control software, using version control requires time and effort. The concepts underlying version control must be understood and the technical particulars required to operate the version control software chosen must be learned. Version control best practices must be learned and integrated into the organization's existing software development practices. Management effort may be required to maintain the discipline needed to follow best practices in order to obtain useful benefit.

### Benefits

\[[edit](/w/index.php?title=Version_control&action=edit&section=17 "Edit section: Benefits")\]

#### Allows for reverting changes

\[[edit](/w/index.php?title=Version_control&action=edit&section=18 "Edit section: Allows for reverting changes")\]

A core benefit is the ability to keep history and revert changes, allowing the developer to easily undo changes. This gives the developer more opportunity to experiment, eliminating the fear of breaking existing code.[\[18\]](#cite_note-23)

#### Branching simplifies deployment, maintenance and development

\[[edit](/w/index.php?title=Version_control&action=edit&section=19 "Edit section: Branching simplifies deployment, maintenance and development")\]

Branching assists with [deployment](https://en.wikipedia.org/wiki/Software_deployment "Software deployment") and [release management](https://en.wikipedia.org/wiki/Release_management "Release management"). Branching and merging, the production, packaging, and labeling of source code [patches](https://en.wikipedia.org/wiki/Patch_\(computing\) "Patch (computing)") and the easy application of patches to code bases, simplifies the maintenance and concurrent development of the multiple code bases associated with the various stages of the deployment process; development, testing, staging, production, etc.[\[19\]](#cite_note-24)

#### Damage mitigation, accountability and process and design improvement

\[[edit](/w/index.php?title=Version_control&action=edit&section=20 "Edit section: Damage mitigation, accountability and process and design improvement")\]

There can be damage mitigation, accountability, process and design improvement, and other benefits associated with the record keeping provided by version control, the tracking of who did what, when, why, and how.[\[20\]](#cite_note-25)

When bugs arise, knowing what was done when helps with damage mitigation and recovery by assisting in the identification of what problems exist, how long they have existed, and determining problem scope and solutions.[\[21\]](#cite_note-26) Previous versions can be installed and tested to verify conclusions reached by examination of code and commit messages.[\[22\]](#cite_note-27)

#### Simplifies debugging

\[[edit](/w/index.php?title=Version_control&action=edit&section=21 "Edit section: Simplifies debugging")\]

Version control can greatly simplify debugging. The application of a test case to multiple versions can quickly identify the change which introduced a bug.[\[23\]](#cite_note-28) The developer need not be familiar with the entire code base and can focus instead on the code that introduced the problem.

#### Improves collaboration and communication

\[[edit](/w/index.php?title=Version_control&action=edit&section=22 "Edit section: Improves collaboration and communication")\]

Version control enhances collaboration in multiple ways. Since version control can identify conflicting changes, i.e. incompatible changes made to the same lines of code, there is less need for coordination among developers.[\[24\]](#cite_note-29)

The packaging of commits, branches, and all the associated commit messages and version labels, improves communication between developers, both in the moment and over time.[\[25\]](#cite_note-30) Better communication, whether instant or deferred, can improve the code review process, the testing process, and other critical aspects of the software development process.

## Integration

\[[edit](/w/index.php?title=Version_control&action=edit&section=23 "Edit section: Integration")\]

Some of the more advanced revision-control tools offer many other facilities, allowing deeper integration with other tools and software-engineering processes.

### Integrated development environment

\[[edit](/w/index.php?title=Version_control&action=edit&section=24 "Edit section: Integrated development environment")\]

[Plugins](https://en.wikipedia.org/wiki/Plug-in_\(computing\) "Plug-in (computing)") are often available for [IDEs](https://en.wikipedia.org/wiki/Integrated_development_environment "Integrated development environment") such as [Oracle JDeveloper](https://en.wikipedia.org/wiki/Oracle_JDeveloper "Oracle JDeveloper"), [IntelliJ IDEA](https://en.wikipedia.org/wiki/IntelliJ_IDEA "IntelliJ IDEA"), [Eclipse](https://en.wikipedia.org/wiki/Eclipse_\(computing\) "Eclipse (computing)"), [Visual Studio](https://en.wikipedia.org/wiki/Visual_Studio "Visual Studio"), [Delphi](https://en.wikipedia.org/wiki/Delphi_\(programming_language\) "Delphi (programming language)"), [NetBeans IDE](https://en.wikipedia.org/wiki/NetBeans "NetBeans"), [Xcode](https://en.wikipedia.org/wiki/Xcode "Xcode"), and [GNU Emacs](https://en.wikipedia.org/wiki/GNU_Emacs "GNU Emacs") (via vc.el). ## Common terminology

\[[edit](/w/index.php?title=Version_control&action=edit&section=25 "Edit section: Common terminology")\]

Terminology can vary from system to system, but some terms in common usage include:[\[27\]](#cite_note-32)

### Baseline

\[[edit](/w/index.php?title=Version_control&action=edit&section=26 "Edit section: Baseline")\]

Main article: [Baseline (configuration management)](https://en.wikipedia.org/wiki/Baseline_\(configuration_management\) "Baseline (configuration management)")

An approved revision of a document or source file to which subsequent changes can be made. See [baselines, labels and tags](#Baselines,_labels_and_tags).

### Blame

\[[edit](/w/index.php?title=Version_control&action=edit&section=27 "Edit section: Blame")\]

A search for the author and revision that last modified a particular line.

### Branch

\[[edit](/w/index.php?title=Version_control&action=edit&section=28 "Edit section: Branch")\]

Main article: [Branching (revision control)](https://en.wikipedia.org/wiki/Branching_\(revision_control\) "Branching (revision control)")

A set of files under version control may be _branched_ or _forked_ at a point in time so that, from that time forward, two copies of those files may develop at different speeds or in different ways independently of each other.

### Change

\[[edit](/w/index.php?title=Version_control&action=edit&section=29 "Edit section: Change")\]

A _change_ (or _[diff](https://en.wikipedia.org/wiki/Diff "Diff")_, or _[delta](https://en.wikipedia.org/wiki/Delta_encoding "Delta encoding")_) represents a specific modification to a document under version control. The granularity of the modification considered a change varies between version control systems.

### Change list

\[[edit](/w/index.php?title=Version_control&action=edit&section=30 "Edit section: Change list")\]

On many version control systems with [atomic](https://en.wikipedia.org/wiki/Atomic_transaction "Atomic transaction") multi-change commits, a _change list_ (or _CL_), _change set_, _update_, or _[patch](https://en.wikipedia.org/wiki/Patch_\(computing\) "Patch (computing)")_ identifies the set of _changes_ made in a single commit. This can also represent a sequential view of the source code, allowing the examination of source as of any particular changelist ID.

### Checkout

\[[edit](/w/index.php?title=Version_control&action=edit&section=31 "Edit section: Checkout")\]

To _check out_ (or _co_) is to create a local working copy from the repository. A user may specify a specific revision or obtain the latest. The term 'checkout' can also be used as a noun to describe the working copy. When a file has been checked out from a shared file server, it cannot be edited by other users. Think of it like a hotel, when you check out, you no longer have access to its amenities.

### Clone

\[[edit](/w/index.php?title=Version_control&action=edit&section=32 "Edit section: Clone")\]

_Cloning_ means creating a repository containing the revisions from another repository. This is equivalent to _push_ing or _pull_ing into an empty (newly initialized) repository. As a noun, two repositories can be said to be _clone_s if they are kept synchronized, and contain the same revisions.

### Commit (noun)

\[[edit](/w/index.php?title=Version_control&action=edit&section=33 "Edit section: Commit (noun)")\]

This section is an excerpt from [Changeset](https://en.wikipedia.org/wiki/Changeset "Changeset").\[[edit](https://en.wikipedia.org/w/index.php?title=Changeset&action=edit)\]

In version control software, a [changeset](https://en.wikipedia.org/wiki/Changeset "Changeset") (also known as commit[\[28\]](#cite_note-Changeset_gitglossary-changeset-33) and revision[\[29\]](#cite_note-34)[\[30\]](#cite_note-35)) is a set of alterations packaged together, along with meta-information about the alterations. A changeset describes the exact differences between two successive versions in the version control system's repository of changes. Changesets are typically treated as an [atomic](https://en.wikipedia.org/wiki/Atomicity_\(database_systems\) "Atomicity (database systems)") unit, an indivisible set, by version control systems. This is one [synchronization model](https://en.wikipedia.org/wiki/Synchronization_model "Synchronization model").[\[31\]](#cite_note-36)[\[32\]](#cite_note-37)

### Commit (verb)

\[[edit](/w/index.php?title=Version_control&action=edit&section=34 "Edit section: Commit (verb)")\]

Main article: [Commit (revision control)](https://en.wikipedia.org/wiki/Commit_\(revision_control\) "Commit (revision control)")

To _[commit](https://en.wikipedia.org/wiki/Commit_\(revision_control\) "Commit (revision control)")_ (_check in_, _ci_ or, more rarely, _install_, _submit_ or _record_) is to write or merge the changes made in the working copy back to the repository. A commit contains metadata, typically the author information and a commit message that describes the change.

### Commit message

\[[edit](/w/index.php?title=Version_control&action=edit&section=35 "Edit section: Commit message")\]

A short note, written by the developer, stored with the commit, which describes the commit. Ideally, it records why the modification was made, a description of the modification's effect or purpose, and non-obvious aspects of how the change works.

### Conflict

\[[edit](/w/index.php?title=Version_control&action=edit&section=36 "Edit section: Conflict")\]

A conflict occurs when different parties make changes to the same document, and the system is unable to reconcile the changes. A user must _resolve_ the conflict by combining the changes, or by selecting one change in favour of the other.

### Delta compression

\[[edit](/w/index.php?title=Version_control&action=edit&section=37 "Edit section: Delta compression")\]

Main article: [Delta compression](https://en.wikipedia.org/wiki/Delta_compression "Delta compression")

Most revision control software uses [delta compression](https://en.wikipedia.org/wiki/Delta_compression "Delta compression"), which retains only the differences between successive versions of files. This allows for more efficient storage of many different versions of files.

### Dynamic stream

\[[edit](/w/index.php?title=Version_control&action=edit&section=38 "Edit section: Dynamic stream")\]

A stream in which some or all file versions are mirrors of the parent stream's versions.

### Export

\[[edit](/w/index.php?title=Version_control&action=edit&section=39 "Edit section: Export")\]

_Exporting_ is the act of obtaining the files from the repository. It is similar to _checking out_ except that it creates a clean directory tree without the version-control metadata used in a working copy. This is often used prior to publishing the contents, for example.

### Fetch

\[[edit](/w/index.php?title=Version_control&action=edit&section=40 "Edit section: Fetch")\]

See _pull_.

### Forward integration

\[[edit](/w/index.php?title=Version_control&action=edit&section=41 "Edit section: Forward integration")\]

The process of merging changes made in the main _trunk_ into a development (feature or team) branch.

### Head

\[[edit](/w/index.php?title=Version_control&action=edit&section=42 "Edit section: Head")\]

Also sometimes called _tip_, this refers to the most recent commit, either to the trunk or to a branch. The trunk and each branch have their own head, though HEAD is sometimes loosely used to refer to the trunk.[\[33\]](#cite_note-38)

### Import

\[[edit](/w/index.php?title=Version_control&action=edit&section=43 "Edit section: Import")\]

_Importing_ is the act of copying a local directory tree (that is not currently a working copy) into the repository for the first time.

### Initialize

\[[edit](/w/index.php?title=Version_control&action=edit&section=44 "Edit section: Initialize")\]

To create a new, empty repository.

### Interleaved deltas

\[[edit](/w/index.php?title=Version_control&action=edit&section=45 "Edit section: Interleaved deltas")\]

Some revision control software uses [Interleaved deltas](https://en.wikipedia.org/wiki/Interleaved_deltas "Interleaved deltas"), a method that allows storing the history of text based files in a more efficient way than by using [Delta compression](https://en.wikipedia.org/wiki/Delta_compression "Delta compression").

### Label

\[[edit](/w/index.php?title=Version_control&action=edit&section=46 "Edit section: Label")\]

See _tag_.

### Locking

\[[edit](/w/index.php?title=Version_control&action=edit&section=47 "Edit section: Locking")\]

Main article: [File locking](https://en.wikipedia.org/wiki/File_locking "File locking")

When a developer _[locks](https://en.wikipedia.org/wiki/File_locking "File locking")_ a file, no one else can update that file until it is unlocked. Locking can be supported by the version control system, or via informal communications between developers (aka _social locking_).

### Mainline

\[[edit](/w/index.php?title=Version_control&action=edit&section=48 "Edit section: Mainline")\]

Similar to _trunk_, but there can be a mainline for each branch.

### Merge

\[[edit](/w/index.php?title=Version_control&action=edit&section=49 "Edit section: Merge")\]

Main article: [Merge (revision control)](https://en.wikipedia.org/wiki/Merge_\(revision_control\) "Merge (revision control)")

A _merge_ or _integration_ is an operation in which two sets of changes are applied to a file or set of files. Some sample scenarios are as follows:

-   A user, working on a set of files, _updates_ or _syncs_ their working copy with changes made, and checked into the repository, by other users.[\[34\]](#cite_note-FOOTNOTECollins-SussmanFitzpatrickPilato2004[httpsvnbookred-beancomen15svntourcyclehtmlsvntourcycleresolve_1.5:_SVN_tour_cycle_resolve]-39)
-   A user tries to _check in_ files that have been updated by others since the files were _checked out_, and the _revision control software_ automatically merges the files (typically, after prompting the user if it should proceed with the automatic merge, and in some cases only doing so if the merge can be clearly and reasonably resolved).
-   A _branch_ is created, the code in the files is independently edited, and the updated branch is later incorporated into a single, unified _trunk_.
-   A set of files is _branched_, a problem that existed before the branching is fixed in one branch, and the fix is then merged into the other branch. (This type of selective merge is sometimes known as a _cherry pick_ to distinguish it from the complete merge in the previous case.)

### Promote

\[[edit](/w/index.php?title=Version_control&action=edit&section=50 "Edit section: Promote")\]

The act of copying file content from a less controlled location into a more controlled location. For example, from a user's workspace into a repository, or from a stream to its parent.[\[35\]](#cite_note-40)

### Pull, push

\[[edit](/w/index.php?title=Version_control&action=edit&section=51 "Edit section: Pull, push")\]

Copy revisions from one repository into another. _Pull_ is initiated by the receiving repository, while _push_ is initiated by the source. _Fetch_ is sometimes used as a synonym for _pull_, or to mean a _pull_ followed by an _update_.

### Pull request

\[[edit](/w/index.php?title=Version_control&action=edit&section=52 "Edit section: Pull request")\]

This section is an excerpt from [Distributed version control § Pull requests](https://en.wikipedia.org/wiki/Distributed_version_control#Pull_requests "Distributed version control").\[[edit](https://en.wikipedia.org/w/index.php?title=Distributed_version_control&action=edit)\]

Contributions to a source code repository that uses a distributed version control system are commonly made by means of a pull request, also known as a merge request.[\[36\]](#cite_note-Distributed_version_control_gitlab-merge-req-41) The contributor requests that the project maintainer _pull_ the source code change, hence the name "pull request". The maintainer has to _merge_ the pull request if the contribution should become part of the source base.[\[37\]](#cite_note-Distributed_version_control_ossw-42)

The developer creates a pull request to notify maintainers of a new change; a comment thread is associated with each pull request. This allows for [focused discussion of code changes](https://en.wikipedia.org/wiki/Code_review "Code review"). Submitted pull requests are visible to anyone with repository access. A pull request can be accepted or rejected by maintainers.[\[38\]](#cite_note-43)

Once the pull request is reviewed and approved, it is merged into the repository. Depending on the established workflow, the code may need to be tested before being included into official release. Therefore, some projects contain a special branch for merging untested pull requests.[\[37\]](#cite_note-Distributed_version_control_ossw-42)[\[39\]](#cite_note-44) Other projects run an automated test suite on every pull request, using a [continuous integration](https://en.wikipedia.org/wiki/Continuous_integration "Continuous integration") tool, and the reviewer checks that any new code has appropriate test coverage.

### Repository

\[[edit](/w/index.php?title=Version_control&action=edit&section=53 "Edit section: Repository")\]

This section is an excerpt from [Repository (version control)](https://en.wikipedia.org/wiki/Repository_\(version_control\) "Repository (version control)").\[[edit](https://en.wikipedia.org/w/index.php?title=Repository_\(version_control\)&action=edit)\]

In version control systems, a [repository](https://en.wikipedia.org/wiki/Repository_\(version_control\) "Repository (version control)") is a data structure that stores either [metadata](https://en.wikipedia.org/wiki/Metadata "Metadata") or metadata and files for a set of files or [directory structure](https://en.wikipedia.org/wiki/Directory_structure "Directory structure").[\[40\]](#cite_note-45) Depending on whether the version control system in use is distributed, like [Git](https://en.wikipedia.org/wiki/Git "Git") or [Mercurial](https://en.wikipedia.org/wiki/Mercurial "Mercurial"), or centralized, like [Subversion](https://en.wikipedia.org/wiki/Apache_Subversion "Apache Subversion"), [CVS](https://en.wikipedia.org/wiki/Concurrent_Versions_System "Concurrent Versions System"), or [Perforce](https://en.wikipedia.org/wiki/Perforce "Perforce"), the whole set of information in the repository may be duplicated on every user's system or may be maintained on a single [server](https://en.wikipedia.org/wiki/Server_\(computing\) "Server (computing)").[\[41\]](#cite_note-Repository_\(version_control\)_Ernst-2018-46) Some of the metadata that a repository contains includes, among other things, a historical record of changes in the repository, a set of commit objects, and a set of references to commit objects, called _heads_.

### Resolve

\[[edit](/w/index.php?title=Version_control&action=edit&section=54 "Edit section: Resolve")\]

The act of user intervention to address a conflict between different changes to the same document.

### Reverse integration

\[[edit](/w/index.php?title=Version_control&action=edit&section=55 "Edit section: Reverse integration")\]

The process of merging different team branches into the main trunk of the versioning system.

### Reversion

\[[edit](/w/index.php?title=Version_control&action=edit&section=56 "Edit section: Reversion")\]

The abandonment of one or more recent changes in favor of a return to a previous version of the material at hand. A revert may be done for many reasons, including: fixing errors introduced by previous edits; restoring the material to a state that was not contentious until new disputes can be resolved; undoing [scope creep](https://en.wikipedia.org/wiki/Scope_creep "Scope creep"); and [regression testing](https://en.wikipedia.org/wiki/Regression_testing "Regression testing").

### Revision and version

\[[edit](/w/index.php?title=Version_control&action=edit&section=57 "Edit section: Revision and version")\]

A [version](https://en.wikipedia.org/wiki/Software_versioning "Software versioning") is any change in form. In SVK, a Revision is the state at a point in time of the entire tree in the repository.

### Share

\[[edit](/w/index.php?title=Version_control&action=edit&section=58 "Edit section: Share")\]

The act of making one file or folder available in multiple branches at the same time. When a shared file is changed in one branch, it is changed in other branches.

### Stream

\[[edit](/w/index.php?title=Version_control&action=edit&section=59 "Edit section: Stream")\]

A container for branched files that has a known relationship to other such containers. Streams form a hierarchy; each stream can inherit various properties (like versions, namespace, workflow rules, subscribers, etc.) from its parent stream.

### Tag

\[[edit](/w/index.php?title=Version_control&action=edit&section=60 "Edit section: Tag")\]

Main article: [Revision tag](https://en.wikipedia.org/wiki/Revision_tag "Revision tag")

A _[tag](https://en.wikipedia.org/wiki/Revision_tag "Revision tag")_ or _label_ refers to an important snapshot in time, consistent across many files. These files at that point may all be tagged with a user-friendly, meaningful name or revision number. See [baselines, labels and tags](#Baselines,_labels_and_tags).

### Trunk

\[[edit](/w/index.php?title=Version_control&action=edit&section=61 "Edit section: Trunk")\]

Main article: [Trunk (software)](https://en.wikipedia.org/wiki/Trunk_\(software\) "Trunk (software)")

The [trunk](https://en.wikipedia.org/wiki/Trunk_\(software\) "Trunk (software)") is the unique line of development that is not a branch (sometimes also called Baseline, Mainline or Master[\[42\]](#cite_note-47)[\[43\]](#cite_note-48))

### Update

\[[edit](/w/index.php?title=Version_control&action=edit&section=62 "Edit section: Update")\]

An _update_ (or _sync_, but _sync_ can also mean a combined _push_ and _pull_) merges changes made in the repository (by other people, for example) into the local _working copy_. _Update_ is also the term used by some CM tools (CM+, PLS, SMS) for the change package concept (see _changelist_). Synonymous with _checkout_ in revision control systems that require each repository to have exactly one working copy (common in distributed systems)

### Unlocking

\[[edit](/w/index.php?title=Version_control&action=edit&section=63 "Edit section: Unlocking")\]

Releasing a lock.

### Working copy

\[[edit](/w/index.php?title=Version_control&action=edit&section=64 "Edit section: Working copy")\]

The _working copy_ is the local copy of files from a repository, at a specific time or revision. All work done to the files in a repository is initially done on a working copy, hence the name. Conceptually, it is a _[sandbox](https://en.wikipedia.org/wiki/Sandbox_\(software_development\) "Sandbox (software development)")_.
