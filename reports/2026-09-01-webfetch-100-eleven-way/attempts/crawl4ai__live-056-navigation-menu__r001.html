### fix\(runtime\): give worker isolate threads the stack size we report

`resourceLimits.stackSizeMb` reports `DEFAULT_STACK_SIZE_MB` \(4,
matching Node\) for a `node:worker_threads` worker created without
explicit limits — but `op_create_worker` only called
`Builder::stack_size\(\)` when `stackSizeMb` was explicitly passed. So the
thread the worker's isolate actually ran on got Rust's 2MB default while
we told the user it was 4MB.

Beyond the reported value being wrong, 2MB leaves almost no native
headroom above V8's own JS stack limit \(`--stack-size`, ~1MB by
default\): with `--stack-size` raised above 2MB, recursing JS in a
default worker overflows the OS stack and **aborts the process** instead
of raising `RangeError`.

`DEFAULT_WORKER_STACK_SIZE_MB = 4` now applies to every worker isolate
thread; an explicit `stackSizeMb` still overrides.

New spec test
`node::worker_threads_resource_limits::resource_limits_default_stack_size`.
It was validated with a negative control — forcing the default back to
2MB makes it fail exactly as designed:

```
<thread 'worker-1' has overflowed its stack
<fatal runtime error: stack overflow, aborting
>caught RangeError: true
```

With the fix, all 4 tests in that spec pass.

### chore: drop dead Windows cargo config and fix a stack-size comment

Cargo evaluates `target.'cfg\(...\)'` specs against `rustc --print cfg
--target <triple>`, whose output **always contains `debug_assertions`**
regardless of the profile being built. Two consequences in
`.cargo/config.toml`, neither of which produced a warning:

- `cfg\(all\(windows, debug_assertions\)\)` has always matched **every**
Windows build, so `/STACK:4194304` has been applied to release all along
— despite its comment saying "in debug". Respelled `cfg\(windows\)`, which
states the existing effective behavior honestly.
- `cfg\(all\(windows, not\(debug_assertions\)\)\)` matched **nothing**, so its
`link-arg=/OPT:ICF` was dead config that never applied to any build.
Removed; it was redundant anyway, since rustc already passes
`/OPT:REF,ICF` when optimizing.

**This is a no-op**, verified by diffing the flags Cargo actually emits
for `x86_64-pc-windows-msvc` in both profiles, using the exact config
text from before and after. Identical in both. The check also directly
confirms both claims above: `/STACK:4194304` *is* emitted in release
before the change, and `/OPT:ICF` is emitted in neither profile before
the change.

A method caveat worth stating: `cargo build -v --target
x86_64-pc-windows-msvc` against the full repo timed out resolving the
dep graph before it printed any link args, so the comparison was run on
a throwaway crate using byte-identical config text — that's what
determines the flags. \(Gotcha for anyone reproducing: Cargo quotes it as
`-C 'link-arg=/STACK:4194304'`, so a `-C link-arg=\[^ \]*` grep matches
nothing.\)

Comments in `.cargo/config.toml` now document the Cargo `cfg` behavior
so the profile-gating intent isn't re-attempted — there is no stable way
to gate rustflags on the profile.

`runtime/tokio_util.rs` gets a comment-only correction:
`thread_stack_size` sizes the blocking pool only. This is a
`current_thread` runtime, so V8 runs on the thread that calls
`block_on`, not a pool thread — the old comment's claim that 2MB
"matches the main thread size" was wrong \(Unix main is ~8MB; Windows
main is the PE reserve\).

[Deno](https://deno.com) ([/ˈdiːnoʊ/](https://ipa-reader.com/?text=%CB%88di%CB%90no%CA%8A), pronounced `dee-no`) is a JavaScript, TypeScript, and WebAssembly runtime with secure defaults and a great developer experience. ## Installation
[](https://github.com/denoland/deno#installation)
Install the Deno runtime on your system using one of the commands below. Note that there are a number of ways to install Deno - a comprehensive list of installation options can be found [here](https://docs.deno.com/runtime/manual/getting_started/installation).
Shell (Mac, Linux):

```
curl -fsSL https://deno.land/install.sh | sh
```

PowerShell (Windows):

```
irm https://deno.land/install.ps1 | iex
```

[Homebrew](https://formulae.brew.sh/formula/deno) (Mac):

```
brew install deno
```

[Chocolatey](https://community.chocolatey.org/packages/deno) (Windows):

```
choco install deno
```

[WinGet](https://winstall.app/apps/DenoLand.Deno) (Windows):

```
winget install --id=DenoLand.Deno
```

[Scoop](https://scoop.sh/#/apps?q=deno&id=678d8fb557b611df996989c675b1099630a5bbee) (Windows):

```
scoop install main/deno
```

## Your first Deno program
[](https://github.com/denoland/deno#your-first-deno-program)
Deno can be used for many different applications, but is most commonly used to build web servers. Create a file called `server.ts` and include the following TypeScript code:

```
Deno.serve((_req: Request) => {
  return new Response("Hello, world!");
});
```

Run your server with the following command:

```
deno run --allow-net server.ts
```

This should start a local web server on <http://localhost:8000>.
Learn more about writing and running Deno programs [in the docs](https://docs.deno.com/runtime/manual).
