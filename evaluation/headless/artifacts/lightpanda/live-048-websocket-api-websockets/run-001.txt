# WebSocket API (WebSockets)


**Note:** This feature is available in [Web Workers](/en-US/docs/Web/HTML "/en-US/docs/Web/HTML").

The **WebSocket API** makes it possible to open a two-way interactive communication
session between the user's browser and a server. With this API, you can send messages
to a server and receive responses without having to poll the server for a reply.

The WebSocket API provides two alternative mechanisms for creating and using web
socket connections: the [`WebSocket`](/en-US/docs/Web/HTML/Reference/Elements "See all HTML references") interface and the [`WebSocketStream`](/en-US/docs/Web/HTML/Reference/Global_attributes "See all HTML references") interface.

- The `WebSocket` interface is stable and has good browser and server support. However it doesn't support [backpressure](/en-US/docs/Web/HTML/Reference/Attributes "See all HTML references"). As a result, when messages arrive faster than the application can process them it will either fill up the device's memory by buffering those messages, become unresponsive due to 100% CPU usage, or both.
- The `WebSocketStream` interface is a [`Promise`](/en-US/docs/Web/HTML/Reference "See all HTML references")-based alternative to `WebSocket`. It uses the [Streams API](/en-US/docs/Web/HTML/Guides/Responsive_images "See all HTML references") to handle receiving and sending messages, meaning that socket connections can take advantage of stream backpressure automatically, regulating the speed of reading or writing to avoid bottlenecks in the application. However, `WebSocketStream` is non-standard and currently only supported in one rendering engine.

Additionally, the [WebTransport API](/en-US/docs/Web/HTML/Guides/Responsive_images "See all HTML guides") is expected to replace the WebSocket API for many applications. WebTransport is a versatile, low-level API that provides backpressure and many other features not supported by either `WebSocket`
or `WebSocketStream`, such as unidirectional streams, out-of-order delivery, and unreliable data
transmission via datagrams. WebTransport is more complex to use than WebSockets and
its cross-browser support is not as wide, but it enables the implementation of sophisticated
solutions. If standard WebSocket connections are a good fit for your use case and
you need wide browser compatibility, you should employ the WebSockets API to get
up and running quickly. However, if your application requires a non-standard custom
solution, then you should use the WebTransport API.


**Note:**If a page has an open WebSocket connection, the browser may not add it to
the [bfcache](/en-US/docs/Web/SVG "/en-US/docs/Web/CSS"). It's therefore good practice to close the connection when the user has finished with the page. See [working with the bfcache](/en-US/docs/Web/SVG "/en-US/docs/Web/CSS").

## [Interfaces](/en-US/docs/Web/CSS/Reference/Properties "See all CSS references")
[`WebSocket`](/en-US/docs/Web/CSS/Reference/Properties "See all CSS references")
The primary interface for connecting to a WebSocket server and then sending and receiving
data on the connection.
[`WebSocketStream`](/en-US/docs/Web/CSS/Reference/Selectors "See all CSS references")
Promise-based interface for connecting to a WebSocket server; uses [streams](/en-US/docs/Web/CSS/Reference/Values "See all CSS references") to send and receive data on the connection.
[`CloseEvent`](/en-US/docs/Web/CSS/Reference/Values "See all CSS references")
The event sent by the WebSocket object when the connection closes.
[`MessageEvent`](/en-US/docs/Web/CSS/Reference "See all CSS references")
The event sent by the WebSocket object when a message is received from the server.

## [Related HTTP headers](/en-US/docs/Web/CSS/Guides/Box_model/Introduction "See all CSS guides")

The HTTP headers are used in the [WebSocket handshake](/en-US/docs/Web/CSS/Guides/Box_model/Introduction "See all CSS guides"):
[`Sec-WebSocket-Key`](/en-US/docs/Web/CSS/Guides/Animations/Using "See all CSS guides")
An HTTP request header that contains a [nonce](/en-US/docs/Web/CSS/Guides/Flexible_box_layout/Basic_concepts "See all CSS guides") from the client.This is used in the [WebSocket opening handshake](/en-US/docs/Web/CSS/Guides/Flexible_box_layout/Basic_concepts "See all CSS guides") to verify that the client explicitly intends to open a WebSocket.It is added automatically by the browser.
[`Sec-WebSocket-Accept`](/en-US/docs/Web/CSS/Guides/Colors/Applying_color "See all CSS guides")
An HTTP [response header](/en-US/docs/Web/CSS/Guides/Colors/Applying_color "See all CSS guides") used in the
*WebSocket opening handshake* to indicate that the server is willing to upgrade
to a WebSocket connection.The value in the directive is calculated from the value
of `Sec-WebSocket-Key` in the corresponding request.
[`Sec-WebSocket-Version`](/en-US/docs/Web/CSS/How_to/Layout_cookbook/Column_layouts "/en-US/docs/Web/JavaScript")
An HTTP header that in requests indicates the version of the WebSocket protocol understood
by the client.In responses, it is sent only if the requested protocol version is
not supported by the server, and lists the versions that the server supports.
[`Sec-WebSocket-Protocol`](/en-US/docs/Web/CSS/How_to/Layout_cookbook/Center_an_element "/en-US/docs/Web/JavaScript")
An HTTP header that in requests indicates the sub-protocols supported by the client
in preferred order.In responses, it indicates the sub-protocol selected by the server
from the client's preferences.
[`Sec-WebSocket-Extensions`](/en-US/docs/Web/CSS/How_to/Layout_cookbook/Card "/en-US/docs/Web/JavaScript")
An HTTP header that in requests indicates the WebSocket extensions supported by the
client in preferred order.In responses, it indicates the extension selected by the
server from the client's preferences.

## [Tools](/en-US/docs/Web/JavaScript/Reference/Global_Objects "See all JavaScript references")

- [AsyncAPI](/en-US/docs/Web/JavaScript/Reference/Global_Objects "See all JavaScript references"): A specification for describing event-driven architectures based on protocols like WebSocket. You can use it to describe WebSocket-based APIs just as you would describe REST APIs with the OpenAPI specification. Learn [why you should consider using AsyncAPI with WebSocket](/en-US/docs/Web/JavaScript/Reference/Operators "See all JavaScript references") and [how to do so](/en-US/docs/Web/JavaScript/Reference/Operators "See all JavaScript references").
- [µWebSockets](/en-US/docs/Web/JavaScript/Reference/Statements "See all JavaScript references"): Highly scalable WebSocket server and client implementation for [C++11](/en-US/docs/Web/JavaScript/Reference/Functions "See all JavaScript references") and [Node.js](/en-US/docs/Web/JavaScript/Reference/Functions "See all JavaScript references").
- [Socket.IO](/en-US/docs/Web/JavaScript/Reference "See all JavaScript references"): A long polling/WebSocket based third party transfer protocol for [Node.js](/en-US/docs/Web/JavaScript/Guide/Control_flow_and_error_handling "See all JavaScript references").
- [SocketCluster](/en-US/docs/Web/JavaScript/Guide/Control_flow_and_error_handling "See all JavaScript guides"): A pub/sub WebSocket framework for [Node.js](/en-US/docs/Web/JavaScript/Guide/Control_flow_and_error_handling "See all JavaScript guides") with a focus on scalability.
- [WebSocket-Node](/en-US/docs/Web/JavaScript/Guide/Control_flow_and_error_handling "See all JavaScript guides"): A WebSocket server API implementation for [Node.js](/en-US/docs/Web/JavaScript/Guide/Loops_and_iteration "See all JavaScript guides").
- [Total.js](/en-US/docs/Web/JavaScript/Guide/Loops_and_iteration "See all JavaScript guides"): Web application framework for [Node.js](/en-US/docs/Web/JavaScript/Guide/Working_with_objects "See all JavaScript guides") (Example: [WebSocket chat](/en-US/docs/Web/JavaScript/Guide/Working_with_objects "See all JavaScript guides"))
- [SignalR](/en-US/docs/Web/JavaScript/Guide/Using_classes "See all JavaScript guides"): SignalR will use WebSockets under the covers when it's available, and gracefully fallback to other techniques and technologies when it isn't, while your application code stays the same.
- [Caddy](/en-US/docs/Web/JavaScript/Guide "See all JavaScript guides"): A web server capable of proxying arbitrary commands (stdin/stdout) as a websocket.
- [ws](/en-US/docs/Web/API "/en-US/docs/Web/API"): a popular WebSocket client & server library for [Node.js](/en-US/docs/Web/API "/en-US/docs/Web/API").
- [cowboy](/en-US/docs/Web/API "/en-US/docs/Web/API"): Cowboy is a small, fast and modern HTTP server for Erlang/OTP with WebSocket support.
- [ZeroMQ](/en-US/docs/Web/API "/en-US/docs/Web/API"): ZeroMQ is embeddable networking library that carries messages across in-process, IPC, TCP, UDP, TIPC, multicast and WebSocket.
- [WebSocket King](/en-US/docs/Web/API "/en-US/docs/Web/API"): A client tool to help develop, test and work with WebSocket servers.
- [PHP WebSocket Server](/en-US/docs/Web/API/File_System_API "See all Web API guides"): Server written in PHP to handle connections via websockets `wss://` or `ws://` and normal sockets over `ssl://`, `tcp://`
- [Django Channels](/en-US/docs/Web/API/Fetch_API "See all Web API guides"): Django library that adds support for WebSockets (and other protocols that require long running asynchronous connections).
- [(Phoenix) Channels](/en-US/docs/Web/API/Geolocation_API "See all Web API guides"): Scalable real-time communication using WebSocket in Elixir Phoenix framework.
- [Phoenix LiveView](/en-US/docs/Web/API/HTML_DOM_API "See all Web API guides"): Real-time interactive web experiences through WebSocket in Elixir Phoenix framework.
- [Flask-SocketIO](/en-US/docs/Web/API/Push_API "See all Web API guides"): gives Flask applications access to low latency bi-directional communications between the clients and the server.
- [Gorilla WebSocket](/en-US/docs/Web/API/Service_Worker_API "See all Web API guides"): Gorilla WebSocket is a [Go](/en-US/docs/Web/API "See all Web API guides") implementation of the WebSocket protocol.
