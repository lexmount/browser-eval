**Version control** (also known as **revision control**, **source control**, and
**source code management**) is the [software engineering](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles") practice of controlling, organizing, and tracking different versions in history of [computer files](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles") – primarily [source code](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles") [text files](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles"), but generally any type of file.

Version control is a component of [software configuration management](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022
"ResourceLoaderDynamicStyles").[[1]](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles")

A **version control system** is a [software tool](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles") that automates version control. Alternatively, version control is embedded as a feature of some systems such as [word processors](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles"), [spreadsheets](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles"), collaborative [web docs](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022
"ResourceLoaderDynamicStyles"),[[2]](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles")
and [content management systems](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles"), such as [Wikipedia's page history](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles").

Version control includes options to view old versions and to [revert](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles") a file to a previous version.


## Overview
[[edit](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022
"ResourceLoaderDynamicStyles")]
As teams develop software, it is common to [deploy](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles") multiple versions of the same software, and for different developers to work on one or more different versions simultaneously.  [Bugs](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles") or features of the software are often only present in certain versions (because of the fixing of some problems and the introduction of others as the program develops). Therefore, for the purposes of locating and fixing bugs, it is vitally important to be able to retrieve and run different versions of the software to determine in which version(s) the problem occurs. It may also be necessary to develop two versions of the software concurrently: for instance, where one version has bugs fixed, but no new features ([branch](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles")), while the other version is where new features are worked on ([trunk](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles")).

At the simplest level, developers could simply retain multiple copies of the different
versions of the program, and label them appropriately. This simple approach has been
used in many large software projects. While this method can work, it is inefficient
as many near-identical copies of the program have to be maintained. This requires
a lot of self-discipline on the part of developers and often leads to mistakes. Since
the code base is the same, it also requires granting read-write-execute permission
to a set of developers, and this adds the pressure of someone managing permissions
so that the code base is not compromised, which adds more complexity. Consequently,
systems to automate some or all of the revision control process have been developed.
This [abstracts](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles") most operational steps (hides them from ordinary users).

Moreover, in software development, legal and business practice, and other environments,
it has become increasingly common for a single document or snippet of code to be
edited by a team, the members of which may be geographically dispersed and may pursue
different and even contrary interests.  Sophisticated revision control that tracks
and accounts for ownership of changes to documents and code may be extremely helpful
or even indispensable in such situations.

Revision control may also track changes to [configuration files](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles"), such as those typically stored in `/etc`
or `/usr/local/etc` on [Unix](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles") systems. This gives system administrators another way to easily track changes made and a way to roll back to earlier versions should the need arise.

Many version control systems identify the version of a file as a number or letter,
called the *version number*, *version*, *revision number*, *revision*, or *revision
level*. For example, the first version of a file might be version *1*. When the file
is changed the next version is *2*. Each version is associated with a [timestamp](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles") and the person making the change. Revisions can be compared, restored, and, with some types of files,
merged.[[3]](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles")


## History
[[edit](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022
"ResourceLoaderDynamicStyles")]

See also: [Comparison of version control software § History and adoption](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles")
IBM's OS/360 [IEBUPDTE](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles") software update tool dates back to 1962, arguably a precursor to version control system tools. Two source management and version control packages that were heavily used by IBM 360/370 installations were [The Librarian](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles") and [Panvalet](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022
"ResourceLoaderDynamicStyles").[[4]](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022
"ResourceLoaderDynamicStyles")[[5]](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles")

A full system designed for source code control was started in 1972: the [Source Code Control System](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles") (SCCS), again for the OS/360. SCCS's user manual, especially the introduction, which was published on December 4, 1975, implied that it was the first deliberate revision control
system.[[6]](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles")
The [Revision Control System](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles") (RCS) followed in
1982[[7]](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles")
and, later, [Concurrent Versions System](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles") (CVS) added network and concurrent development features to RCS. After CVS, a dominant successor was [Subversion](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022
"ResourceLoaderDynamicStyles"),[[8]](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles")
followed by the rise of [distributed version control](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles") tools such as [Git](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022
"ResourceLoaderDynamicStyles").[[9]](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles")


## Structure
[[edit](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022
"ResourceLoaderDynamicStyles")]
Revision control manages changes to a set of data over time. These changes can be
structured in various ways.

Often the data is thought of as a collection of many individual items, such as files
or documents, and changes to individual files are tracked. This is in line with the
notion of keeping files separate but causes problems when identity changes, which
happens when files are renamed, split or merged.  Accordingly, some systems such
as [Git](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles"), consider changes to the data as a whole instead, which is less intuitive for simple changes but simplifies more complex changes.

When data that is under revision control is modified, after being retrieved by *checking
out,* this is not in general immediately reflected in the revision control system
(in the *[repository](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022
"ResourceLoaderDynamicStyles")*), but must instead be *checked in* or *committed.*
A copy outside of revision control is known as a "working copy". As a simple example,
when editing a computer file, the data stored in memory by the editing program is
the working copy, which is committed by saving the file. Concretely, one may print
out a document, edit it by hand, and only later manually input the changes into a
computer and save it. For source code control, the working copy is instead a copy
of all files in a particular revision, generally stored locally on the developer's
computer;[[note 1]](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles")
in this case saving the file only changes the working copy, and checking into the
repository is a separate step.

If multiple people are working on a single data set or document, they are implicitly
creating branches of the data (in their working copies), and thus issues of merging
arise, as discussed below. For simple collaborative document editing, this can be
prevented by using [file locking](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles") or simply avoiding working on the same document that someone else is working on.

Revision control systems are often centralized, with a single authoritative data
store, the *repository,* and check-outs and check-ins done with reference to this
central repository. Alternatively, in [distributed revision control](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles"), no single repository is authoritative, and data can be checked out and checked into any repository. When checking into a different repository, this is interpreted as a merge or patch.


### Graph structure
[[edit](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022
"ResourceLoaderDynamicStyles")][![application/x-wiki](//en.wikipedia.org/wiki/Special:CentralAutoLogin/start?useformat=desktop&type=script&usesul3=1 "ResourceLoaderDynamicStyles")](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles")
Example history graph of a revision-controlled project, with the trunk in green and
the branches in yellow; the graph is not a tree, however, due to presence of merges
(the red arrows).
In terms of [graph theory](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles"), revisions are generally thought of as a line of development (the
*trunk*) with branches off of this, forming a directed tree, visualized as one or
more parallel lines of development (the "mainlines" of the branches) branching off
a trunk. In reality the structure is more complicated, forming a [directed acyclic graph](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles"), but for many purposes "tree with merges" is an adequate approximation.

Revisions occur in sequence over time, and thus can be arranged in order, either
by revision number or timestamp.[[note 2]](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles")
Revisions are based on past revisions, though it is possible to largely or completely
replace an earlier revision, such as "delete all existing text, insert new text".
In the simplest case, with no branching or undoing, each revision is based on its
immediate predecessor alone, and they form a simple line, with a single latest version,
the "HEAD" revision or *tip*. In [graph theory](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles") terms, drawing each revision as a point and each "derived revision" relationship as an arrow (conventionally pointing from older to newer, in the same direction as time), this is a [linear graph](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles"). If there is branching, so multiple future revisions are based on a past revision, or undoing, so a revision can depend on a revision older than its immediate predecessor, then the resulting graph is instead a [directed tree](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles") (each node can have more than one child), and has multiple tips, corresponding to the revisions without children ("latest revision on each
branch").[[note 3]](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles")
In principle the resulting tree need not have a preferred tip ("main" latest revision)
– just various different revisions – but in practice one tip is generally identified
as HEAD. When a new revision is based on HEAD, it is either identified as the new
HEAD, or considered a new branch.[[note 4]](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles")
The list of revisions from the start to HEAD (in graph theory terms, the unique path
in the tree, which forms a linear graph as before) is the *trunk* or *mainline.*[[note
5]](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles")
Conversely, when a revision can be based on more than one previous revision (when
a node can have more than one *parent*), the resulting process is called a *[merge](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles"),*
and is one of the most complex aspects of revision control. This most often occurs
when changes occur in multiple branches (most often two, but more are possible),
which are then merged into a single branch incorporating both changes. If these changes
overlap, it may be difficult or impossible to merge, and require manual intervention
or rewriting.

In the presence of merges, the resulting graph is no longer a tree, as nodes can
have multiple parents, but is instead a rooted [directed acyclic graph](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles") (DAG). The graph is acyclic since parents are always backwards in time, and rooted because there is an oldest version. Assuming there is a trunk, merges from branches can be considered as "external" to the tree – the changes in the branch are packaged up as a
*patch,* which is applied to HEAD (of the trunk), creating a new revision without
any explicit reference to the branch, and preserving the tree structure. Thus, while
the actual relations between versions form a DAG, this can be considered a tree plus
merges, and the trunk itself is a line.

In distributed revision control, in the presence of multiple repositories these may
be based on a single original version (a root of the tree), but there need not be
an original root - instead there can be a separate root (oldest revision) for each
repository. This can happen, for example, if two people start working on a project
separately. Similarly, in the presence of multiple data sets (multiple projects)
that exchange data or merge, there is no single root, though for simplicity one may
think of one project as primary and the other as secondary, merged into the first
with or without its own revision history.


## Specialized strategies
[[edit](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022
"ResourceLoaderDynamicStyles")]
Engineering revision control developed from formalized processes based on tracking
revisions of early [blueprints](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles") or [bluelines](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles")*["MIL-STD-100G: Department of Defense Standard Practice for Engineering Drawings"](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles")

## Source-management models
[[edit](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control -
Wikipedia")]
Traditional revision control systems use a centralized model where all the revision
control functions take place on a shared [server](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control - Wikipedia"). If two developers try to change the same file at the same time, without some method of managing access the developers may end up overwriting each other's work. Centralized revision control systems solve this problem in one of two different "source management models": file locking and version merging.


### Atomic operations
[[edit](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control -
Wikipedia")]

Main article: [Atomic commit](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control - Wikipedia")
An operation is *atomic* if the system is left in a consistent state even if the
operation is interrupted. The *commit* operation is usually the most critical in
this sense. Commits tell the revision control system to make a group of changes final,
and available to all users. Not all revision control systems have atomic commits;
Concurrent Versions System lacks this feature.[[14]](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control - Wikipedia")


### File locking
[[edit](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control -
Wikipedia")]
The simplest method of preventing "[concurrent access](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control - Wikipedia")" problems involves [locking files](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control - Wikipedia") so that only one developer at a time has write access to the central "[repository](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control - Wikipedia")" copies of those files. Once one developer "checks out" a file, others can read that file, but no one else may change that file until that developer "checks in" the updated version (or cancels the checkout).

File locking has both merits and drawbacks.  It can provide some protection against
difficult [merge conflicts](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control - Wikipedia") when a user is making radical changes to many sections of a large file (or group of files). If the files are left exclusively locked for too long, other developers may be tempted to bypass the revision control software and change the files locally, forcing a difficult manual merge when the other changes are finally checked in. In a large organization, files can be left "checked out" and locked and forgotten about as developers move between projects - these tools may or may not make it easy to see who has a file checked out.


### Version merging
[[edit](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control -
Wikipedia")]

Main article: [Merge (version control)](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control - Wikipedia")
Most version control systems allow multiple developers to edit the same file at the
same time. The first developer to "check in" changes to the central repository always
succeeds. The system may provide facilities to [merge](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control - Wikipedia") further changes into the central repository, and preserve the changes from the first developer when other developers check in.

Merging two files can be a very delicate operation, and usually possible only if
the [data structure](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control - Wikipedia") is simple, as in [text files](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control - Wikipedia"). The result of a merge of two [image files](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control - Wikipedia") might not result in an image file at all. The second developer checking in files will need to take care with the merge, to make sure that the changes are compatible and that the merge operation does not introduce its own [logic](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control - Wikipedia") errors within the files. These problems limit the availability of automatic or semi-automatic merge operations mainly to simple text-based documents, unless a specific merge [plugin](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control - Wikipedia") is available for the file types.

The concept of a *reserved edit* can provide an optional means to explicitly lock
a file for exclusive write access, even when a merging capability exists.


### Baselines, labels and tags
[[edit](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control -
Wikipedia")]
Most revision control tools will use only one of these similar terms (baseline, label,
tag) to refer to the action of identifying a snapshot ("label the project") or the
record of the snapshot ("try it with baseline *X*").  Typically only one of the terms
*baseline*, *label*, or *tag* is used in documentation or discussion[[15]](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control -
Wikipedia") ; they can be considered synonyms.

In most projects, some snapshots are more significant than others, such as those
used to indicate published releases, branches, or milestones.

When both the term *baseline* and either of *label* or *tag* are used together in
the same context, *label* and *tag* usually refer to the mechanism within the tool
of identifying or making the record of the snapshot, and *baseline* indicates the
increased significance of any given label or tag.

Most formal discussion of [configuration management](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control - Wikipedia") uses the term
[*baseline*](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control - Wikipedia").


## Distributed revision control
[[edit](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control -
Wikipedia")]

Main article: [Distributed version control](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control - Wikipedia")
Distributed revision control systems (DRCS) take a peer-to-peer approach, as opposed
to the [client–server](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control - Wikipedia") approach of centralized systems. Rather than a single, central repository on which clients synchronize, each peer's working copy of the codebase is a [bona-fide](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control - Wikipedia")
repository.[[16]](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control -
Wikipedia")Distributed revision control conducts synchronization by exchanging [patches](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control - Wikipedia") (change-sets) from peer to peer. This results in some important differences from a centralized system:

- No canonical, reference copy of the codebase exists by default; only working copies.
- Common operations (such as commits, viewing history, and reverting changes) are fast, because there is no need to communicate with a central server.[[1]](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control - Wikipedia"): 7 

Rather, communication is only necessary when pushing or pulling changes to or from
other peers.

- Each working copy effectively functions as a remote backup of the codebase and of its change-history, providing inherent protection against data loss.[[1]](/w/load.php?lang=en&modules=ext.cite.parsoid.styles%7Cext.cite.styles%7Cext.uls.interlanguage%7Cext.visualEditor.desktopArticleTarget.noscript%7Cext.wikimediamessages.styles%7Cjquery.makeCollapsible.styles%7Cmediawiki.skinning.content.parsoid%7Cskins.vector.icons%2Cstyles%7Cskins.vector.search.codex.styles%7Cwikibase.client.init&only=styles&skin=vector-2022 "client-js vector-feature-language-in-header-enabled vector-feature-language-in-main-menu-disabled vector-feature-language-in-main-page-header-disabled vector-feature-page-tools-pinned-disabled vector-feature-toc-pinned-clientpref-1 vector-feature-main-menu-pinned-disabled vector-feature-limited-width-clientpref-1 vector-feature-limited-width-content-enabled vector-feature-custom-font-size-clientpref-1 vector-feature-appearance-pinned-clientpref-1 skin-theme-clientpref-day vector-sticky-header-enabled vector-toc-available skin-thumbsize-clientpref-standard"): 4 


## Best practices
[[edit](/w/load.php?lang=en&modules=ext.cite.parsoid.styles%7Cext.cite.styles%7Cext.uls.interlanguage%7Cext.visualEditor.desktopArticleTarget.noscript%7Cext.wikimediamessages.styles%7Cjquery.makeCollapsible.styles%7Cmediawiki.skinning.content.parsoid%7Cskins.vector.icons%2Cstyles%7Cskins.vector.search.codex.styles%7Cwikibase.client.init&only=styles&skin=vector-2022
"ext.globalCssJs.user.styles")]
Following best practices is necessary to obtain the full benefits of version control.
Best practice may vary by version control tool and the field to which version control
is applied.  The generally accepted best practices in [software development](/w/load.php?lang=en&modules=ext.cite.parsoid.styles%7Cext.cite.styles%7Cext.uls.interlanguage%7Cext.visualEditor.desktopArticleTarget.noscript%7Cext.wikimediamessages.styles%7Cjquery.makeCollapsible.styles%7Cmediawiki.skinning.content.parsoid%7Cskins.vector.icons%2Cstyles%7Cskins.vector.search.codex.styles%7Cwikibase.client.init&only=styles&skin=vector-2022 "ext.globalCssJs.user.styles") include: making small/incremental changes; making [commits](/w/load.php?lang=en&modules=ext.cite.parsoid.styles%7Cext.cite.styles%7Cext.uls.interlanguage%7Cext.visualEditor.desktopArticleTarget.noscript%7Cext.wikimediamessages.styles%7Cjquery.makeCollapsible.styles%7Cmediawiki.skinning.content.parsoid%7Cskins.vector.icons%2Cstyles%7Cskins.vector.search.codex.styles%7Cwikibase.client.init&only=styles&skin=vector-2022 "ext.globalCssJs.user.styles") which involve only one task or fix -- a corollary to this is to commit only code which works and does not knowingly break existing functionality; using branching to complete functionality before release; writing clear and descriptive commit messages, making what, why, and how clear in either the commit description or the code; and using a consistent branching
strategy.[[17]](/w/load.php?lang=en&modules=ext.cite.parsoid.styles%7Cext.cite.styles%7Cext.uls.interlanguage%7Cext.visualEditor.desktopArticleTarget.noscript%7Cext.wikimediamessages.styles%7Cjquery.makeCollapsible.styles%7Cmediawiki.skinning.content.parsoid%7Cskins.vector.icons%2Cstyles%7Cskins.vector.search.codex.styles%7Cwikibase.client.init&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles")

## Costs and benefits
[[edit](/w/load.php?lang=en&modules=ext.cite.parsoid.styles%7Cext.cite.styles%7Cext.uls.interlanguage%7Cext.visualEditor.desktopArticleTarget.noscript%7Cext.wikimediamessages.styles%7Cjquery.makeCollapsible.styles%7Cmediawiki.skinning.content.parsoid%7Cskins.vector.icons%2Cstyles%7Cskins.vector.search.codex.styles%7Cwikibase.client.init&only=styles&skin=vector-2022
"ResourceLoaderDynamicStyles")]
Costs and benefits will vary dependent upon the version control tool chosen and the
field in which it is applied.  This section speaks to the field of software development,
where version control is widely applied.


### Costs
[[edit](/w/load.php?lang=en&modules=ext.cite.parsoid.styles%7Cext.cite.styles%7Cext.uls.interlanguage%7Cext.visualEditor.desktopArticleTarget.noscript%7Cext.wikimediamessages.styles%7Cjquery.makeCollapsible.styles%7Cmediawiki.skinning.content.parsoid%7Cskins.vector.icons%2Cstyles%7Cskins.vector.search.codex.styles%7Cwikibase.client.init&only=styles&skin=vector-2022
"ResourceLoaderDynamicStyles")]
In addition to the costs of licensing the version control software, using version
control requires time and effort.  The concepts underlying version control must be
understood and the technical particulars required to operate the version control
software chosen must be learned.  Version control best practices must be learned
and integrated into the organization's existing software development practices.  
Management effort may be required to maintain the discipline needed to follow best
practices in order to obtain useful benefit.


### Benefits
[[edit](/w/load.php?lang=en&modules=ext.cite.parsoid.styles%7Cext.cite.styles%7Cext.uls.interlanguage%7Cext.visualEditor.desktopArticleTarget.noscript%7Cext.wikimediamessages.styles%7Cjquery.makeCollapsible.styles%7Cmediawiki.skinning.content.parsoid%7Cskins.vector.icons%2Cstyles%7Cskins.vector.search.codex.styles%7Cwikibase.client.init&only=styles&skin=vector-2022
"ResourceLoaderDynamicStyles")]


#### Allows for reverting changes
[[edit](/w/load.php?lang=en&modules=ext.cite.parsoid.styles%7Cext.cite.styles%7Cext.uls.interlanguage%7Cext.visualEditor.desktopArticleTarget.noscript%7Cext.wikimediamessages.styles%7Cjquery.makeCollapsible.styles%7Cmediawiki.skinning.content.parsoid%7Cskins.vector.icons%2Cstyles%7Cskins.vector.search.codex.styles%7Cwikibase.client.init&only=styles&skin=vector-2022
"ResourceLoaderDynamicStyles")]
A core benefit is the ability to keep history and revert changes, allowing the developer
to easily undo changes.  This gives the developer more opportunity to experiment,
eliminating the fear of breaking existing code.[[18]](/w/load.php?lang=en&modules=ext.cite.parsoid.styles%7Cext.cite.styles%7Cext.uls.interlanguage%7Cext.visualEditor.desktopArticleTarget.noscript%7Cext.wikimediamessages.styles%7Cjquery.makeCollapsible.styles%7Cmediawiki.skinning.content.parsoid%7Cskins.vector.icons%2Cstyles%7Cskins.vector.search.codex.styles%7Cwikibase.client.init&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles")


#### Branching simplifies deployment, maintenance and development
[[edit](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022
"ResourceLoaderDynamicStyles")]
Branching assists with [deployment](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles") and [release management](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles").  Branching and merging, the production, packaging, and labeling of source code [patches](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles") and the easy application of patches to code bases, simplifies the maintenance and concurrent development of the multiple code bases associated with the various stages of the deployment process; development, testing, staging, production,
etc.[[19]](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles")


#### Damage mitigation, accountability and process and design improvement
[[edit](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022
"ResourceLoaderDynamicStyles")]
There can be damage mitigation, accountability, process and design improvement, and
other benefits associated with the record keeping provided by version control, the
tracking of who did what, when, why, and how.[[20]](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles")

When bugs arise, knowing what was done when helps with damage mitigation and recovery
by assisting in the identification of what problems exist, how long they have existed,
and determining problem scope and solutions.[[21]](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles")
Previous versions can be installed and tested to verify conclusions reached by examination
of code and commit messages.[[22]](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles")


#### Simplifies debugging
[[edit](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022
"ResourceLoaderDynamicStyles")]
Version control can greatly simplify debugging.  The application of a test case to
multiple versions can quickly identify the change which introduced a bug.[[23]](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles")
The developer need not be familiar with the entire code base and can focus instead
on the code that introduced the problem.


#### Improves collaboration and communication
[[edit](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022
"ResourceLoaderDynamicStyles")]
Version control enhances collaboration in multiple ways. Since version control can
identify conflicting changes, i.e. incompatible changes made to the same lines of
code, there is less need for coordination among developers.[[24]](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles")

The packaging of commits, branches, and all the associated commit messages and version
labels, improves communication between developers, both in the moment and over time.[[25]](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles")
Better communication, whether instant or deferred, can improve the code review process,
the testing process, and other critical aspects of the software development process.

## Common terminology
[[edit](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022
"ResourceLoaderDynamicStyles")]
Terminology can vary from system to system, but some terms in common usage include:[[27]](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles")


### Baseline
[[edit](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022
"ResourceLoaderDynamicStyles")]

Main article: [Baseline (configuration management)](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles")
An approved revision of a document or source file to which subsequent changes can
be made.  See [baselines, labels and tags](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles").


### Blame
[[edit](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022
"ResourceLoaderDynamicStyles")]
A search for the author and revision that last modified a particular line.


### Branch
[[edit](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022
"ResourceLoaderDynamicStyles")]

Main article: [Branching (revision control)](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles")

A set of files under version control may be *branched* or *forked* at a point in
time so that, from that time forward, two copies of those files may develop at different
speeds or in different ways independently of each other.


### Change
[[edit](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022
"ResourceLoaderDynamicStyles")]
A *change* (or *[diff](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022
"ResourceLoaderDynamicStyles")*, or *[delta](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022
"ResourceLoaderDynamicStyles")*) represents a specific modification to a document
under version control.  The granularity of the modification considered a change varies
between version control systems.


### Change list
[[edit](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022
"ResourceLoaderDynamicStyles")]
On many version control systems with [atomic](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles") multi-change commits, a
*change list* (or *CL*), *change set*, *update*, or *[patch](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles")*
identifies the set of *changes* made in a single commit.  This can also represent
a sequential view of the source code, allowing the examination of source as of any
particular changelist ID.


### Checkout
[[edit](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022
"ResourceLoaderDynamicStyles")]
To *check out* (or *co*) is to create a local working copy from the repository. A
user may specify a specific revision or obtain the latest. The term 'checkout' can
also be used as a noun to describe the working copy. When a file has been checked
out from a shared file server, it cannot be edited by other users. Think of it like
a hotel, when you check out,  you no longer have access to its amenities.


### Clone
[[edit](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022
"ResourceLoaderDynamicStyles")]
*Cloning* means creating a repository containing the revisions from another repository.
This is equivalent to *push*ing or *pull*ing into an empty (newly initialized) repository.
As a noun, two repositories can be said to be *clone*s if they are kept synchronized,
and contain the same revisions.


### Commit (noun)
[[edit](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022
"ResourceLoaderDynamicStyles")]

This section is an excerpt from [Changeset](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022
"ResourceLoaderDynamicStyles").[[edit](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022
"ResourceLoaderDynamicStyles")]


In version control software, a [changeset](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles") (also known as
commit[[28]](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles")
and revision[[29]](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022
"ResourceLoaderDynamicStyles")[[30]](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022
"ResourceLoaderDynamicStyles")) is a set of alterations packaged together, along
with meta-information about the alterations.  A changeset describes the exact differences
between two successive versions in the version control system's repository of changes.
Changesets are typically treated as an [atomic](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles") unit, an indivisible set, by version control systems.  This is one [synchronization model](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022
"ResourceLoaderDynamicStyles").[[31]](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022
"ResourceLoaderDynamicStyles")[[32]](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles")


### Commit (verb)
[[edit](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022
"ResourceLoaderDynamicStyles")]

Main article: [Commit (revision control)](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles")
To *[commit](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles")*
(*check in*, *ci* or, more rarely, *install*, *submit* or *record*) is to write or
merge the changes made in the working copy back to the repository. A commit contains
metadata, typically the author information and a commit message that describes the
change.


### Commit message
[[edit](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022
"ResourceLoaderDynamicStyles")]
A short note, written by the developer, stored with the commit, which describes the
commit.  Ideally, it records why the modification was made, a description of the
modification's effect or purpose, and non-obvious aspects of how the change works.


### Conflict
[[edit](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022
"ResourceLoaderDynamicStyles")]
A conflict occurs when different parties make changes to the same document, and the
system is unable to reconcile the changes.  A user must *resolve* the conflict by
combining the changes, or by selecting one change in favour of the other.


### Delta compression
[[edit](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022
"ResourceLoaderDynamicStyles")]

Main article: [Delta compression](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles")
Most revision control software uses [delta compression](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles"), which retains only the differences between successive versions of files. This allows for more efficient storage of many different versions of files.


### Dynamic stream
[[edit](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022
"ResourceLoaderDynamicStyles")]
A stream in which some or all file versions are mirrors of the parent stream's versions.


### Export
[[edit](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022
"ResourceLoaderDynamicStyles")]
*Exporting* is the act of obtaining the files from the repository. It is similar
to *checking out* except that it creates a clean directory tree without the version-control
metadata used in a working copy. This is often used prior to publishing the contents,
for example.


### Fetch
[[edit](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022
"ResourceLoaderDynamicStyles")]
See *pull*.


### Forward integration
[[edit](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022
"ResourceLoaderDynamicStyles")]
The process of merging changes made in the main *trunk* into a development (feature
or team) branch.


### Head
[[edit](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022
"ResourceLoaderDynamicStyles")]
Also sometimes called *tip*, this refers to the most recent commit, either to the
trunk or to a branch. The trunk and each branch have their own head, though HEAD
is sometimes loosely used to refer to the trunk.[[33]](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles")


### Import
[[edit](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022
"ResourceLoaderDynamicStyles")]
*Importing* is the act of copying a local directory tree (that is not currently a
working copy) into the repository for the first time.


### Initialize
[[edit](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022
"ResourceLoaderDynamicStyles")]
To create a new, empty repository.


### Interleaved deltas
[[edit](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022
"ResourceLoaderDynamicStyles")]
Some revision control software uses [Interleaved deltas](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles"), a method that allows storing the history of text based files in a more efficient way than by using [Delta compression](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles").


### Label
[[edit](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022
"ResourceLoaderDynamicStyles")]
See *tag*.


### Locking
[[edit](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022
"ResourceLoaderDynamicStyles")]

Main article: [File locking](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles")
When a developer *[locks](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles")*
a file, no one else can update that file until it is unlocked. Locking can be supported
by the version control system, or via informal communications between developers
(aka *social locking*).


### Mainline
[[edit](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022
"ResourceLoaderDynamicStyles")]
Similar to *trunk*, but there can be a mainline for each branch.


### Merge
[[edit](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022
"ResourceLoaderDynamicStyles")]

Main article: [Merge (revision control)](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles")
A *merge* or *integration* is an operation in which two sets of changes are applied
to a file or set of files. Some sample scenarios are as follows:

- A user, working on a set of files, *updates* or *syncs* their working copy with changes made, and checked into the repository, by other users.[[34]](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles")
- A user tries to *check in* files that have been updated by others since the files were *checked out*, and the *revision control software* automatically merges the files (typically, after prompting the user if it should proceed with the automatic merge, and in some cases only doing so if the merge can be clearly and reasonably resolved).
- A *branch* is created, the code in the files is independently edited, and the updated branch is later incorporated into a single, unified *trunk*.
- A set of files is *branched*, a problem that existed before the branching is fixed in one branch, and the fix is then merged into the other branch. (This type of selective merge is sometimes known as a *cherry pick* to distinguish it from the complete merge in the previous case.)


### Promote
[[edit](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022
"ResourceLoaderDynamicStyles")]
The act of copying file content from a less controlled location into a more controlled
location. For example, from a user's workspace into a repository, or from a stream
to its parent.[[35]](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles")


### Pull, push
[[edit](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022
"ResourceLoaderDynamicStyles")]
Copy revisions from one repository into another. *Pull* is initiated by the receiving
repository, while *push* is initiated by the source. *Fetch* is sometimes used as
a synonym for *pull*, or to mean a *pull* followed by an *update*.


### Pull request
[[edit](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control -
Wikipedia")]

This section is an excerpt from [Distributed version control § Pull requests](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control -
Wikipedia").[[edit](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control -
Wikipedia")]


Contributions to a source code repository that uses a distributed version control
system are commonly made by means of a pull request, also known as a merge request.[[36]](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control - Wikipedia")
The contributor requests that the project maintainer *pull* the source code change,
hence the name "pull request". The maintainer has to *merge* the pull request if
the contribution should become part of the source base.[[37]](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control - Wikipedia")

The developer creates a pull request to notify maintainers of a new change; a comment
thread is associated with each pull request. This allows for [focused discussion of code changes](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control - Wikipedia"). Submitted pull requests are visible to anyone with repository access. A pull request can be accepted or rejected by
maintainers.[[38]](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control - Wikipedia")

Once the pull request is reviewed and approved, it is merged into the repository.
Depending on the established workflow, the code may need to be tested before being
included into official release. Therefore, some projects contain a special branch
for merging untested pull requests.[[37]](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control -
Wikipedia")[[39]](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control - Wikipedia")
Other projects run an automated test suite on every pull request, using a [continuous integration](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control - Wikipedia") tool, and the reviewer checks that any new code has appropriate test coverage.


### Repository
[[edit](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control -
Wikipedia")]

This section is an excerpt from [Repository (version control)](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control -
Wikipedia").[[edit](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control -
Wikipedia")]


In version control systems, a [repository](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control - Wikipedia") is a data structure that stores either [metadata](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control - Wikipedia") or metadata and files for a set of files or [directory structure](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control -
Wikipedia").[[40]](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control - Wikipedia")
Depending on whether the version control system in use is distributed, like [Git](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control - Wikipedia") or [Mercurial](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control - Wikipedia"), or centralized, like [Subversion](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control - Wikipedia"), [CVS](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control - Wikipedia"), or [Perforce](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control - Wikipedia"), the whole set of information in the repository may be duplicated on every user's system or may be maintained on a single [server](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control -
Wikipedia").[[41]](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control - Wikipedia")
Some of the metadata that a repository contains includes, among other things, a historical
record of changes in the repository, a set of commit objects, and a set of references
to commit objects, called *heads*.


### Resolve
[[edit](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control -
Wikipedia")]
The act of user intervention to address a conflict between different changes to the
same document.


### Reverse integration
[[edit](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control -
Wikipedia")]
The process of merging different team branches into the main trunk of the versioning
system.


### Reversion
[[edit](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control -
Wikipedia")]
The abandonment of one or more recent changes in favor of a return to a previous
version of the material at hand. A revert may be done for many reasons, including:
fixing errors introduced by previous edits; restoring the material to a state that
was not contentious until new disputes can be resolved; undoing [scope creep](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control - Wikipedia"); and [regression testing](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control - Wikipedia").


### Revision and version
[[edit](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control -
Wikipedia")]
A [version](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control - Wikipedia") is any change in form. In SVK, a Revision is the state at a point in time of the entire tree in the repository.


### Share
[[edit](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control -
Wikipedia")]
The act of making one file or folder available in multiple branches at the same time.
When a shared file is changed in one branch, it is changed in other branches.


### Stream
[[edit](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control -
Wikipedia")]
A container for branched files that has a known relationship to other such containers.
Streams form a hierarchy; each stream can inherit various properties (like versions,
namespace, workflow rules, subscribers, etc.) from its parent stream.

### Update
[[edit](/w/load.php?lang=en&modules=ext.cite.parsoid.styles%7Cext.cite.styles%7Cext.uls.interlanguage%7Cext.visualEditor.desktopArticleTarget.noscript%7Cext.wikimediamessages.styles%7Cjquery.makeCollapsible.styles%7Cmediawiki.skinning.content.parsoid%7Cskins.vector.icons%2Cstyles%7Cskins.vector.search.codex.styles%7Cwikibase.client.init&only=styles&skin=vector-2022
"ResourceLoaderDynamicStyles")]
An *update* (or *sync*, but *sync* can also mean a combined *push* and *pull*) merges
changes made in the repository (by other people, for example) into the local *working
copy*.  *Update* is also the term used by some CM tools (CM+, PLS, SMS) for the change
package concept (see *changelist*). Synonymous with *checkout* in revision control
systems that require each repository to have exactly one working copy (common in
distributed systems)

"ResourceLoaderDynamicStyles")]
Releasing a lock.


### Working copy
[[edit](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022
"ResourceLoaderDynamicStyles")]
The *working copy* is the local copy of files from a repository, at a specific time
or revision. All work done to the files in a repository is initially done on a working
copy, hence the name. Conceptually, it is a *[sandbox](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022
"ResourceLoaderDynamicStyles")*.

## Notes
[[edit](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022
"ResourceLoaderDynamicStyles")]


1. [↑](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles") In this case, edit buffers are a secondary form of working copy, and not referred to as such.
2. [↑](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles") In principle two revisions can have identical timestamp, and thus cannot be ordered on a line. This is generally the case for separate repositories, though is also possible for simultaneous changes to several branches in a single repository. In these cases, the revisions can be thought of as a set of separate lines, one per repository or branch (or branch within a repository).
3. [↑](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles") The revision or repository "tree" should not be confused with the directory tree of files in a working copy.
4. [↑](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles") If a new branch is based on HEAD, then topologically HEAD is no longer a tip, since it has a child.
5. [↑](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "ResourceLoaderDynamicStyles") "Mainline" can also refer to the main path in a separate branch.
