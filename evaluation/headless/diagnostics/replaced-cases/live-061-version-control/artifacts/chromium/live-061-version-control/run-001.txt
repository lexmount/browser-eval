**Version control** (also known as **revision control**, **source control**, and
**source code management**) is the [software engineering](https://donate.wikimedia.org/?wmf_source=donate&wmf_medium=sidebar&wmf_campaign=en.wikipedia.org&uselang=en "Log in and more options") practice of controlling, organizing, and tracking different versions in history of [computer files](https://donate.wikimedia.org/?wmf_source=donate&wmf_medium=sidebar&wmf_campaign=en.wikipedia.org&uselang=en "User menu") – primarily [source code](https://donate.wikimedia.org/?wmf_source=donate&wmf_medium=sidebar&wmf_campaign=en.wikipedia.org&uselang=en "User menu") [text files](https://donate.wikimedia.org/?wmf_source=donate&wmf_medium=sidebar&wmf_campaign=en.wikipedia.org&uselang=en "User menu"), but generally any type of file.

Version control is a component of [software configuration management](https://donate.wikimedia.org/?wmf_source=donate&wmf_medium=sidebar&wmf_campaign=en.wikipedia.org&uselang=en "User
menu").[[1]](/w/index.php?title=Special:CreateAccount&returnto=Version+control " title=")

A **version control system** is a [software tool](/w/index.php?title=Special:CreateAccount&returnto=Version+control " title=") that automates version control. Alternatively, version control is embedded as a feature of some systems such as [word processors](/w/index.php?title=Special:UserLogin&returnto=Version+control " title="), [spreadsheets](/w/index.php?title=Special:UserLogin&returnto=Version+control " title="), collaborative [web docs](/w/index.php?title=Special:UserLogin&returnto=Version+control "
title="),[[2]](# "Contents") and [content management systems](# "Contents"), such as [Wikipedia's page history](# "Contents").

Version control includes options to view old versions and to [revert](# "Contents") a file to a previous version.


## Overview
[[edit](# "Contents")]
As teams develop software, it is common to [deploy](# "Contents") multiple versions of the same software, and for different developers to work on one or more different versions simultaneously.  [Bugs](# "Contents") or features of the software are often only present in certain versions (because of the fixing of some problems and the introduction of others as the program develops). Therefore, for the purposes of locating and fixing bugs, it is vitally important to be able to retrieve and run different versions of the software to determine in which version(s) the problem occurs. It may also be necessary to develop two versions of the software concurrently: for instance, where one version has bugs fixed, but no new features ([branch](#Structure "Contents")), while the other version is where new features are worked on ([trunk](#Structure "Contents")).

At the simplest level, developers could simply retain multiple copies of the different
versions of the program, and label them appropriately. This simple approach has been
used in many large software projects. While this method can work, it is inefficient
as many near-identical copies of the program have to be maintained. This requires
a lot of self-discipline on the part of developers and often leads to mistakes. Since
the code base is the same, it also requires granting read-write-execute permission
to a set of developers, and this adds the pressure of someone managing permissions
so that the code base is not compromised, which adds more complexity. Consequently,
systems to automate some or all of the revision control process have been developed.
This [abstracts](#Specialized_strategies "Contents") most operational steps (hides them from ordinary users).

Moreover, in software development, legal and business practice, and other environments,
it has become increasingly common for a single document or snippet of code to be
edited by a team, the members of which may be geographically dispersed and may pursue
different and even contrary interests.  Sophisticated revision control that tracks
and accounts for ownership of changes to documents and code may be extremely helpful
or even indispensable in such situations.

Revision control may also track changes to [configuration files](#In_game_development "Contents"), such as those typically stored in `/etc`
or `/usr/local/etc` on [Unix](#In_game_development "Contents") systems. This gives system administrators another way to easily track changes made and a way to roll back to earlier versions should the need arise.

Many version control systems identify the version of a file as a number or letter,
called the *version number*, *version*, *revision number*, *revision*, or *revision
level*. For example, the first version of a file might be version *1*. When the file
is changed the next version is *2*. Each version is associated with a [timestamp](#Atomic_operations "Contents") and the person making the change. Revisions can be compared, restored, and, with some types of files,
merged.[[3]](#File_locking "Contents")


## History
[[edit](#Version_merging "Contents")]

See also: [Comparison of version control software § History and adoption](#Distributed_revision_control "Contents")
IBM's OS/360 [IEBUPDTE](#Best_practices "Contents") software update tool dates back to 1962, arguably a precursor to version control system tools. Two source management and version control packages that were heavily used by IBM 360/370 installations were [The Librarian](#Costs_and_benefits "Contents") and [Panvalet](#Costs
"Contents").[[4]](#Costs "Contents")[[5]](#Benefits "Contents")

A full system designed for source code control was started in 1972: the [Source Code Control System](#Allows_for_reverting_changes "Contents") (SCCS), again for the OS/360. SCCS's user manual, especially the introduction, which was published on December 4, 1975, implied that it was the first deliberate revision control
system.[[6]](#Damage_mitigation,_accountability_and_process_and_design_improvement "Contents")
The [Revision Control System](#Damage_mitigation,_accountability_and_process_and_design_improvement "Contents") (RCS) followed in
1982[[7]](#Simplifies_debugging "Contents") and, later, [Concurrent Versions System](#Simplifies_debugging "Contents") (CVS) added network and concurrent development features to RCS. After CVS, a dominant successor was [Subversion](#Improves_collaboration_and_communication
"Contents"),[[8]](#Integration "Contents") followed by the rise of [distributed version control](#Integration "Contents") tools such as [Git](#Integration
"Contents").[[9]](#Integrated_development_environment "Contents")


## Structure
[[edit](#Common_terminology "Contents")]
Revision control manages changes to a set of data over time. These changes can be
structured in various ways.

Often the data is thought of as a collection of many individual items, such as files
or documents, and changes to individual files are tracked. This is in line with the
notion of keeping files separate but causes problems when identity changes, which
happens when files are renamed, split or merged.  Accordingly, some systems such
as [Git](#Baseline "Contents"), consider changes to the data as a whole instead, which is less intuitive for simple changes but simplifies more complex changes.

When data that is under revision control is modified, after being retrieved by *checking
out,* this is not in general immediately reflected in the revision control system
(in the *[repository](#Blame "Contents")*), but must instead be *checked in* or *committed.*
A copy outside of revision control is known as a "working copy". As a simple example,
when editing a computer file, the data stored in memory by the editing program is
the working copy, which is committed by saving the file. Concretely, one may print
out a document, edit it by hand, and only later manually input the changes into a
computer and save it. For source code control, the working copy is instead a copy
of all files in a particular revision, generally stored locally on the developer's
computer;[[note 1]](#Change_list "Contents") in this case saving the file only changes
the working copy, and checking into the repository is a separate step.

If multiple people are working on a single data set or document, they are implicitly
creating branches of the data (in their working copies), and thus issues of merging
arise, as discussed below. For simple collaborative document editing, this can be
prevented by using [file locking](#Clone "Contents") or simply avoiding working on the same document that someone else is working on.

Revision control systems are often centralized, with a single authoritative data
store, the *repository,* and check-outs and check-ins done with reference to this
central repository. Alternatively, in [distributed revision control](#Commit_(verb) "Contents"), no single repository is authoritative, and data can be checked out and checked into any repository. When checking into a different repository, this is interpreted as a merge or patch.


### Graph structure
[[edit](#Commit_message "Contents")][![Versionsverwaltung – German](note "Contents")](#Conflict "Contents")
Example history graph of a revision-controlled project, with the trunk in green and
the branches in yellow; the graph is not a tree, however, due to presence of merges
(the red arrows).
In terms of [graph theory](#Fetch "Contents"), revisions are generally thought of as a line of development (the
*trunk*) with branches off of this, forming a directed tree, visualized as one or
more parallel lines of development (the "mainlines" of the branches) branching off
a trunk. In reality the structure is more complicated, forming a [directed acyclic graph](#Forward_integration "Contents"), but for many purposes "tree with merges" is an adequate approximation.

Revisions occur in sequence over time, and thus can be arranged in order, either
by revision number or timestamp.[[note 2]](#Import "Contents") Revisions are based
on past revisions, though it is possible to largely or completely replace an earlier
revision, such as "delete all existing text, insert new text". In the simplest case,
with no branching or undoing, each revision is based on its immediate predecessor
alone, and they form a simple line, with a single latest version, the "HEAD" revision
or *tip*. In [graph theory](#Interleaved_deltas "Contents") terms, drawing each revision as a point and each "derived revision" relationship as an arrow (conventionally pointing from older to newer, in the same direction as time), this is a [linear graph](#Label "Contents"). If there is branching, so multiple future revisions are based on a past revision, or undoing, so a revision can depend on a revision older than its immediate predecessor, then the resulting graph is instead a [directed tree](#Label "Contents") (each node can have more than one child), and has multiple tips, corresponding to the revisions without children ("latest revision on each
branch").[[note 3]](#Mainline "Contents") In principle the resulting tree need not
have a preferred tip ("main" latest revision) – just various different revisions
– but in practice one tip is generally identified as HEAD. When a new revision
is based on HEAD, it is either identified as the new HEAD, or considered a new branch.[[note
4]](#Pull,_push "Contents") The list of revisions from the start to HEAD (in graph
theory terms, the unique path in the tree, which forms a linear graph as before)
is the *trunk* or *mainline.*[[note 5]](#Repository "Contents") Conversely, when
a revision can be based on more than one previous revision (when a node can have
more than one *parent*), the resulting process is called a *[merge](#Resolve "Contents"),*
and is one of the most complex aspects of revision control. This most often occurs
when changes occur in multiple branches (most often two, but more are possible),
which are then merged into a single branch incorporating both changes. If these changes
overlap, it may be difficult or impossible to merge, and require manual intervention
or rewriting.

In the presence of merges, the resulting graph is no longer a tree, as nodes can
have multiple parents, but is instead a rooted [directed acyclic graph](#Reversion "Contents") (DAG). The graph is acyclic since parents are always backwards in time, and rooted because there is an oldest version. Assuming there is a trunk, merges from branches can be considered as "external" to the tree – the changes in the branch are packaged up as a
*patch,* which is applied to HEAD (of the trunk), creating a new revision without
any explicit reference to the branch, and preserving the tree structure. Thus, while
the actual relations between versions form a DAG, this can be considered a tree plus
merges, and the trunk itself is a line.

In distributed revision control, in the presence of multiple repositories these may
be based on a single original version (a root of the tree), but there need not be
an original root - instead there can be a separate root (oldest revision) for each
repository. This can happen, for example, if two people start working on a project
separately. Similarly, in the presence of multiple data sets (multiple projects)
that exchange data or merge, there is no single root, though for simplicity one may
think of one project as primary and the other as secondary, merged into the first
with or without its own revision history.


## Specialized strategies
[[edit](#Trunk "Contents")]
Engineering revision control developed from formalized processes based on tracking
revisions of early [blueprints](#Update "Contents") or [bluelines](#Update "Contents")*["MIL-STD-100G: Department of Defense Standard Practice for Engineering Drawings"](https://ar.wikipedia.org/wiki/%D8%B6%D8%A8%D8%B7_%D8%A7%D9%84%D9%86%D8%B3%D8%AE "vector-unpinned-container")
(PDF). United States Department of Defense. 9 June 1997. Retrieved 2026-05-16.*.
This system of control implicitly allowed returning to an earlier state of the design,
for cases in which an engineering dead-end was reached in the development of the
design. A revision table was used to keep track of the changes made. Additionally,
the modified areas of the drawing were highlighted using revision clouds.

## Source-management models
[[edit](fr "Gestion de versions")]
Traditional revision control systems use a centralized model where all the revision
control functions take place on a shared [server](gl "Control de versións"). If two developers try to change the same file at the same time, without some method of managing access the developers may end up overwriting each other's work. Centralized revision control systems solve this problem in one of two different "source management models": file locking and version merging.


### Atomic operations
[[edit](https://hr.wikipedia.org/wiki/Upravljanje_izvornim_k%C3%B4dom "Upravljanje izvornim kôdom –
Croatian")]

Main article: [Atomic commit](hy "Վերահսկման կառավարում")
An operation is *atomic* if the system is left in a consistent state even if the
operation is interrupted. The *commit* operation is usually the most critical in
this sense. Commits tell the revision control system to make a group of changes final,
and available to all users. Not all revision control systems have atomic commits;
Concurrent Versions System lacks this feature.[[14]](https://it.wikipedia.org/wiki/Controllo_versione "Controllo versione – Italian")


### File locking
[[edit](https://ko.wikipedia.org/wiki/%EB%B2%84%EC%A0%84_%EA%B4%80%EB%A6%AC "버전 관리 –
Korean")]
The simplest method of preventing "[concurrent access](https://my.wikipedia.org/wiki/%E1%80%9B%E1%80%84%E1%80%BA%E1%80%B8%E1%80%99%E1%80%BC%E1%80%85%E1%80%BA%E1%80%91%E1%80%AD%E1%80%94%E1%80%BA%E1%80%B8%E1%80%81%E1%80%BB%E1%80%AF%E1%80%95%E1%80%BA%E1%80%99%E1%80%BE%E1%80%AF%E1%80%85%E1%80%94%E1%80%85%E1%80%BA "버전 관리")" problems involves [locking files](https://my.wikipedia.org/wiki/%E1%80%9B%E1%80%84%E1%80%BA%E1%80%B8%E1%80%99%E1%80%BC%E1%80%85%E1%80%BA%E1%80%91%E1%80%AD%E1%80%94%E1%80%BA%E1%80%B8%E1%80%81%E1%80%BB%E1%80%AF%E1%80%95%E1%80%BA%E1%80%99%E1%80%BE%E1%80%AF%E1%80%85%E1%80%94%E1%80%85%E1%80%BA "ရင်းမြစ်ထိန်းချုပ်မှုစနစ် – Burmese") so that only one developer at a time has write access to the central "[repository](my "ရင်းမြစ်ထိန်းချုပ်မှုစနစ် – Burmese")" copies of those files. Once one developer "checks out" a file, others can read that file, but no one else may change that file until that developer "checks in" the updated version (or cancels the checkout).

File locking has both merits and drawbacks.  It can provide some protection against
difficult [merge conflicts](https://ro.wikipedia.org/wiki/Controlul_versiunilor "Controlul versiunilor – Romanian") when a user is making radical changes to many sections of a large file (or group of files). If the files are left exclusively locked for too long, other developers may be tempted to bypass the revision control software and change the files locally, forcing a difficult manual merge when the other changes are finally checked in. In a large organization, files can be left "checked out" and locked and forgotten about as developers move between projects - these tools may or may not make it easy to see who has a file checked out.


### Version merging
[[edit](https://ta.wikipedia.org/wiki/%E0%AE%A4%E0%AE%BF%E0%AE%B0%E0%AF%81%E0%AE%A4%E0%AF%8D%E0%AE%A4%E0%AE%95%E0%AF%8D_%E0%AE%95%E0%AE%9F%E0%AF%8D%E0%AE%9F%E0%AF%81%E0%AE%AA%E0%AF%8D%E0%AE%AA%E0%AE%BE%E0%AE%9F%E0%AF%81
"Versionshantering")]

Main article: [Merge (version control)](th "การควบคุมการปรับปรุงแก้ไข – Thai")
Most version control systems allow multiple developers to edit the same file at the
same time. The first developer to "check in" changes to the central repository always
succeeds. The system may provide facilities to [merge](https://tr.wikipedia.org/wiki/S%C3%BCr%C3%BCm_kontrol_sistemi "Sürüm kontrol sistemi – Turkish") further changes into the central repository, and preserve the changes from the first developer when other developers check in.

Merging two files can be a very delicate operation, and usually possible only if
the [data structure](https://uz.wikipedia.org/wiki/Versiya_boshqarish_tizimi "Versiya boshqarish tizimi – Uzbek") is simple, as in [text files](https://uz.wikipedia.org/wiki/Versiya_boshqarish_tizimi "Versiya boshqarish tizimi – Uzbek"). The result of a merge of two [image files](https://vi.wikipedia.org/wiki/H%E1%BB%87_th%E1%BB%91ng_qu%E1%BA%A3n_l%C3%BD_phi%C3%AAn_b%E1%BA%A3n "Hệ thống quản lý phiên bản – Vietnamese") might not result in an image file at all. The second developer checking in files will need to take care with the merge, to make sure that the changes are compatible and that the merge operation does not introduce its own [logic](vi "Hệ thống quản lý phiên bản – Vietnamese") errors within the files. These problems limit the availability of automatic or semi-automatic merge operations mainly to simple text-based documents, unless a specific merge [plugin](https://zh-yue.wikipedia.org/wiki/%E7%89%88%E6%9C%AC%E6%8E%A7%E5%88%B6 "版本控制 – Cantonese") is available for the file types.

The concept of a *reserved edit* can provide an optional means to explicitly lock
a file for exclusive write access, even when a merging capability exists.


### Baselines, labels and tags
[[edit](https://www.wikidata.org/wiki/Special:EntityPage/Q189439#sitelinks-wikipedia "Edit interlanguage
links")]
Most revision control tools will use only one of these similar terms (baseline, label,
tag) to refer to the action of identifying a snapshot ("label the project") or the
record of the snapshot ("try it with baseline *X*").  Typically only one of the terms
*baseline*, *label*, or *tag* is used in documentation or discussion[[15]](/wiki/Talk:Version_control "Discuss improvements to the content page
[t]") ; they can be considered synonyms.

In most projects, some snapshots are more significant than others, such as those
used to indicate published releases, branches, or milestones.

When both the term *baseline* and either of *label* or *tag* are used together in
the same context, *label* and *tag* usually refer to the mechanism within the tool
of identifying or making the record of the snapshot, and *baseline* indicates the
increased significance of any given label or tag.

Most formal discussion of [configuration management](/wiki/Version_control " title=") uses the term
[*baseline*](/wiki/Version_control " title=").

## Best practices
[[edit](/w/load.php?lang=en&modules=ext.cite.parsoid.styles%7Cext.cite.styles%7Cext.uls.interlanguage%7Cext.visualEditor.desktopArticleTarget.noscript%7Cext.wikimediamessages.styles%7Cjquery.makeCollapsible.styles%7Cmediawiki.skinning.content.parsoid%7Cskins.vector.icons%2Cstyles%7Cskins.vector.search.codex.styles%7Cwikibase.client.init&only=styles&skin=vector-2022 "Version control -
Wikipedia")]
Following best practices is necessary to obtain the full benefits of version control.
Best practice may vary by version control tool and the field to which version control
is applied.  The generally accepted best practices in [software development](/w/load.php?lang=en&modules=ext.cite.parsoid.styles%7Cext.cite.styles%7Cext.uls.interlanguage%7Cext.visualEditor.desktopArticleTarget.noscript%7Cext.wikimediamessages.styles%7Cjquery.makeCollapsible.styles%7Cmediawiki.skinning.content.parsoid%7Cskins.vector.icons%2Cstyles%7Cskins.vector.search.codex.styles%7Cwikibase.client.init&only=styles&skin=vector-2022 "Version control - Wikipedia") include: making small/incremental changes; making [commits](/w/load.php?lang=en&modules=ext.cite.parsoid.styles%7Cext.cite.styles%7Cext.uls.interlanguage%7Cext.visualEditor.desktopArticleTarget.noscript%7Cext.wikimediamessages.styles%7Cjquery.makeCollapsible.styles%7Cmediawiki.skinning.content.parsoid%7Cskins.vector.icons%2Cstyles%7Cskins.vector.search.codex.styles%7Cwikibase.client.init&only=styles&skin=vector-2022 "Version control - Wikipedia") which involve only one task or fix -- a corollary to this is to commit only code which works and does not knowingly break existing functionality; using branching to complete functionality before release; writing clear and descriptive commit messages, making what, why, and how clear in either the commit description or the code; and using a consistent branching
strategy.[[17]](/w/load.php?lang=en&modules=ext.cite.parsoid.styles%7Cext.cite.styles%7Cext.uls.interlanguage%7Cext.visualEditor.desktopArticleTarget.noscript%7Cext.wikimediamessages.styles%7Cjquery.makeCollapsible.styles%7Cmediawiki.skinning.content.parsoid%7Cskins.vector.icons%2Cstyles%7Cskins.vector.search.codex.styles%7Cwikibase.client.init&only=styles&skin=vector-2022 "Version control - Wikipedia")
Other software development best practices such as [code review](/w/load.php?lang=en&modules=ext.cite.parsoid.styles%7Cext.cite.styles%7Cext.uls.interlanguage%7Cext.visualEditor.desktopArticleTarget.noscript%7Cext.wikimediamessages.styles%7Cjquery.makeCollapsible.styles%7Cmediawiki.skinning.content.parsoid%7Cskins.vector.icons%2Cstyles%7Cskins.vector.search.codex.styles%7Cwikibase.client.init&only=styles&skin=vector-2022 "Version control - Wikipedia") and automated [regression testing](/w/load.php?lang=en&modules=ext.cite.parsoid.styles%7Cext.cite.styles%7Cext.uls.interlanguage%7Cext.visualEditor.desktopArticleTarget.noscript%7Cext.wikimediamessages.styles%7Cjquery.makeCollapsible.styles%7Cmediawiki.skinning.content.parsoid%7Cskins.vector.icons%2Cstyles%7Cskins.vector.search.codex.styles%7Cwikibase.client.init&only=styles&skin=vector-2022 "Version control - Wikipedia") may assist in the following of version control best practices.


## Costs and benefits
[[edit](/w/load.php?lang=en&modules=ext.cite.parsoid.styles%7Cext.cite.styles%7Cext.uls.interlanguage%7Cext.visualEditor.desktopArticleTarget.noscript%7Cext.wikimediamessages.styles%7Cjquery.makeCollapsible.styles%7Cmediawiki.skinning.content.parsoid%7Cskins.vector.icons%2Cstyles%7Cskins.vector.search.codex.styles%7Cwikibase.client.init&only=styles&skin=vector-2022 "Version control -
Wikipedia")]
Costs and benefits will vary dependent upon the version control tool chosen and the
field in which it is applied.  This section speaks to the field of software development,
where version control is widely applied.


### Costs
[[edit](/w/load.php?lang=en&modules=site.styles&only=styles&skin=vector-2022 "Version control -
Wikipedia")]
In addition to the costs of licensing the version control software, using version
control requires time and effort.  The concepts underlying version control must be
understood and the technical particulars required to operate the version control
software chosen must be learned.  Version control best practices must be learned
and integrated into the organization's existing software development practices.  
Management effort may be required to maintain the discipline needed to follow best
practices in order to obtain useful benefit.


### Benefits
[[edit](/w/rest.php/v1/search "Wikipedia (en)")]


#### Allows for reverting changes
[[edit](//meta.wikimedia.org ">
<link rel=")]
A core benefit is the ability to keep history and revert changes, allowing the developer
to easily undo changes.  This gives the developer more opportunity to experiment,
eliminating the fear of breaking existing code.[[18]](/wiki/Main_Page "Main menu")


#### Branching simplifies deployment, maintenance and development
[[edit](/wiki/Main_Page "Visit the main page [z]")]
Branching assists with [deployment](/wiki/Main_Page "Visit the main page [z]") and [release management](/wiki/Main_Page "Visit the main page [z]").  Branching and merging, the production, packaging, and labeling of source code [patches](/wiki/Main_Page "Visit the main page [z]") and the easy application of patches to code bases, simplifies the maintenance and concurrent development of the multiple code bases associated with the various stages of the deployment process; development, testing, staging, production,
etc.[[19]](/wiki/Main_Page "Visit the main page [z]")


#### Damage mitigation, accountability and process and design improvement
[[edit](/wiki/Wikipedia:About "Learn about Wikipedia and how it works")]
There can be damage mitigation, accountability, process and design improvement, and
other benefits associated with the record keeping provided by version control, the
tracking of who did what, when, why, and how.[[20]](/wiki/Help:Introduction "Learn how to edit Wikipedia")

When bugs arise, knowing what was done when helps with damage mitigation and recovery
by assisting in the identification of what problems exist, how long they have existed,
and determining problem scope and solutions.[[21]](/wiki/Special:SpecialPages "A list of all special pages [q]")
Previous versions can be installed and tested to verify conclusions reached by examination
of code and commit messages.[[22]](/wiki/Special:Search "Search Wikipedia [f]")


#### Simplifies debugging
[[edit](/wiki/Special:Search "Search Wikipedia [f]")]
Version control can greatly simplify debugging.  The application of a test case to
multiple versions can quickly identify the change which introduced a bug.[[23]](https://donate.wikimedia.org/?wmf_source=donate&wmf_medium=sidebar&wmf_campaign=en.wikipedia.org&uselang=en "Search Wikipedia [f]")
The developer need not be familiar with the entire code base and can focus instead
on the code that introduced the problem.


#### Improves collaboration and communication
[[edit](https://donate.wikimedia.org/?wmf_source=donate&wmf_medium=sidebar&wmf_campaign=en.wikipedia.org&uselang=en "Change the appearance of the page's font size, width, and
color")]
Version control enhances collaboration in multiple ways. Since version control can
identify conflicting changes, i.e. incompatible changes made to the same lines of
code, there is less need for coordination among developers.[[24]](https://donate.wikimedia.org/?wmf_source=donate&wmf_medium=sidebar&wmf_campaign=en.wikipedia.org&uselang=en "Change the appearance of the page's font size, width, and color")

The packaging of commits, branches, and all the associated commit messages and version
labels, improves communication between developers, both in the moment and over time.[[25]](https://donate.wikimedia.org/?wmf_source=donate&wmf_medium=sidebar&wmf_campaign=en.wikipedia.org&uselang=en " title=")
Better communication, whether instant or deferred, can improve the code review process,
the testing process, and other critical aspects of the software development process.

## Common terminology
[[edit](# "Contents")]
Terminology can vary from system to system, but some terms in common usage include:[[27]](# "Contents")


### Baseline
[[edit](# "Contents")]

Main article: [Baseline (configuration management)](# "Contents")
An approved revision of a document or source file to which subsequent changes can
be made.  See [baselines, labels and tags](#History "Contents").


### Blame
[[edit](#Structure "Contents")]
A search for the author and revision that last modified a particular line.


### Branch
[[edit](#Graph_structure "Contents")]

Main article: [Branching (revision control)](#In_business_and_law "Contents")
A set of files under version control may be *branched* or *forked* at a point in
time so that, from that time forward, two copies of those files may develop at different
speeds or in different ways independently of each other.


### Change
[[edit](#In_game_development "Contents")]
A *change* (or *[diff](#Source-management_models "Contents")*, or *[delta](#Source-management_models
"Contents")*) represents a specific modification to a document under version control.
The granularity of the modification considered a change varies between version control
systems.


### Change list
[[edit](#Atomic_operations "Contents")]
On many version control systems with [atomic](#File_locking "Contents") multi-change commits, a
*change list* (or *CL*), *change set*, *update*, or *[patch](#File_locking "Contents")*
identifies the set of *changes* made in a single commit.  This can also represent
a sequential view of the source code, allowing the examination of source as of any
particular changelist ID.


### Checkout
[[edit](#Baselines,_labels_and_tags "Contents")]
To *check out* (or *co*) is to create a local working copy from the repository. A
user may specify a specific revision or obtain the latest. The term 'checkout' can
also be used as a noun to describe the working copy. When a file has been checked
out from a shared file server, it cannot be edited by other users. Think of it like
a hotel, when you check out,  you no longer have access to its amenities.


### Clone
[[edit](#Best_practices "Contents")]
*Cloning* means creating a repository containing the revisions from another repository.
This is equivalent to *push*ing or *pull*ing into an empty (newly initialized) repository.
As a noun, two repositories can be said to be *clone*s if they are kept synchronized,
and contain the same revisions.


### Commit (noun)
[[edit](#Costs "Contents")]

This section is an excerpt from [Changeset](#Damage_mitigation,_accountability_and_process_and_design_improvement
"Contents").[[edit](#Damage_mitigation,_accountability_and_process_and_design_improvement
"Contents")]


In version control software, a [changeset](#Simplifies_debugging "Contents") (also known as
commit[[28]](#Improves_collaboration_and_communication "Contents") and revision[[29]](#Integration
"Contents")[[30]](#Integrated_development_environment "Contents")) is a set of alterations
packaged together, along with meta-information about the alterations.  A changeset
describes the exact differences between two successive versions in the version control
system's repository of changes.  Changesets are typically treated as an [atomic](#Integrated_development_environment "Contents") unit, an indivisible set, by version control systems.  This is one [synchronization model](#Common_terminology
"Contents").[[31]](#Baseline "Contents")[[32]](#Baseline "Contents")


### Commit (verb)
[[edit](#Branch "Contents")]

Main article: [Commit (revision control)](#Checkout "Contents")
To *[commit](#Clone "Contents")* (*check in*, *ci* or, more rarely, *install*, *submit*
or *record*) is to write or merge the changes made in the working copy back to the
repository. A commit contains metadata, typically the author information and a commit
message that describes the change.


### Commit message
[[edit](#Commit_(verb) "Contents")]
A short note, written by the developer, stored with the commit, which describes the
commit.  Ideally, it records why the modification was made, a description of the
modification's effect or purpose, and non-obvious aspects of how the change works.


### Conflict
[[edit](#Conflict "Contents")]
A conflict occurs when different parties make changes to the same document, and the
system is unable to reconcile the changes.  A user must *resolve* the conflict by
combining the changes, or by selecting one change in favour of the other.


### Delta compression
[[edit](#Dynamic_stream "Contents")]

Main article: [Delta compression](#Forward_integration "Contents")
Most revision control software uses [delta compression](#Forward_integration "Contents"), which retains only the differences between successive versions of files. This allows for more efficient storage of many different versions of files.


### Dynamic stream
[[edit](#Import "Contents")]
A stream in which some or all file versions are mirrors of the parent stream's versions.


### Export
[[edit](#Interleaved_deltas "Contents")]
*Exporting* is the act of obtaining the files from the repository. It is similar
to *checking out* except that it creates a clean directory tree without the version-control
metadata used in a working copy. This is often used prior to publishing the contents,
for example.


### Fetch
[[edit](#Locking "Contents")]
See *pull*.


### Forward integration
[[edit](#Mainline "Contents")]
The process of merging changes made in the main *trunk* into a development (feature
or team) branch.


### Head
[[edit](#Promote "Contents")]
Also sometimes called *tip*, this refers to the most recent commit, either to the
trunk or to a branch. The trunk and each branch have their own head, though HEAD
is sometimes loosely used to refer to the trunk.[[33]](#Pull_request "Contents")


### Import
[[edit](#Repository "Contents")]
*Importing* is the act of copying a local directory tree (that is not currently a
working copy) into the repository for the first time.


### Initialize
[[edit](#Reverse_integration "Contents")]
To create a new, empty repository.


### Interleaved deltas
[[edit](#Reversion "Contents")]
Some revision control software uses [Interleaved deltas](#Revision_and_version "Contents"), a method that allows storing the history of text based files in a more efficient way than by using [Delta compression](#Share "Contents").


### Label
[[edit](#Stream "Contents")]
See *tag*.


### Locking
[[edit](#Tag "Contents")]

Main article: [File locking](#Unlocking "Contents")
When a developer *[locks](#Working_copy "Contents")* a file, no one else can update
that file until it is unlocked. Locking can be supported by the version control system,
or via informal communications between developers (aka *social locking*).


### Mainline
[[edit](#See_also "Contents")]
Similar to *trunk*, but there can be a mainline for each branch.


### Merge
[[edit](#References "Contents")]

Main article: [Merge (revision control)](https://ar.wikipedia.org/wiki/%D8%B6%D8%A8%D8%B7_%D8%A7%D9%84%D9%86%D8%B3%D8%AE "vector-dropdown vector-page-titlebar-toc vector-button-flush-left")
A *merge* or *integration* is an operation in which two sets of changes are applied
to a file or set of files. Some sample scenarios are as follows:

- A user, working on a set of files, *updates* or *syncs* their working copy with changes made, and checked into the repository, by other users.[[34]](https://ar.wikipedia.org/wiki/%D8%B6%D8%A8%D8%B7_%D8%A7%D9%84%D9%86%D8%B3%D8%AE "ضبط النسخ – Arabic")
- A user tries to *check in* files that have been updated by others since the files were *checked out*, and the *revision control software* automatically merges the files (typically, after prompting the user if it should proceed with the automatic merge, and in some cases only doing so if the merge can be clearly and reasonably resolved).
- A *branch* is created, the code in the files is independently edited, and the updated branch is later incorporated into a single, unified *trunk*.
- A set of files is *branched*, a problem that existed before the branching is fixed in one branch, and the fix is then merged into the other branch. (This type of selective merge is sometimes known as a *cherry pick* to distinguish it from the complete merge in the previous case.)


### Promote
[[edit](https://da.wikipedia.org/wiki/Versionsstyring "Versionsstyring – Danish")]
The act of copying file content from a less controlled location into a more controlled
location. For example, from a user's workspace into a repository, or from a stream
to its parent.[[35]](https://es.wikipedia.org/wiki/Control_de_versiones "Control de versiones – Spanish")


### Pull, push
[[edit](https://et.wikipedia.org/wiki/Versioonihaldus "Versioonihaldus – Estonian")]
Copy revisions from one repository into another. *Pull* is initiated by the receiving
repository, while *push* is initiated by the source. *Fetch* is sometimes used as
a synonym for *pull*, or to mean a *pull* followed by an *update*.


### Pull request
[[edit](https://fi.wikipedia.org/wiki/Versionhallinta "Versionhallinta – Finnish")]

This section is an excerpt from [Distributed version control § Pull requests](https://hr.wikipedia.org/wiki/Upravljanje_izvornim_k%C3%B4dom "Upravljanje izvornim kôdom –
Croatian").[[edit](https://hu.wikipedia.org/wiki/Verzi%C3%B3kezel%C3%A9s "Verziókezelés –
Hungarian")]


Contributions to a source code repository that uses a distributed version control
system are commonly made by means of a pull request, also known as a merge request.[[36]](https://id.wikipedia.org/wiki/Kendali_versi "Kendali versi – Indonesian")
The contributor requests that the project maintainer *pull* the source code change,
hence the name "pull request". The maintainer has to *merge* the pull request if
the contribution should become part of the source base.[[37]](it "Controllo versione")

The developer creates a pull request to notify maintainers of a new change; a comment
thread is associated with each pull request. This allows for [focused discussion of code changes](ko "버전 관리"). Submitted pull requests are visible to anyone with repository access. A pull request can be accepted or rejected by
maintainers.[[38]](my "ရင်းမြစ်ထိန်းချုပ်မှုစနစ်")

Once the pull request is reviewed and approved, it is merged into the repository.
Depending on the established workflow, the code may need to be tested before being
included into official release. Therefore, some projects contain a special branch
for merging untested pull requests.[[37]](https://sq.wikipedia.org/wiki/Kontrolli_i_versionit "Kontrolli i versionit –
Albanian")[[39]](sv "Versionshantering") Other projects run an automated test suite
on every pull request, using a [continuous integration](ta "திருத்தக் கட்டுப்பாடு – Tamil") tool, and the reviewer checks that any new code has appropriate test coverage.


### Repository

In version control systems, a [repository](yue "版本控制 – Cantonese") is a data structure that stores either [metadata](https://zh.wikipedia.org/wiki/%E7%89%88%E6%9C%AC%E6%8E%A7%E5%88%B6 "版本控制 – Chinese") or metadata and files for a set of files or [directory structure](zh "版本控制 –

### Revision and version
[[edit](/w/load.php?lang=en&modules=ext.cite.parsoid.styles%7Cext.cite.styles%7Cext.uls.interlanguage%7Cext.visualEditor.desktopArticleTarget.noscript%7Cext.wikimediamessages.styles%7Cjquery.makeCollapsible.styles%7Cmediawiki.skinning.content.parsoid%7Cskins.vector.icons%2Cstyles%7Cskins.vector.search.codex.styles%7Cwikibase.client.init&only=styles&skin=vector-2022

A [version](/w/load.php?lang=en&modules=ext.cite.parsoid.styles%7Cext.cite.styles%7Cext.uls.interlanguage%7Cext.visualEditor.desktopArticleTarget.noscript%7Cext.wikimediamessages.styles%7Cjquery.makeCollapsible.styles%7Cmediawiki.skinning.content.parsoid%7Cskins.vector.icons%2Cstyles%7Cskins.vector.search.codex.styles%7Cwikibase.client.init&only=styles&skin=vector-2022 "ext.globalCssJs.user.styles") is any change in form. ### Share
[[edit](/w/load.php?lang=en&modules=ext.cite.parsoid.styles%7Cext.cite.styles%7Cext.uls.interlanguage%7Cext.visualEditor.desktopArticleTarget.noscript%7Cext.wikimediamessages.styles%7Cjquery.makeCollapsible.styles%7Cmediawiki.skinning.content.parsoid%7Cskins.vector.icons%2Cstyles%7Cskins.vector.search.codex.styles%7Cwikibase.client.init&only=styles&skin=vector-2022

### Update
[[edit](/w/index.php?title=Version_control&action=edit ">
<link rel=")]
An *update* (or *sync*, but *sync* can also mean a combined *push* and *pull*) merges
changes made in the repository (by other people, for example) into the local *working
copy*.  *Update* is also the term used by some CM tools (CM+, PLS, SMS) for the change
package concept (see *changelist*). Synonymous with *checkout* in revision control
systems that require each repository to have exactly one working copy (common in
distributed systems)

Releasing a lock.


### Working copy
[[edit](/wiki/Main_Page "Main menu")]
The *working copy* is the local copy of files from a repository, at a specific time
or revision. All work done to the files in a repository is initially done on a working
copy, hence the name. Conceptually, it is a *[sandbox](/wiki/Main_Page "Visit the main page [z]")*.
