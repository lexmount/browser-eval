# 风控网站：规则制定与核对说明

本文件说明怎样为当前正式 100 个网址案例制定规则。它是制定方法，不是已经完成的逐例规则，也不表示这些案例已经接受产品测试。

## 1. 范围、依据和制定顺序

### 1.1 只处理正式 100 例

当前输入是本目录下的 [正式名单](qualification/cohort/qualified-cases.json)、[候补名单](qualification/cohort/qualified-reserves.json)和[输入校验清单](qualification/cohort/input-manifest.json)。当前正式 100 例覆盖 74 个独立网站；`risk-diverse-271` 已作为随机候补替换 `risk-107`，其余 9 个候补暂不制定规则。

正式案例因页面失效、证据不足、无法形成可靠规则等原因确需替换时，记录问题及原因，从符合既有[名单要求](qualification/cohort-policy.json)的剩余候补中随机抽取一例，再为替代案例制定规则。抽取前按案例 ID 排序，保存可抽名单、随机种子、抽取方法和结果；不能反复抽取直到出现偏好的案例。抽中后若发现真实问题，保留记录，再从剩余合适候补中抽取。不得根据 Moli 能否抓取决定替换。候补不足时列为待解决，不自行补充新网站。

### 1.2 本阶段做什么

后续依据本说明开展的工作是：读取独立网页证据、确定目标范围、制定规则、验证规则、冻结规则。不调用 Moli 或其他被测产品，不生成成绩，不发布报告。

已有资格结论和证据可以复用，不要求重新逐例筛选资格。发现证据矛盾或目标发生变化时，只核对受影响案例。当前有保存正文不等于已经拥有完整评分规则。

规则依据必须来自独立网页。不能先看产品返回，再挑它容易命中的文字、减少字段、降低数量或缩短参考正文。5 个旧测试集重叠案例的既有分数不能作为本批规则依据。

### 1.3 每例的顺序

1. 核对名单中的案例 ID、输入网址、语言、目标范围及证据位置。
2. 阅读保存的正文、原始网页、范围说明和必要的截图或页面结构记录。
3. 核对网址、自动跳转和语言是否足够明确；需要时补查原目标页面。
4. 先确定应该取得哪些内容、哪些不属于本任务，再选择规则类型。
5. 写出稳定文字、链接、字段、数量或正文要求，注明依据。
6. 用完整内容和有意缺失、错配的内容验证规则，检查误通过和误失败。
7. 保存规则、参考范围和校验值，标明已冻结或仍待解决。

## 2. 可以参考哪些网页内容

### 2.1 优先复用，必要时补查

优先使用交接已保存的原始网页、正文、跳转记录、页面结构和截图。只有缺失、矛盾、范围不清、明显过时或不足以支持规则时，才补查受影响案例。

保存了完整文本，不代表全文都已核实可用。逐例 `reference` 中的范围说明需要与实际文件一起阅读。导航、广告、隐藏段落、验证提示都可能混在文本中，不能直接整份作为标准答案。

稳定性根据内容性质、页面位置和已有观察判断，不是因为短时间刷新几次都相同就证明长期不变。旧观察说明当时页面状态，不保证今天网页永远不变。

逐例核对时必须查看首次自动加载页面的完整范围，不能只在正文中寻找稳定文字。顶部分类导航、侧边栏、页面操作、固定页脚和普通文字按钮，只要无需点击、跳转、输入或滚动触发加载，且有独立证据证明已经出现并预计通常稳定，就属于候选稳定文字。对这些区域应逐项判断并记录；不能因为它们位于正文之外就直接排除。当前登录状态、选中值、实验标签、个性化入口和会随界面状态变化的文字仍不冻结。

### 2.2 不局限于截图或首屏

可以使用原页面首次自动加载后正常显示的文字、列表、表格和链接。已经加载、位于屏幕下方的正常内容也可使用，不能只因为截图没拍到就排除。

截图用于帮助判断布局、遮挡、折叠和错误页状态；正文和链接还须结合保存的文本、HTML 或页面结构核对。不能只凭一张截图制定整页规则，也不能只因提取文本里有某句话就认定它正常显示。

iframe 或子文档首次自动加载的目标内容可以纳入，但要说明其归属。只取得父页面标题、嵌入标签或空框架，不等于取得子文档正文。

### 2.3 不采用的文字

- 不使用 OCR，即不把图片识别成文字来制定规则。
- 不使用图片、海报、图标或图片按钮里的文字。
- 不把图片替代说明（alt）、隐藏模板、脚本或折叠后尚未显示的内容当作正常正文。
- 不使用必须点击、展开、输入、翻页或滚动新加载后才出现的内容。
- 不把验证码、拒绝页、登录提示和加载占位符当作目标正文。
- 不把只存在于浏览器标签页标题、而页面内容中没有显示的文字直接列为可见稳定文字。

普通文字按钮与图片按钮不同：普通文字按钮可在不点击的情况下读取。实际显示、通常稳定且有明确作用的普通文字按钮可以选为稳定文字，但不能代替正文和条目完整性；选入后同样是必需项。

### 2.4 补查时不执行页面交互

只打开确定的目标网址，等待首次自动加载。不执行点击、输入、搜索、展开、翻页、登录、接受同意墙或进入详情页等 Browser Use 操作；不主动滚动，也不触发滚动加载。

已加载的屏幕下方内容通过保存的全文和页面结构核对。历史资格取证的操作按原记录说明，不因为旧材料可用而自动允许本阶段重复那些操作。

“等待完成”与“内容符合规则”分开。注明首次加载完成的现象和等待上限，不能把“页面等待结束”当作正文已经齐全。等待条件来自独立观察，不能根据产品表现反复延长。

## 3. 固定输入网址、目标和语言

本节解决制定规则前的网址与语言准备，不要求现在调用 Moli，也不把产品调用作为规则完成的前提。

### 3.1 每例需要确定的内容

- 唯一的正式输入网址：规则取证及以后 Fetch 都使用这个网址。
- 目标对象：哪篇文章、哪个商品、哪个栏目或哪条帖子。
- 目标正文语言：中文或英文，按本批既有约定执行。
- 已观察到的自动跳转过程及最终网址。
- 必要的语言地区设置，以及这些设置有没有影响最终目标。

不能只因为两个页面属于同一网站就认为相同。规则页是英文文章，实际输入却容易跳到中文首页，这种输入不能直接冻结。

### 3.2 怎样处理跳转和语言变化

先看已有跳转和语言证据。若发现语言切换或目标不明确，补查真实有效的固定入口，例如网站实际提供的英文路径、中文路径、语言参数或语言偏好设置。

可以使用网站真实支持的 `/en/`、`/zh-cn/` 或语言参数，但不能凭猜测添加 `/en`、`/cn`。调整后须实际核对：地址有效、仍是原目标、正文语言正确、没有跳到另一篇内容或首页。浏览器自动翻译不算固定源网页语言。

正常的 HTTPS 跳转、规范地址跳转可以接受，但要记录。若使用最终规范地址作为新输入，还须确认新输入对应的限制和正文证据适用，不能只改字符串后继续沿用所有旧结论。

需要修改交接网址时，保存原网址、拟用网址、原因及核对依据；改变目标或任务范围的方案列为待决定，不悄悄更换案例。无法固定语言或目标时标为待解决，不能通过同时允许中英文规则掩盖问题。

### 3.3 本阶段的交付边界

交付一个已核对的固定网址及必要设置，供后续直接使用。说明的是在已观察环境中该入口对应正确目标和语言，不承诺外部网站永远不会改变，也不声称已验证尚未发生的 Moli 调用。

## 4. 规则类型与组合原则

一个案例可以组合多种规则。选用的必需规则都要满足，不能以某项通过抵消另一项缺失。不是每个页面都必须采用全部类型。

| 规则 | 要回答的问题 |
|---|---|
| 有没有抓错页面 | 内容是否属于指定目标和语言，是否只有错误页或外壳？ |
| 稳定文字 | 预计通常存在、不容易变化的选定文字是否取得？ |
| 名称与链接（name-link） | 每条名称是否带有同一条目的真实、合规链接？ |
| 同条目必要字段 | 每条记录是否含有规定的真实字段，且没有跨条目拼接？ |
| 数量与去重 | 有效且不重复的条目是否达到独立观察数量的至少 80%？ |
| 正文匹配 | 声明范围的正文是否得到足够覆盖，而不只是开头或标题？ |

下面每类规则都必须落到具体网页证据，不能只登记一个类型名。

## 5. 有没有抓错页面

核对目标身份、语言和内容区域。文章可依据文章标题与正文主题，商品可依据具体名称、型号等独立身份信息，列表可依据栏目名称和实际列表结构。通用站名通常不能单独区分同站不同页面。

以下情况不能因命中网站名称而通过：返回首页而非指定文章、返回另一商品、语言不对、只有导航页脚、只有验证码或登录页面、只有加载框架。

不要设成“出现登录或验证码两个字就失败”。正常文章可能讨论这些词；目标正文也可能与普通登录入口同时存在。判断依据是目标内容是否确实取得并满足其他规则。

正例：文章目标、语言和正文均正确，额外带有普通登录入口，不仅因此拒绝。

反例：网址看起来正确，返回却只有站名和“正在检查浏览器”，仍应失败。

## 6. 稳定文字

### 6.1 什么才算稳定

选择依据是：有理由认为这段文字不会轻易变化，通常稳定存在于该目标页面。例如长期栏目、固定说明、章节标题、稳定正文、合适的导航、页脚和普通文字按钮。

不是“这次看到了就算稳定”，也不是要求保证永不变化。为每组说明内容性质、页面位置、已有证据和为什么预计通常存在。

变化榜单的当前成员、新闻列表的当前标题、价格、排名、库存、热度、数量计数、版权年份等，不作为必须精确匹配的稳定值。若选择版权文字，避开会变的年份等部分，保留具有实际意义的稳定片段。

固定文章标题或指定商品名称与“当前榜单成员”不同：前者用于识别固定目标，可以在证据支持下选用。

### 6.2 数量、分组与通过方式

不设统一最低组数，也不设上限。合适的文字可以多保留；不要找到三组就停止，也不要为了凑三组加入不合适内容。同一句话拆成若干重叠小段不能冒充独立识别项。

每组选择一个有完整意义的片段，记录原文、位置、作用和稳定性依据。不固定一大段混有日期、价格等易变信息的文字。

所有登记的组均为必需项，全部命中才通过这类检查。页脚或按钮一旦选入，缺少它也会失败，即使正文完整。这是本批选定的要求；制定时必须认真筛选，不能因为“稳定”就把整页外围文字全部收进来。

导航、页脚和按钮的命中不能证明正文或列表完整。它们不能替代本应存在的目标内容检查。

### 6.3 格式差异与必要文案变体

使用项目公共匹配方式处理合理的大小写、空格、换行和 Markdown 表达差异；不把格式变化当作内容缺失。不能自行删除有意义的数字、词语或符号来提高命中。

默认每组只有一种已观察原文。只有确有必要，且独立网页证据证明同一目标、同一语言存在正常文案差异时，才增加允许写法；不是每组都要配置变体。

例如，已独立观察到同一说明分别使用 “About this project” 和 “About the project”，且差异不改变目标，可在一组中列出两者，命中其中一个即可。记录各自证据和保留两种写法的原因。

不得凭空列举近义词，不得因为 Moli 返回另一种写法而增补，不得用中英文互为变体解决语言不一致。若文字经常变化，优先放弃将其作为必需稳定文字，而不是无限扩充允许答案。

## 7. 名称与链接（name-link）

### 7.1 一条有效记录包含什么

适用于文章、商品、视频、仓库等带真实链接的目标列表。名称必须非空，是网页实际提供的可见名称；链接必须由网页实际提供，并属于同一条目。

“点击这里”“查看详情”等通用文字通常不能代替具体名称。名称在卡片标题、链接在同卡片其他位置时，可以按真实归属配对；不能从另一个条目借名称或链接。

链接必须是实际链接。禁止根据商品 ID、文章 ID、名称、路径规律或经验，生成网页没有提供的地址；禁止猜测后缀、试拼链接或把无链接卡片补成有链接卡片。识别内容 ID 只用于检查已有链接和去重，不用于制造链接。

### 7.2 按实际网页制定地址格式

根据独立页面提供的真实链接，逐例确定允许的协议、完整域名、路径结构、必要参数和结尾要求。可采用严格的路径模式检查，但不能只凭“包含域名”或“包含某个 ID”就放行。

以下只是说明格式的虚构例子，不能直接作为任何真实案例规则：

- 已观察的详情链接是 `https://shop.example/product/12345`，可依据证据要求域名精确为 `shop.example`，路径是 `/product/` 加数字 ID；是否允许末尾斜杠另按真实页面确定。
- 若真实地址是 `/item?id=12345`，则检查 `/item` 路径及必要的 `id` 参数，不能强行改成 `/product/12345`。
- 视频、帖子等可能使用字母数字组合、固定长度编号或文字路径，不统一假设所有 ID 都是数字。

域名检查先解析地址，避免 `shop.example.evil.test` 或 `evil.test/?next=shop.example` 冒充允许域名。只有已核实的子域名可放行。`javascript:`、空链接和单纯页面内占位链接不作为详情链接。

路径检查覆盖完整目标结构：`/product/12345/reviews` 是否属于目标详情页必须明确，不能只因前缀匹配就算通过。域名和 ID 形态正确也不能证明该链接一定是真实目标；还必须满足网页实际提供、名称归属及目标区域要求。

### 7.3 相对地址与参数

网页实际提供 `/product/12345` 这类相对链接时，可以按该页面真实基址补全成完整地址，必要时核对页面的 base 设置。这是在解析已经存在的链接，不是依据 ID 新造链接。只给 ID 而没有真实链接的情况不能这样补全。

用于文章、商品、语言、地区等身份的参数必须保留并检查。仅当证据说明某参数只用于追踪、不改变目标时，才允许在比较或去重时忽略。不要一律删掉全部查询参数或片段；部分页面用片段决定实际内容。

保留原始地址及用于比较、去重的形式，不为方便匹配改写成另一种未经证实的地址。

### 7.4 名单变化、去重和 80% 数量要求

变化列表不固定观察时的具体名称和 URL 名单。只固定实际条目的结构、名称与链接归属、允许地址格式、去重方式及数量门槛。

**name-link 必须同时检查数量：后续 Fetch 返回的有效、不重复名称—链接记录，至少达到独立网页同范围有效记录数的 80%，向上取整。** 固定数量列表及有证据的例外按第 9 节处理。

例如原榜单初始加载 20 条有效记录，至少需要返回 16 条有效记录。返回 18 条但有 4 条重复或链接错误，只能计 14 条，应失败。不是要求“返回内容中有 80% 的记录有效”，也不是要求仍为历史观察时的那 16 个具体成员。

名称、链接、字段缺失的记录不计数。导航、帮助、分类、广告、推荐区域不能冒充所声明榜单。相同目标用不同追踪参数重复出现，只计一条。

## 8. 同一条目的必要字段

没有普通详情链接时，不强加链接规则，也不自行制造链接。依据实际卡片或表格选择必要的文字字段；存在链接并且属于目标要求时，可与 name-link 一起使用。

逐例写明每条记录需要哪些字段、什么算有效、哪些可选。例如商品名称和价格、赛事双方与状态、地震地点与震级。只要求页面真实提供且对目标有作用的字段，不要求额外详情页才出现的内容。

字段值可以变化：价格规则检查有效价格信息，不冻结当天金额；日期规则检查有效日期，不冻结某一天。数值为零不自动代表缺失。“暂无”“加载中”等是否属于真实有效状态，需要按字段含义判断，不能统一当作完整值。

同一条记录必须有规定字段，不得从不同卡片拼接。若某字段确实只适用于部分记录，先声明由页面事实决定的适用条件，不根据产品漏抓情况临时豁免。

空卡片、骨架屏、重复按钮、纯图片数量不能算有效条目。有效且不重复的记录同样按第 9 节数量要求检查。

## 9. 数量与去重

### 9.1 明确分母和分子

- 分母 N：制定规则时，独立网页在相同语言、相同目标区域及首次自动加载范围内，实际观察到的有效、不重复条目数。
- 最低数量 T：`ceil(N × 0.80)`，即向上取整。
- 后续计数 M：Fetch 返回中满足所选名称、链接、字段、区域和去重要求的有效条目数。
- 数量通过条件：`M ≥ T`，同时其他必需规则也满足。

例如 N=12 时 T=10；N=20 时 T=16。分母不能使用 Fetch 自己返回的数量，也不能使用网站声称的全站总数。滚动、点击或翻页后才出现的条目不计入 N。

### 9.2 固定数量、波动和异常情况

页面设计及独立证据明确支持固定全量时，可以要求完整固定数量，并说明理由。变化列表默认 80%；只有独立证据证明需要采用其他门槛时才逐例注明例外，不能依据产品表现降低要求。

首次加载数量明显波动时，结合已有观察确认原因：目标、语言或加载范围是否变化。必要时补查并保存各次有效数量、最终依据和门槛，不能挑一次最低数量掩盖未加载完成。

N=0 或无法确定有效数量时，不能把零门槛当作规则完成。先确认是否错误页、加载不完整或本来没有所需目标内容，再决定待补或替换。

门槛冻结后不为每次产品返回调整。之后发现真实网页变化时，保存变更证据并修订相应范围，不无记录覆盖旧规则。

### 9.3 去重与跨区域

优先按已有真实详情链接中的内容身份去重；无链接记录使用有依据的字段组合。内容 ID 只用于识别重复，不能用于拼接网址。

去重不能随意只按标题，因为不同内容可能重名。一个目标的不同追踪链接不能重复计数。同一条记录多次出现在页头、榜单和推荐中，不能重复凑数。

多个目标列表都重要时，分别声明区域和最低数量，不能用第一个列表的多余条目补足第二个列表完全缺失。

## 10. 正文匹配

### 10.1 参考范围

用于文章、说明文档、商品介绍、短帖等文字内容。先确定原任务要求的目标范围，再制作参考；不能为了容易通过缩成标题和第一段。

文章、文档、固定说明页及其他固定文本目标都必须以完整目标正文为准。凡是首次自动加载后已经直接显示或已经加载，并经独立证据确认属于目标内容的部分，包括位于屏幕下方但不需要点击、展开或触发新加载的部分，都纳入正文参考。分区只用于把完整正文分成最多 5 个连续区域，不能只选开头、部分章节或少数段落，也不能用局部正文代表全文。属于本例目标范围的新闻、榜单、版本、价格等变化区域不适合冻结成固定正文时，也不能直接略过；应改用 name-link、同条目字段、去重和数量规则覆盖。

参考来自独立网页，排除导航、广告、推荐、页脚、登录提示及不属于目标的内容。它们即使另作稳定文字，也不能增加正文覆盖率。去除采集造成的重复，不删除真实正文以迁就产品输出。

只有部分章节经过核实时，明确已核实范围；若原任务要求更多正文，需要补足证据，不能把局部覆盖宣称为全文完整。极短且没有足够实际内容的页面，要判断是否能形成有意义的规则，不能硬凑参考。

### 10.2 分区与比例

优先按自然段、章节或完整组件划为连续区域，最多 5 区，覆盖所声明正文的前、中、后部。短文可以只分一区，不硬拆。现有自动均分仅是实现工具，不能替代对区域边界的检查。

默认每个区域至少覆盖 60%，至少 `max(1, 区域数−1)` 个区域达到 80%：

| 区域数 | 最低要求 |
|---|---|
| 1 | 该区至少 80% |
| 2 | 两区均至少 60%，其中至少一区达到 80% |
| 3 | 三区均至少 60%，其中至少两区达到 80% |
| 5 | 五区均至少 60%，其中至少四区达到 80% |

例如三区覆盖为 90%、85%、65% 可以通过这项检查；95%、95%、20% 不通过。不是全文平均超过 80% 就够，也不是全文只要一区达到 80% 就够。

比例例外必须有独立网页依据并逐例说明；不得看过产品返回后反向修改。

### 10.3 覆盖率是什么意思

使用项目公共正文评分实现，不另写一套含义不同的算法。当前 v3 会统一部分格式，保留字母和数字，将正文拆成连续 6 个字符的重叠短片段，再比较参考区域的片段有多少在返回中得到匹配。它是文字片段覆盖，不是人工判断“大意相同”，也不是简单数完整句子或字数。

共享片段的次数会在区域之间分配，不能把一份返回片段无限重复计入多个区域。仍需用缺段和重复粘贴反例验证，不把比例指标当成正文真实性或准确顺序的全面证明。

短区域不足以形成有效片段时，不填空规则让它自动通过；合并合理相邻内容，或采用适合短文本的必需文字检查，并记录选择原因。

变化首页推荐、当前新闻列表中的摘要，不冻结成长期必需正文。指定文章或帖子的稳定原文可以使用；若目标文字确实频繁变化，先判断是否应采用字段或条目规则，不拿旧正文强制匹配新内容。

## 11. 组合示例

以下是规则搭配示例，不是已经为实际案例冻结的答案。

| 页面 | 通常组合 | 需要防止的误通过 |
|---|---|---|
| 固定文章 | 目标与语言、合适稳定文字、正文分区 | 只有标题和开头，缺中后部 |
| 变化榜单 | 栏目与语言、稳定文字、name-link、去重和至少 80% 数量 | 固定旧成员；错链接或重复凑数 |
| 无链接卡片 | 页面身份、稳定文字、同条目必要字段、数量 | 空卡片；不同记录字段拼接 |
| 商品详情 | 指定商品身份、稳定说明、必要字段、适合的正文范围 | 换成另一商品；把旧价格当稳定答案 |
| 短帖子 | 帖子与作者身份、适量稳定文字、适合短文的正文检查 | 硬凑三组文字；拿回复或视频文字补原帖 |
| 带 iframe 页面 | 父页身份及实际子文档目标内容 | 只有父页标题或 iframe 标签 |

每项选中的必需规则都要满足。稳定页脚全命中不能抵消正文缺失；链接条目足够不能抵消已声明的另一正文区域缺失。组内多个必要时允许的文案写法任选其一，不等于整页任意一种规则满足即可。

## 12. 怎样验证规则没有过松或过严

后续制定逐例规则时，使用项目公共评分入口验证，不只手工看规则配置。当前说明文件的编写不运行这些测试。

完整的独立参考应通过。还要检查合理空格、换行、大小写、Markdown 表格或列表、真实相对链接补全，以及已证实无关的追踪参数差异，不会误拒正确内容。

有意构造以下反例，按案例适用类型验证：

- 缺任一必需稳定文字，包括选入的页脚或普通文字按钮。
- 只保留站名、导航和页脚，去掉目标内容。
- 返回错误目标、错误语言、纯验证页或加载空壳。
- 空名称、名称链接错配、错域名、错路径、不完整或伪造链接。
- 只给商品 ID 没有链接，不能由评分过程帮它补出网址。
- 缺字段、跨条目借字段、重复项凑数、其他区域冒充目标列表。
- name-link 或字段记录的有效数量低于门槛，包括刚好少一条的边界情况。
- 正文缺中间或结尾、反复粘贴开头、参考采集重复导致的假覆盖。

也验证正常文章提到“登录”“验证码”不被直接拒绝。恰好达到数量及覆盖门槛应按未四舍五入的实际值判定，显示时的取整不能改变结果。

链接结构合规只能证明结构符合要求，不能独自证明变化列表中每个新名称都真实。需要按所声明的证据与条目归属核对，不能把单纯路径检查包装为全面真实性验证。

发现公共评分实现不能表达已确定规则时，记录缺口；不能默默删规则或声称已验证。后续实现修复要处理共同原因，并验证正反两个方向，不只对某次产品输出打补丁。

## 13. 每例交付内容与状态

每例记录：

- 案例 ID、页面名称、正式输入网址、观察最终网址及跳转、目标语言和必要设置。
- 原任务目标、首次加载范围、完成条件、排除内容。
- 独立证据位置、观察时间、文件校验值及复用或补查原因。
- 稳定文字的原文、位置、作用、稳定性理由；只有必要时才附允许写法和对应证据。
- name-link 的真实链接来源、允许域名和路径、参数处理、条目归属与去重方式。
- 字段要求、有效值说明、独立有效数量 N、门槛 T 及例外依据。
- 正文参考、分区、匹配版本和比例要求。
- 正反例验证结果、已知限制，以及已冻结、待补证据、待决定或需替换的状态。

原始网页和观察材料继续保存在仓库外既有证据目录，不复制产品结果、凭据或内部执行日志到 Git。规则文件与精简证据引用可纳入版本管理。冻结后保留旧版本依据，发生修订时记录影响，不能无记录覆盖历史结论。
