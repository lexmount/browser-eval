# Browser Service Eval

Reproducible evaluation of browser engines and services across public task
suites, functional correctness, latency, output size, CPU, memory, and network
traffic.

The first backend compares warm local Chromium and Moli in equal, isolated
Docker cgroups. It does not require Codex, another coding agent, an LLM API key,
website accounts, or login state.

## Latest report

[Chromium 与 Moli 浏览器工具调用评测](https://artifact-hub.dev.lexmount.net/s/zzzUqvSKjTFB)

## Run the browser evaluation

Requirements: Docker Engine (cgroup v2), Python 3.11+ with `venv`, at least 4
CPU cores, 6 GiB available memory, and Internet access.

```bash
./examples/browser_use/run.sh
```

The command builds pinned browser images, installs the controller in a local
virtual environment, runs the versioned 30-task deterministic suite, and writes:

- raw reproducibility artifacts to `artifacts/browser_use/latest/` (ignored by Git)
- latest-only Markdown, HTML, and audit data to `docs/reports/` (ignored by Git)

All statistics and HTML are generated by repository scripts. To rebuild the
summary and report from an existing `attempts.jsonl` without rerunning the
browsers, use:

```bash
uv run python examples/browser_use/rebuild_report.py
```

See [examples/browser_use/README.md](examples/browser_use/README.md) for the
measurement protocol, complexity tiers, overrides, and CubeSandbox decision.

## Harness layout

- `harness/browser_use`: interactive browser-use execution, metrics, and reports
- `harness/web_fetch`: Web Fetch providers, execution, scoring, and reports

Browser Use and Web Fetch intentionally keep separate suites and metrics.
Web Fetch has no legacy top-level package or compatibility imports.

## Web Fetch 评测

独立的浏览器 Markdown 对比覆盖 Kitesurf、Lightpanda、Obscura、
Moli 1.1.1、Moli 1.1.3 与 Chromium。完整的参考冻结、调用、
测后核验、结果独立审查和发布协议见
[运行协议](harness/web_fetch/HEADLESS.md)。实测输出保留在用户目录的持久化证据中，
不提交到 Git；这组数据不与下面的历史 12 方法混排。

历史主测为 140 个任务 × 12 种方法：网页正文 100 个，文档、图片、视频、复杂热门网站各 10 个。动态内容另有 10 个任务、12 种方法的独立补测，覆盖异步接口、前端应用、内嵌数据、延迟呈现和 iframe 子文档；不与历史组混成总榜。`evaluation/dataset.json` 的 `coverage_plan` 显式规定每组参评范围，未运行不算失败。
包含 Moli 1.1.1 的完整 140 条调用；保留原有 11 种方法的测量输出与成绩，各批次执行时间见报告环境页。

`reports/` 和 `publish/` 是可重建产物及本地发布回执，不提交 Git；发布凭据不得写入仓库。

## 重新实测

把根目录 `.env.example` 复制为 `.env`，只填写需要的方法。所有 Web Fetch 入口默认只读取仓库根目录 `.env`，不读取用户目录、不执行 shell 内容；已导出的环境变量优先。只有显式 `--env-file <路径>` 才改用其他文件，文件不存在时报错。`.env` 与本地变体已被 Git 忽略，示例不含凭据。

用 `python3 -m harness.web_fetch validate --providers <方法名>` 校验凭据。原生实现还需要对应仓库和 Python/Node 依赖；路径均在 `.env.example` 中列出，开源依赖可通过 `scripts/bootstrap_oss_baselines.sh` 准备。

```bash
python3 scripts/run_benchmark.py
# 或仅实测 Moli（当前完整评测集，不调用其他供应商）
python3 scripts/run_benchmark.py --providers moli-webfetch --output ~/.browser-eval/runs/moli-webfetch
# 仅检查新增动态组配置，不创建输出、不调用接口
python3 scripts/run_benchmark.py --track dynamic --validate-only
# 扩充案例时，只运行已独立冻结的新案例 JSON；源页证据放在其旁边的 sources/
python3 scripts/run_benchmark.py --dataset ~/.browser-eval/runs/new-reference/dataset.json --track dynamic --output ~/.browser-eval/runs/new-cases
# 仅补跑指定的托管方法；其余已测记录不受影响
python3 scripts/run_benchmark.py --track dynamic --providers lexmount-global,lexmount-cn,firecrawl,tavily,exa,cloudflare-markdown --output ~/.browser-eval/runs/dynamic-hosted
```

使用具备当前全部解析依赖的 Python 环境执行。默认调用存档中的方法及新接入的 Moli（目前 12 种），可用 `--providers` 选择；云端方法可能消耗配额。所有选中方法先通过配置检查，再开始调用。不同方法并发，同一方法先完成网页组，再测其他组；正文与资源配置分开。已有输出目录会被拒绝覆盖。新结果核验后才能替换 `evaluation/`，不自动替换已发布成绩。

新增方法完成同一评测集后，可执行 `python3 scripts/add_provider_results.py ~/.browser-eval/runs/<完整运行目录> --provider <新方法>`。已有方法补测尚未执行的组时，使用 `--provider <方法> --track dynamic`；输入必须完整覆盖该组，案例与参考须与当前评测集完全一致。此入口拒绝缺失/重复任务、参考变化、输出哈希不符或执行批次不完整；原有 JSONL 行和输出字节不变，禁止覆盖已测任务。补测后同步审查 `configs/evaluation-inventory.json` 的方法覆盖，再重建报告。原始执行组、运行 ID 与时间仍各自保留，不能把不同时间的调用描述成同时测量。

### Moli WebFetch

按 [官方 skill](https://github.com/lexmount/moli/tree/main/skills/moli-webfetch) 安装本地 CLI，在 `.env` 设置 `MOLI_BINARY`（默认 `moli`，不需要账号/API Key）。普通网页正文使用 `moli fetch --dump markdown --wait-until done`；Moli 1.1.3 对直接文档和媒体地址预先选择裸 `moli fetch URL`，让 CLI 自动决定返回原始响应还是序列化页面。识别为原始 PDF 或媒体时直接取得字节，文档正文随后在同一截止预算内解析；本轮 DOCX 响应被 Moli 序列化为 HTML，没有形成可解析的原始文件，因此按保存结果失败。直接文件任务到格式、长度和 SHA-256 校验完成为止，不做无关的 Markdown 转换。适配器保留 stdout 原文、独立 stderr 和退出状态。Markdown 模式没有 HTTP 状态/最终 URL，因此这些字段留空，而不是发第二次请求拼接元数据。工具成功不等于任务通过，仍使用相同机械评分规则。

官方还提供 JSON/HTML/semantic tree、DOM eval、授权会话及需 layout 的截图/PDF 输出。这些能力与正文和原始响应路线分开说明；生成 PDF 不等于解析已有 PDF，媒体链接也不等于取得原文件。Moli 1.1.3 对非 HTML 响应使用自动原始输出（或 JSON 的 `body_base64`），不能强制 `--dump html/markdown`。本地文档解析属于正文任务的计时内后处理，不暗中借用其他 provider。

独立源页检查：`python3 scripts/audit_sources.py`，需要 requests、BeautifulSoup4 和文档解析依赖。HTTP 失败只触发进一步检查，不能据此自动删除任务。复杂热门网站的列表按字段结构评分，不耦合当前标题、排序或价格。动态正文参考采集须遵守 `harness/web_fetch/README.md` 的配对证据与有界完成条件；页面分类不是 JS 必要性的证据。

```bash
export WEBFETCH_REPORT_PUBLIC_URL=https://artifact-hub.dev.lexmount.net/api/preview/bWkRP157EtF6
python3 scripts/build_report.py
python3 scripts/package_artifact_hub.py
```
