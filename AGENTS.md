# Report maintenance

- For a new or substantially rewritten report interpretation, official blog or public-account article, read `.agents/skills/benchmark-editorial/SKILL.md` and follow its linked editorial, HTML and Humanizer passes. This requirement survives new sessions; a dashboard rebuild alone is not an editorial rewrite. Keep process notes out of the published report.

- Keep one current implementation: `harness/web_fetch/report.py`, built by `scripts/build_report.py` from persistent measured evidence (`~/.browser-eval/evidence/current/` by default, or `WEB_FETCH_EVIDENCE_DIR`) into `reports/webfetch/`. Git keeps the canonical dataset, annotations and independent source evidence under `evaluation/`, but never measured outputs, execution manifests or provider artifacts.
- Do not create report-version filenames, compatibility renderers, redirect pages, or builds that depend on older report directories. Update the current implementation directly.
- Keep task rules, measured outputs, timestamps, runtime settings and hashes as evidence. A presentation change must not alter measured outputs or silently change scores.
- The published report is a formal deliverable: tasks, reference scope, methodology, results, provider interfaces and evidence. Do not publish assistant work logs, iteration notes, assistance requests or user to-do lists.
- Treat user prompts, assistant plans, reviewer discussion, troubleshooting notes and internal checklists as source material only. Publish the current conclusion, method, evidence and limitations; do not narrate the production process outside the formal release log.
- Every public section must answer a reader question and lead with its result or scope. Omit empty tables, unexplained hashes and repeated definitions; keep technical identifiers in collapsed evidence details or downloadable records.
- Result review is a first-class report stage with its own page. State reviewer, protocol, coverage, disagreements, adjudication and unresolved count, and retain per-attempt review evidence. Do not bury review records in environment or reproduction instructions.
- The reproduction page links the repository as the canonical source for code and datasets, then gives only the current core configuration and commands. Do not publish machine-local paths or repeat every execution batch.
- Ask for any required manual action in the conversation only. Zhihu and Dianping snapshots have already been provided. Browser access restrictions alone do not invalidate a task.
- Dynamic lists use stable field requirements, not fixed current titles, positions or prices. Disclose when factual correctness is not measured.
- Task acceptance and full-text quality are distinct. Preserve task results even when full-text reference coverage is absent; show unavailable text metrics as —, not zero. Explicit stable contracts combine stable text anchors with record shape, required fields, types, count and uniqueness. Never equate structure with factual correctness or freshness. Binary task pass and continuous text overlap are independent; do not zero measured overlap because a task failed.
- Web, dynamic, popular-site and document text use the shared `score_attempt` orchestration and the same task-result predicate. Keep task-specific fields in case configuration, not provider/track-specific scoring branches. Partial stable text supports required-group coverage, not whole-body precision or F1. Keep case coverage visible; unannotated text is unavailable, not perfect. Do not promote snapshots containing excluded volatile fields into invariant body-quality averages. Old snapshot scores remain clearly scoped attempt diagnostics.
- Stable popular-site text must come from independently observed task-relevant headings, descriptions or field labels, not provider output or imagined page chrome. Retain evidence path/hash and location/scope. Do not require unobserved language translations, login prompts, generic navigation, current members, ranks or price values. A missing annotation is a reference limitation, not evidence of provider failure.
- Popular-site title diagnostics join returned entities to independent name evidence by detail URL, not live list membership. Label them as title metrics, disclose title/case coverage and conditional averaging, and retain per-title evidence. They are not full-body quality, retrieval recall, freshness or a substitute for task acceptance. Unknown identities and absent titles remain unmeasured; never copy title scores into `word_*`.
- Use invariant contracts for frequently changing values, retaining stable titles and explanatory text as content anchors where independently justified. Such contracts do not expire with a ranking or price update. Preserve output hashes, original call identity and explicit scoring-rule provenance. Exact live-snapshot comparisons retain the reference-binding and postcheck protocol in `harness/web_fetch/README.md`; never apply those gates to invariant tasks or certify historical calls retroactively.
- Dynamic-content ground truth requires paired initial HTTP bytes and independently rendered visible text, bounded completion and full declared scope. Follow `harness/web_fetch/README.md`; run `validate_render_reference` before freezing new references. Distinguish embedded state from follow-up data fetching; do not require JS as the only valid implementation. Keep supplements separate, declare planned provider coverage, and never count unexecuted methods as failures.
- Keep the three result filters (pass, fail, all), default to fail, and show failure classification. Preserve every registered provider's interface examples and adoption statistics.
- Each ranking must explain its task family, distinguishing difficulty, a typical input-to-output flow, acceptance, concrete example and limits locally. Keep meaning, flow and acceptance visible; home-page examples, boundaries, metric details and cross-track overview may collapse. Label flows as typical paths, not verified internals or mandatory implementations. Do not equate dynamic loading with frequently changing text or call the general web cohort purely static. Presentation edits must not alter scoring data.
- Evaluation credentials default only to this repository's `.env`, never a user's home directory. Artifact Hub publishing is the user-requested exception: reuse `~/.config/artifact-hub/token`, with explicit environment/repository overrides. Keep `.env.example` current; do not commit secrets.
- Persist provider-call outputs outside the repository under `~/.browser-eval/` (or `BROWSER_EVAL_DATA_HOME`). Do not commit `results.jsonl`, execution manifests, run-selection receipts, provider artifacts, raw rerun directories or internal work logs. Keep compact benchmark definitions, annotations, independent source evidence and public report release metadata in Git when they are required to reproduce or explain scoring.
- Before publication, run unit tests, JavaScript UI tests, report integrity and link checks. Retain each report's own Artifact Hub share link. The five-browser report uses its separately authorized site bWkRP157EtF6; never overwrite the original report UeZE1vfcEOrM with it.
- Maintain `research/report-changes.json` for every substantive report release and render it through the current report builder. Explain what changed, why it matters, score/denominator effects, evidence and remaining measurement limits; keep details collapsed and summaries visible. These are public release notes, not assistant work logs. Do not invent explanations for earlier undocumented versions.
- Maintain public provider prices in `research/provider-pricing.json` and render with `report_pricing.py`. Recheck official sources and record the verification date; separate actual annual commitments from rounded monthly labels, fully utilized plan prices from marginal overages, and billable browser time from client latency. Keep undocumented prices unknown, preserve billing exceptions, and never turn public quotes into historical benchmark invoices.
