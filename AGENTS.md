# Code review

Use the [review guidelines](docs/references/review-guidelines.md) that OCR loads. Their shared
section is copied from `lexmount/ai-template-py` at the commit named in the first
line; change it there and copy it here. The Browser Eval supplement at the end is
maintained in this repository.

# Benchmark ownership

Browser Eval owns benchmark scoring and input tooling as well as execution, evidence and reports. Keep the independent scorer APIs in `src/lexbench_webfetch/` and `src/lexbench_websearch/`; they must work without browsers or provider credentials. Shared dataset distribution and pinning belong in `src/harness/benchmarks/`.

Hugging Face owns versioned public benchmark definitions and redistributable reference inputs. `src/harness/benchmarks/data-lock.json` selects their repositories, full commits and file hashes. Change a selection through `make pin-dataset DATASET=<track> REV=<full-HF-commit>`; keep import bindings aligned and historical snapshots intact. Do not copy datasets into Git or reintroduce retired standalone scorer repositories as execution dependencies. Official upstream evaluators retain their pinned code dependencies. Full third-party references without redistribution rights remain external approved inputs.

Every track records full source commits and exact task/reference/scorer hashes. Release tags are labels for commits; documentation links to selection owners instead of repeating current versions. WebArena and WCXB retain their upstream authorities. See `docs/benchmarks.md#benchmark-editions`.

# Report maintenance

Repository documentation, identifiers, comments and docstrings use English. Report UI messages belong in language catalogs; source quotations and acceptance fixtures retain their original language. Keep the root README and `docs/README.zh-CN.md` aligned; additional README translations are welcome, but other guides need no parallel translation. Preserve original-language source quotations and hash-bound acceptance/evidence artifacts. Report-generation languages follow the track contracts below.

- For new search-provider cohorts, run each provider's complete declared case set before starting the next provider. Do not rotate providers within a query. Preserve already frozen in-flight execution contracts when continuing a cohort.

- Before report authoring, run `uv run --frozen python scripts/report_template.py <webfetch|trajectory-replay|browser-use|web-search>` and inspect its renderer, version-pinned example and checks. `configs/report-templates.json` owns discovery; examples supply presentation conventions, never measurements or publication targets. Extend the selected owner for new cohorts and evidence states. A new track must first gain a runnable synthetic example, evidence/detail behavior tests and a release check, then register those resources. Update the owning code and relevant skill when a repeated gap is demonstrated; keep report-specific findings outside instructions. Do not generate a disposable parallel renderer under a work directory.

## Change lifecycle and repository footprint

- Extend the current owner before adding a parallel implementation. A second browser, cohort, dataset size, provider, language or release must select behavior through data, a registry or parameters in the existing pipeline. It must not create a browser-specific runner, copied renderer, numbered implementation or compatibility alias.
- Keep command-line files as thin entry points. Parsing, validation, execution, aggregation and publication contracts belong in the track's shared `src/harness/` module so every entry point uses the same rules.
- Git owns reusable code, compact dataset definitions, acceptance contracts and provenance annotations. Report-instance profiles and publication bindings belong alongside external evidence, selected explicitly by the caller. Measured attempts, generated reports, report prose and illustrations, review payloads, diagnostics, temporary queues and run-local manifests live under the configured data home or the pinned Artifact Site release.
- Keep one supported current implementation of each stage. Remove superseded generators, repair scripts, migrations and their exclusive tests in the same change once no supported entry point calls them. Retain a historical revision in Git only when a current versioned authority names it and reproduction requires its bytes.
- Treat a large diff as a design signal. Before adding files, identify the existing owner, the smallest reusable extension and the data that can stay outside Git. File or line counts alone are not release gates; unexplained duplicate stages, private evidence and unreferenced historical versions are.
- Finish structural changes with a repository inventory: search for references to removed entry points, list the supported entry points, verify that current profiles bind every external artifact, and run the behavior and release gates that exercise those public boundaries.
- Do not preserve a changed command under its old name when its inputs or meaning change. Restore the old contract or introduce the new behavior under the existing shared abstraction and migrate every caller atomically.

- Keep report-specific prose, illustrations and review payloads outside Git, alongside frozen evidence. Commit compact path/hash bindings instead. The replay build reads `research/trajectory-replay-content.json` from the `--content` directory (default: the data home's `report-assets/trajectory-replay/`); restore missing content from the pinned Artifact Site version, not an unversioned latest report. Do not silently fall back to a repository copy. Compact task definitions, acceptance contracts and provenance annotations remain versioned inputs.
- Remove retired report-specific generators and their exclusive tests when no supported entry point calls them. Preserve published reports and historical evidence. Keep behavioral tests for supported build, package and publication boundaries; do not replace them with assertions about private helper structure.
- WCXB builds read profile-bound files from `<evidence>/report-assets/` and preserve the same relative paths in the public package; restore missing files from the profile's pinned Artifact Site version, never from an unversioned latest report. Do not silently fall back to a repository copy.

## Common report presentation

These requirements apply to **all** report tracks; browser-specific rules below only add evidence types.

- Reports are optional. Generate and inspect HTML locally; local construction requires no publication account. Upload only when the user requests sharing and authorizes the selected host. Building, checking or rebuilding a report does not authorize publication.
- Follow the shared presentation contract in `.agents/skills/benchmark-report/references/report-and-release.md`. Metric labels, units, populations, unique directional highlights, one-summary result details, evidence dialogs and repairable error drilldown are common requirements, not Browser Use features.
- Make report home and interpretation pages presentation-ready: each section states one finding and lets a chart, diagram, image, or inspectable specimen carry the main information; prose explains the evidence briefly. Keep exact values available as text. Remove decorative imagery that does not encode data, mechanism, topology, or evidence. Preserve dense tables and logs on the result-analysis and evidence pages that own them instead of turning audit material into decoration.
- When several compared browsers or methods have material failures, give each one a dedicated interpretation chapter with its complete reviewed failure distribution, plain-language mechanism, representative evidence, and the difference from the other methods. Put only a compact leading-error summary on the home page; keep full stage and case inventories in result analysis.
- Run both repository Humanizer and Humanizer Chinese over finished Chinese report prose, headings, and captions after the factual pass. Run Humanizer over English prose. Treat these as language edits: they must preserve measurements, technical meaning, quoted evidence, and uncertainty.
- Highlight the unique column maximum/minimum from raw values; tied or unavailable values stay neutral. A scoped numerical extreme is not a full-benchmark ranking. Do not remove highlights merely because successful-page populations differ; show the counts and scope.
- Mean/P50/P95 share one explicitly stated population and parallel labels. Retain retry execution cost separately when the current contract selects final-call latency; one logical result remains one sample.
- For a before/after build comparison, runs on different dates cannot supply the authoritative speed difference. Predeclare the complete task scope, alternate call order within each task, run serially on a quiet host, bind both binary hashes and all physical calls, and select a round before seeing results. If an earlier timing is corrected, retain it privately, supersede every affected logical timing, and make the report table and detail agree. Release checks must reject an absent or partial timing receipt.
- New or substantially rewritten report renderers must wire semantic presentation checks into their release gate, with negative controls for missing/wrong highlights, duplicate summaries, broken evidence targets and missing failure logs. Use `src/harness/reporting/presentation.py` or equivalent track-specific adapters. A written instruction or a route-count check is not proof that the UI requirement is enforced.
- Renderer/component behavior tests must exercise successful and failed result details, exact error/evidence loading, keyboard dismissal and focus restoration. Keep one representative local test for hosted nested navigation when the host changes path resolution; do not repeat these interactions or viewport/theme matrices during every report release.


- For benchmark design, execution, scoring, result audit, report generation or release, read `.agents/skills/benchmark-report/SKILL.md`. Use `.agents/skills/benchmark-editorial/SKILL.md` additionally only for a new or substantially rewritten standalone interpretation article, official blog or public-account article.
- Keep one report implementation in `src/harness/web_fetch/report.py`. The default `scripts/build_report.py` build uses persistent measured evidence (`~/.browser-eval/evidence/current/` by default, or `WEB_FETCH_EVIDENCE_DIR`) and writes `reports/webfetch/`; the independently bound WCXB build uses `--wcxb` and writes `reports/wcxb/`. Do not create versioned report implementations, compatibility renderers or redirect builds.
- Run repository Python only through `make` targets or `uv run --frozen python`. `.python-version`, `uv.lock`, the Makefile and CI are the runtime contract; never fall back to system Python.
- Run every publishable provider cohort through `scripts/run_certified_benchmark.py`, which freezes executable task inputs. Existing compiled reference answers stay frozen; pre/post source checks require an explicit `source_verification.reference_mode: live_exact` task declaration. Missing newer acceptance-contract fields never imply a live-reference task. Rerunning an unchanged compiled dataset must not require historical source-qualification raw files or reopen cohort admission; source qualification belongs to adding tasks or changing references/acceptance rules. Direct `run_benchmark.py` output and incomplete cohorts are diagnostic evidence only; never assemble or publish them.
- Select report instances explicitly with `--profile` (or an external `--authority-root` bundle for historical full-cohort formats). Store their matrices, publication targets and mutable version receipts outside Git alongside the frozen evidence. Each report and track owns its own publication binding; never borrow another report's target.
- For the complete WebMainBench report, `evaluation/webmainbench-full/current-report.json` inside the selected external authority bundle is the immutable baseline pre-call profile bound by its cohort certificate. Independently certified variant cohorts are registered in `evaluation/webmainbench-full/`; discover the current variant registry and each variant's profile and certificate from that directory rather than hard-coding names. The method-binding file joins the baseline and all certified variant cohorts through locked profile hashes. Their `publication_state` records frozen pre-call state. The live site, share URL, and expected remote version are bound in `evaluation/webmainbench-full/publication-target.json` together with the baseline and all variant profile hashes; update this target after publication without changing or re-certifying historical calls.
- For the current WCXB report, the source-qualified manifest is the entire evaluation population for quality, delivery, and latency. Keep source-invalid cases outside the current manifest, scored evidence, public package, and future provider calls; preserve earlier physical calls only in private historical evidence. The dataset page owns frozen task inputs, source URLs and human reference scope; it must not show measured browser scores. The home page owns aggregate comparisons, the result analysis owns the filterable method-case inventory, and case result pages own full responses. Keep a direct link from each dataset row to a safe frozen-page preview and its human reference. Default result filters must show a nonempty, clearly labeled diagnostic population when one exists, and filtered tables must shrink rather than leave a large blank viewport.
- Persist provider calls outside Git under `~/.browser-eval/` (or `BROWSER_EVAL_DATA_HOME`). Git may contain compact benchmark definitions, annotations, independent source evidence and public release metadata, but never measured outputs, execution manifests, provider artifacts, rerun directories, credentials or internal work logs.
- Web Fetch keeps one current authoritative logical result per method and task. A declared failure retry retains every physical call, retains total retry execution cost separately from the profile-defined primary latency and uses the final response, never the best response. A proven wrong command, version, scorer, reference or timing is a correction: preserve the prior evidence, supersede the complete declared scope and disclose score, denominator and latency effects.
- Aggregate only declared, hash-bound evidence files; reject symlinks and never publish worker directories, local paths or internal run trees. Every auxiliary and retry artifact named by a result must be materialized and hash-verified at the aggregate boundary.
- Independent result review is never automatic. Start it only after explicit user instruction; default to machine failures, and require a separate explicit full-review instruction before reviewing passes or the entire matrix. Publish the exact reviewed/total scope and accepted unreviewed pass count.
- A reference, scoring or acceptance correction must fix the shared cause, not patch stored verdicts or one provider. Add paired executable controls to `src/harness/benchmarks/scoring-regressions.json` where both error directions are plausible; historical controls remain in pinned dataset snapshots. Run controls through the public `score_attempt` and task predicate, and bind the root cause plus regression IDs in every new reference/scoring revision receipt. A revision without this provenance fails before evidence is changed.
- A heterogeneous same-window latency cohort keeps every predeclared method-task call. Report the common-denominator all-call distribution separately from each method's conditional successful-call distribution; an all-method common-pass intersection is diagnostic only and must never drive post-outcome task selection or a ranking.
- Evaluation credentials come only from the repository `.env`. Artifact Site publishing is the sole user-scoped exception: read explicit `ARTIFACT_SITE_TOKEN`, then `~/.config/artifact-site/tokens/<target-host>`; the previous `ARTIFACT_HUB_TOKEN` and `~/.config/artifact-hub/` locations are read-only migration fallbacks. Never load `.env` for publishing. Save new authorizations per target host without overwriting another deployment's token. Keep `.env.example` current and publish only account requirements, official acquisition links and variable names.
- Public report CLIs fall back to English. `BROWSER_EVAL_REPORT_LANGUAGE` changes the environment default; an explicit `--language` wins, and an existing report preserves its saved primary language. Agent-driven builds must set the language from the current user conversation instead of guessing from the host locale. English builds retain the matching Chinese edition; a Chinese selection generates no English translation unless explicitly requested. Keep measured material in its source language. Historical Chinese-only renderers must state their limitation and reject unsupported requests. Record generated editions and the selected entry in report metadata. When English is absent, its navigation opens a not-generated notice with a return link; never ship stale English pages. Require route, value and evidence-link parity only when both editions were explicitly generated.
- Web, dynamic, popular-site and document text use shared `score_attempt` orchestration and one task-result predicate. Task-specific requirements live in case configuration, not provider- or track-specific scoring branches. Binary acceptance and text diagnostics remain separate; missing reference coverage is unavailable, not zero or perfect.
- Dynamic-content reference capture follows `src/harness/web_fetch/README.md`: retain paired initial HTTP bytes and independently rendered visible text, bound completion and the full declared scope. Distinguish embedded state from follow-up fetching; never require JavaScript as the only valid route.
- Popular-site stable text must be independently observed and task-relevant. Do not freeze volatile ranks, prices, member counts or current list membership. Title diagnostics join returned entities to independent names by detail URL and never substitute for body quality, recall, freshness or task acceptance.
- Keep pass, fail and all result filters, defaulting to fail, with failure classification. Every ranking must state its task family, denominator, acceptance meaning, typical input-to-output route and local limits. Preserve every registered provider's interface examples and adoption statistics.
- When a current report has CPU, memory or network evidence, show the same grouped resource comparison on the home page and interpretation page. Lead with the evidence-derived winner for every metric where lower consumption has a clear meaning, mark winning cells in the tables, and state that resource leadership is separate from task pass rate. Do not label utilization or transfer rate as “better” merely because it is lower. Release checks must fail if the winner summary, grouped tables or winner markers are missing in either language.
- Keep `research/provider-pricing.json` as a reusable product-price catalog: retain verification dates, commitments, billing units and unknowns, but do not describe one run or report there. New report release history belongs in hash-bound `report-assets/report-changes.json` beside the evidence. `research/report-changes.json` is a legacy fallback while older report owners migrate; do not add a new report's results, prose, review scope or publication URL to it.
- Render a report's release history from its bound report asset when present; keep Chinese and English release text together in each entry. Do not duplicate release prose or past measurements in report renderers or exact-string translation maps. Release checks compare structured records with rendered routes rather than matching fixed phrases. Browser Use and trajectory replay keep their existing structured release models.
- Use `Browser Use` for the autonomous track and `Browser Trajectory Replay` (Chinese: `轨迹重放`) for the fixed BrowserTool-action track. Their implementation roots are `src/harness/browser_use/` and `src/harness/trajectory_replay/`; do not add aliases or compatibility paths using the retired names.
- The public WebArena human-recording replay is isolated under `src/harness/trajectory_replay/public_webarena/` with its own examples, tests, external report profile and release script. It must not change autonomous `src/harness/browser_use/` or share a report target or denominator with the repository-curated replay suite.
- Browser Trajectory Replay canonical inputs must not contain run-local snapshot refs. Compile each ref to a hash-bound stable selector while preserving the original ref action semantics; do not silently replace a DOM ref click/fill/select with BrowserTool's Playwright selector fallback because that adds different viewport, overlay and navigation-wait behavior.
- Browser Trajectory Replay reports keep the dataset separate from measured verdicts. Every task needs a contract-and-qualified-trajectory page; every result needs a same-task all-browser comparison, a reader-facing failure locator, the exact failed-action or evaluator error, reviewed cause, complete expandable tool responses, and on-demand public evidence. The result inventory stays compact, fixed-height, filterable and linked to a diagnosis dialog. The same-task explorer uses a registry-driven baseline, multi-select comparison browsers and explicit outcome relations; group pass/fail links instead of adding one result column per future browser. Keep Chinese and English task/result routes aligned.
- A BrowserTool call that returns success does not prove its intended site mutation occurred. When the official evaluator rejects a completed trajectory for an absent required network event, locate the last plausible trigger action and publish the exact missing-event assertion, but do not mark that action as failed or change the official verdict. Repair asynchronous or position-dependent trajectory inputs only through new qualification evidence and a frozen full-scope comparison rerun.
- Trajectory Replay component tests exercise Sites-style tokenized preview navigation from a nested result back to the report root; plain relative-link validation alone does not prove that behavior.
- Browser Use reports expose one manifest-authoritative logical result per browser and task. Dataset routes contain only frozen task definitions and acceptance contracts; result routes own verdicts, timings and trajectories. Keep one filterable result inventory instead of adding duplicate success/failure tables.
- Keep automatic evaluator failure location separate from reviewed root cause. A root-cause subtype and reason must come from a per-browser, per-task review bound to the current attempts hash; render both fields blank while that result is unverified, and require complete verified coverage before a formal release when the current profile enables the gate.
- Generate browser rows and comparisons from the participant registry. The same-task explorer uses one baseline browser, multi-select comparison browsers and explicit outcome relations, with browser labels linking to full results; never add one fixed table column per future browser. List Agent, model, prompt/tool contract, resources, environment and evaluator as shared controls. Standard summaries use mean, P50 and P95; compare every registered model-by-browser configuration together and mark only globally unique winners on directionally comparable metrics. For action latency, compare all configurations by per-call latency and keep unequal-workload totals and call counts neutral.
- Put a core-metrics comparison table near the start of every report home page, before secondary diagnosis or interpretation. Prefer tables over repeated cards for dense categorical summaries. Generate its rows and columns from the participant registry rather than assuming a fixed participant count.
- Give each report page one primary reader question and one owner for each fact. Before adding a section, first place the information in the existing summary, filterable inventory, or result detail that owns it; remove duplicated tables and prose. When an evaluation flow has three or more dependent stages or a branch, lead with a Mermaid or ImageGen diagram and keep prose for definitions, constraints, and evidence rather than restating the flow.
- A report interpretation page must stand alone as the reader's main explanation: lead with the measured outcome and denominator, show a compact method comparison, explain the scoring mechanism with at least one inspectable source/reference/output example, diagnose each method's material issue, distinguish measurement from causation, and end with supported conclusions and review scope. Study the supplied reference report's reading sequence and evidence depth before revising; do not copy its benchmark facts. Protect the structure, values, evidence targets, and nearby caveats with release checks and negative controls, then inspect the delivered page as a reader. Rules in Markdown alone are insufficient.
- Use reader-facing labels throughout reports. Do not publish unexplained internal terms or shorthand; Chinese copy must be understandable to a general reader without benchmark implementation context. State the population, denominator, and outcome relation where a compact label would otherwise be ambiguous.
- Result-detail summaries contain only the verdict, concise failed-rule labels and short scalar facts. Full evaluator messages, expected/actual payloads, traces and logs belong in dedicated evidence sections, never narrow KPI cards.
- Result inventories are fixed-height, horizontally scrollable diagnosis tables. Do not place full reviewed causes, evaluator payloads, latency stacks or other paragraph-length content in inventory cells. Every failure row opens an in-page diagnosis with the failure stage, exact program error, reviewed cause, treatment and links to the relevant trajectory, screenshots and logs; the full result page remains the canonical evidence view.
- Compare every registered model-by-browser configuration in one same-task matrix generated from the participant registry. Do not introduce pairwise selectors or duplicate comparison prose when more configurations can be represented as columns.
- Every failed result detail must expose the evidenced failure stage, the programmatic evaluator classification, the exact evaluator/runtime error, the reviewed root cause, the remediation owner/status, a link to the relevant trajectory step, sanitized logs, and the last public trace frames when available. Distinguish a failed BrowserTool action from the last successful action before evaluator rejection. Provide a shared HTML evidence viewer as well as a raw JSON link because static hosts may not preview JSON reliably; load the selected JSON on demand and never duplicate complete evidence payloads into every result page. Extract frames only from ordered Playwright `screencast-frame` events, validate full-page dimensions and provenance, and never treat arbitrary trace resources as screenshots. Label frames as last observed pages, not as exact error screenshots unless the evidence proves that timing.
- Keep official scores immutable when diagnosis finds benchmark/evaluator, site, shared-environment, or frozen-reference interference. Quarantine affected tasks across all configurations in a clearly labeled post-hoc diagnostic subset, record remediation in `research/browser-use-remediation.json`, and readmit them only after a preregistered full-scope rerun.
- Split environment preparation, browser-session setup, Agent run, BrowserTool wall time, evidence finalization and evaluator time at collection. Publish the self-hosted deployment topology and image identity; claim per-execution reset/readiness only when a preparation receipt binds reset, readiness and application health.
- Formal report prose is reader-facing: no prompts, reasoning, internal work narration, conversational rebuttals or references to parallel sessions. Review pages contain review rounds and corrections, not per-case audit tables; release notes contain reader-visible effects.
- English routes may preserve measured task names, IDs and evidence verbatim, but all report-authored interface and explanatory prose must be localized. Release checks must reject known untranslated interface markers and untranslated accessibility attributes.
- Before release, render every top-level navigation page once at the standard desktop width in the saved primary language, and do the same for another explicitly generated edition. Review its content hierarchy, data-bearing visuals, tables and horizontal overflow. Do not multiply this reader pass across detail pages, themes or viewports. Cover responsive layout and theme behavior once in shared renderer/component tests when those owners change; cover filters, pagination, dialogs and evidence links with deterministic generation-time behavior tests. When a host has special nested-path rules, add one representative local topology check instead of navigating the deployed report.
- Keep routine report checks fast and deterministic; they cover the complete route inventory, evidence, links, terminology, filters, pagination and static readability without launching a browser. The release browser pass is a focused content-and-layout review of top-level pages, not a second interaction test suite.

All code changes go through a feature branch and pull request. Never push directly to main or merge a pull request.

Version changes require an explicit human release request. Code synchronization, review fixes, tests and report rebuilds must not automatically bump package, benchmark or report edition numbers, rewrite frozen release catalogs, or create/push release tags. Reuse existing build versions and record source hashes; keep unreleased changes separate from a certified edition.
