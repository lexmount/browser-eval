# 动态网站正文测试集：100 例完整审查交接

## PR 的唯一审查范围

本 PR 用于对 **100 个动态网页正文案例全部重新审查一遍**。它不是“86 例到 100 例”的增量审查，也不是只检查最后新增的 14 例。

审查者必须逐例判断：

1. 这个页面是否符合本测试集对动态网页的定义；
2. 首次自动加载的目标正文范围是否清楚、合理；
3. 验收规则是否真的能区分完整正文、残缺正文和错误页面；
4. Moli WebFetch 的完整输出是否满足该规则；
5. 最终通过或失败判定是否正确。

只有 100 个案例全部有独立结论、未解决项为 0，才算完成本次审查。

## 先理解三个对象

- **案例定义**：说明要访问哪个 URL、允许什么操作、目标正文在哪里、等待到什么状态才算加载完成。
- **验收规则**：说明输出必须包含什么、正文要覆盖到什么程度、列表记录怎样配对，以及哪些错误页或噪音必须排除。
- **实测结果**：Moli WebFetch 对该 URL 的一次真实返回，以及基于案例规则得到的通过或失败。

这三个对象要分开审。页面选得对，不代表规则一定好；规则写得好，也不代表现有判定一定正确。

## 动态网页资格怎么审

每例都应满足以下条件：

- 公开 HTTPS URL，无需登录、验证码、付费或私人权限；
- 任务只要求首次自动加载，不点击、不输入、不主动滚动、不搜索、不翻页；
- 初始 HTTP 正文缺少全部或部分目标内容，而浏览器自动加载后能够观察到目标内容；
- 目标正文有明确边界，加载完成有可观察条件和最长等待时间；
- 页面不是空壳、错误页、登录页或挑战页；
- 规则没有把“必须由 JavaScript 生成”当作唯一通过路线。若嵌入状态或后续请求也能得到同一正文，仍可视为有效抓取。

如果某例不符合这些条件，应记录为 **案例资格问题**，不能直接算作供应商失败。

## 规则怎么审

先看页面目标是什么，再选规则，不要把所有页面都简化成关键词匹配。

### 稳定正文

适合文档、教程、API 说明和固定表单。除了身份锚点，还要检查正文从头到尾的分段覆盖、最低正文长度和排除内容。只命中标题或几个关键词不等于取得正文。

### 固定结构化记录

适合固定商品、引用、表格和卡片列表。应检查记录数量、每条记录的字段归属、字段类型、详情链接和唯一性。名称、价格分别出现但配错记录，不能通过。

### 易变列表

适合新闻、热榜、商品搜索和社区列表。不要长期冻结当天标题、价格、排名或成员；应检查页面身份、最低记录数、标题与详情链接是否同属一条记录、链接范围、类型、唯一性和噪音排除。若要证明某个实时值准确，必须有同一时刻的独立参考。

### iframe 或子文档

必须检查声明的子文档正文，而不是只证明主页面出现了 iframe。子文档正文较短时，应覆盖完整范围；不应只用一个提示词代替正文核对。

## 建议的新会话审查顺序

为避免先看到机器结论后被其影响，逐例按下面顺序审查：

1. 只看 URL、页面身份、目标范围和独立页面证据，先判断案例资格；
2. 隐藏现有通过/失败，检查规则是否覆盖目标正文、结构关系和排除项；
3. 查看完整 Moli 输出，独立给出通过或失败；
4. 最后再揭示报告中的机器判定和既有人工裁定；
5. 若结论不同，记录原因，并判断属于案例资格、规则、解析、评分、来源漂移、供应商输出还是报告展示问题。

建议按数据集顺序分成 `1–25`、`26–50`、`51–75`、`76–100` 四批，但四批的审查标准必须相同。不要先按“旧 86 / 新 14”拆分，因为那会让审查重点错误地落在新增案例上。

## 每例应留下的审查记录

每个案例至少记录以下字段：

```text
case_id
url
dynamic_qualification: pass | fail | unresolved
task_scope: pass | fail | unresolved
rule_quality: pass | fail | unresolved
independent_result_verdict: pass | fail | unresolved
reported_verdict: pass | fail

issue_class: none | source | case | rule | parser | scorer | provider | report

```

如果是分歧，理由必须指向完整输出与具体规则，不能只写“看起来不对”。
