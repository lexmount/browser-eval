评测结果分析

为什么使用配对比值

先对每个“同任务、同轮次、双方都成功”的样本计算 Moli ÷ Chromium，再汇总这些比值。它比“两个总体中位数相除”更能控制不同任务的体量差异；低于 1× 才代表该指标对 Moli 有利。

成功率与失败模式

Chromium 完成 50/50；Moli 完成 44/50。Moli 的 6 次失败集中在两个任务类型：

  • RFC 9110 锚点导航：5 个轮次均在章节链接已解析且可见、自动滚动到位后仍发生 click 超时，说明当前版本在超长文档的元素命中或点击完成判定上存在稳定兼容性问题，而不是随机网络抖动。
  • PyPI requests 页面：1 次出现目标 h1 已解析但持续被判定为隐藏并等待超时，其余 4 次通过，更接近偶发渲染或可见性判断问题。

因此当前主要风险不是“所有网页都略差”，而是特定交互模式会系统性失败。对 agent 来说，这类失败比平均速度更影响默认 provider 资格。

资源与速度解读

  • 内存：Moli 在配对成功样本中的峰值内存显著低于 Chromium，这是本轮最稳定、最有产品价值的优势。
  • 速度与 CPU：本轮不支持“Moli 普遍更快或更省计算”的结论。复杂度增加后差距并非线性，说明页面与操作类型会显著影响结果。
  • 网络：RX/TX 包含网页流量和 CDP 控制流量。更高的 TX 只能说明容器对外发送字节更多，不能直接等价为页面更大或用户带宽成本。
  • token：双方在同一成功任务上的提取规则一致，配对输出 token 没有优势；总体未配对中位数差异主要受 Moli 失败任务缺失影响，不能当作节省。

连续运行与历史影响

任务间清理不会关闭浏览器进程，也不会要求内存分配器把保留内存全部归还系统。因此报告同时比较最后一轮与第一轮：

本轮 Moli 基线内存升高，但耗时没有出现同量级的持续恶化。结论应表述为“存在暖进程保留内存”，而不是“缓存没清干净”或“运行一定越来越慢”。

面向 CowAgent 的决策

  1. 默认 provider 继续使用 Chromium，因为成功率是硬门槛。
  2. 把本地 Moli 和 Cloud Moli 暴露为明确的可选 provider，推荐给内存密度敏感且能接受先验验证的场景。
  3. 不要在当前证据下宣传 Moli 全面更快、更省 CPU、更省网络或更省 token；可以宣传“本评测中峰值内存更低”，并附适用范围。
  4. 下一轮应围绕长文档点击、滚动后命中和 PyPI 可见性问题做回归；当成功率接近 Chromium 后，再以真实 CowAgent agent 任务验证端到端速度和模型 token。
