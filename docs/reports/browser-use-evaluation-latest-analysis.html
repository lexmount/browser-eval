性能解释边界

本轮使用本地固定测试页面，两个浏览器进程均在预热后复用，任务之间清理浏览状态，并使用确定性调用链。资源表只保留双方成功任务：Moli 未通过的 10 个任务被排除，因此存在成功样本选择偏差。

性能结论只能表述为“在本轮 20 个双方首次均成功的任务中观察到相应配对分布”，不能外推为全部任务或所有网站上的固定优势。每个任务只有一个首次执行样本，也不足以建立稳定的性能置信区间。

时序假设与放大性测试设计

已知实现事实：Moli 的 1 Hz 指 CDP screencast 帧的下采样节奏；调度器按 everyNthFrame 以秒为单位安排 screencast，不代表 JavaScript 动画帧只以 1 Hz 运行。Moli 的 requestAnimationFrame 源码目标间隔为 16 ms，两者是不同的调度路径。

待验证假设：低频 screencast 或其触发的布局快照可能放大动态 DOM 更新后几何、可见性或命中测试状态陈旧的问题；这只是机制假设，不是本轮失败的既定根因。必须用失败现场的 actionability probe 和对照实验验证。

  1. 固定变量：对同一页面、同一选择器和同一 BrowserTool 调用，分别使用立即显现、双 rAF、定时器、DOM 替换、动画和视口进入等触发方式；评测集中的 source.coverage 与 source.hypothesis 明确记录每个 probe 的覆盖面。
  2. 放大变量：围绕 16 ms 与 1 秒两个时间尺度改变显现延迟，并在可控条件下对比 screencast 订阅开启/关闭；每个组合使用预先固定的重复次数和相同超时。
  3. 实测证据：失败时采集节点连接状态、disabled、display、visibility、opacity、pointer-events、矩形尺寸和 client rect 数量，并与对应成功样本及页面内时间戳对齐。
  4. 判定规则：只有当 DOM/rAF 已按约 16 ms 完成、但几何或 actionability 状态稳定滞后且随 screencast 条件系统性变化时，才支持“screencast 放大时序问题”；否则应否定该解释并继续检查适配层、布局刷新或测试页面。
