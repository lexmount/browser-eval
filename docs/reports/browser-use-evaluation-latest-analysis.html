本轮结论

  • 功能：Chromium 100.00%（30/30），Moli 93.33%（28/30）。Moli 的失败集中在 Books to Scrape 首次导航超时，发生于第 2、3 次；同轮 Chromium 均通过。
  • 内存：Moli 时间加权平均内存 P50 为 Chromium 的 0.48×，即低约 52.06%；任务内存 P95 和峰值仍需看结果页，不能用单个峰值替代时序分布。
  • 计算与时延：Moli CPU 时间 P50 为 1.16×、P95 为 9.82×；耗时 P50 为 1.32×、P95 为 6.19×。本轮不能得出“Moli CPU 更省”的总体结论，RFC 长文档是主要尾部异常。
  • 网络：Moli RX P50 为 2.52×、TX P50 为 2.73×。这意味着当前实现传输更多数据；需结合 CDP 消息与页面资源拆分后，才能判断优化点。

产品决策

  1. 当前数据支持把 Moli 定位为内存优先的推荐 provider，不支持把它设为默认值：成功率、RFC 尾延迟、CPU 尾部和 Books 首次导航都还未对齐 Chromium。
  2. 当前“内存约减半”来自本轮 28 对成功交集，不等同于 LexBench 的所有场景，也不能外推成固定倍数。
  3. 生产密度应同时看时间加权平均内存、任务内存 P95、CPU、MiB·s 与成功率；网络需要继续拆分网页流量和 CDP 协议流量。
  4. 本轮工具层没有模型规划；CowAgent + LiteLLM smoke 只验证链路，不用于推断重试数、LLM token 或答案准确率。
