Browser Use Evaluation

Run 35bdd5496c5e · warm-browser Chromium vs Moli

Methodology

  • Each engine runs in its own Docker container with identical CPU, memory, PID and shared-memory limits; controller usage is excluded.
  • Browser process and context remain warm; browser cold start is excluded.
  • Before each task, the harness inventories and clears every top-level HTTP(S) navigation origin plus cookies, permissions, browser cache and history, then replaces only the renderer page outside the timer.
  • 5 repeats; 100 ms memory/PID sampling; balanced alternating engine order.
  • After reset and renderer GC, both engines receive a 1500 ms quiescence window before counters and timing begin.
  • Functional results include every attempt. Resource results include only matched attempts passed by both engines.

Observed findings and decision

  • Chromium passed 50/50 attempts; Moli passed 45/50. Moli failures were confined to Inspect RFC 9110 and navigate to a section.
  • Across 45 matched passing attempts, Moli / Chromium medians were 1.69× duration, 1.31× CPU, 0.57× peak memory, 1.65× RX, and 4.61× TX.
  • Matched tool-output tokens were 1.00×; this browser-only suite shows no token-cost advantage.
  • For Moli, last/first baseline memory was 2.21× while last/first duration was 1.03×. The five repeats did not show systematic runtime slowdown, but the warm process retained allocations and did not return to its first-run footprint after state cleanup.
  • Decision for this suite: keep Chromium as the default provider. Offer Moli as an opt-in memory-oriented provider after workload-specific validation; these results support lower peak memory, but do not support broad claims of higher speed, lower CPU, lower network use, or lower token cost.

CubeSandbox decision

  • CubeSandbox officially demonstrates headless Chromium in a MicroVM over CDP, so it is a valid future Browser Use backend.
  • Its native metrics expose host-sandbox and guest-workload CPU/current-memory scopes, but default to 5 s collection, retain only the latest sample, do not export an exact memory peak, and list no per-sandbox network byte counters.
  • This first local reference therefore uses 100 ms Docker cgroup/network-namespace accounting. A CubeSandbox backend should model production topology and remain a separate accounting scope.

Interpretation limits

  • Docker is the reproducible accounting boundary, not a recommendation that CowAgent production browsers must run in Docker.
  • Public-site latency and network traffic retain Internet/CDN variance. Repeated medians and balanced order reduce but cannot remove it.
  • Memory peaks shorter than the sampling interval can be missed.
  • Docker cgroup PID values count Linux tasks/threads, not only OS processes.
  • Chromium includes a tiny in-container TCP forwarder because Debian Chromium binds CDP to loopback; its resource cost is included and slightly biases Chromium upward.
