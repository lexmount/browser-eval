# Repository review supplement

These questions supplement OCR's built-in review instructions. Preserve its scope, severity thresholds, output format and execution policy; where they conflict, follow the built-in instructions. Use the questions to investigate the change, not as a checklist to repeat in the review output. Apply the repository's review-relevant constraints in `AGENTS.md` and `CONTRIBUTING.md`.

Follow this review path, checking each answer against the current diff, relevant callers and evidence:

1. What user problem and acceptance criteria does this PR address? Does the proposed approach achieve them, and do the implementation and every changed file serve that purpose? Which claims in the description or earlier comments need independent verification?
2. How does the change behave through the supported public entry points and downstream consumers? Could it break previously correct behavior or introduce a new defect through defaults, old inputs, boundary cases or interactions outside the diff? If it restores a removed behavior, does Git history explain why it was removed and whether that reason still applies?
3. What happens with invalid or missing input, partial failure, timeouts, retries, cancellation and concurrent work where relevant? Can errors be swallowed, required checks bypassed, state corrupted, resources leaked or secrets/private data exposed?
4. Does the design apply object-oriented principles to shared components: clear responsibilities, encapsulated state and invariants, and stable interfaces that let implementations vary without changing callers? Does it reuse existing objects and upstream capabilities, favor composition over inheritance, and keep shared behavior under one owner? Could scattered conditionals, exposed internals or duplicated pipelines be replaced by a cohesive object or interface? Is the abstraction justified by current behavior, with simple stateless transformations kept as functions and no unnecessary class hierarchies?
5. Would another supported dataset, provider, cohort or report use the same implementation through explicit data or configuration? Is reusable code coupled to one report's IDs, paths, participant count, measurements or prose, and would adding another instance require edits across unrelated modules?
6. Do tests exercise the intended behavior through supported interfaces, including valid and invalid scenarios and the previously correct behavior at risk? Do fixtures reflect real producer/consumer contracts? When execution is available and permitted, have the smallest relevant reproduction and passing control been run on the reviewed revision, including the installed package when affected?
7. Have all changed files and affected shared paths been examined, including other occurrences of a suspected root cause? Where the review environment supports agents, would independent parallel checks of distinct risk areas improve coverage within OCR's execution policy? Before finishing, have candidate findings been verified and duplicates combined, including earlier findings that may still reproduce on the current revision?

Report actionable findings under OCR's normal reporting rules, supported by a concrete trigger, affected behavior and code evidence. Treat design or optimization concerns as findings only when they have a demonstrable consequence; personal style preferences and speculative future requirements are insufficient. For related PRs, verify the repository, revision and dependency state, use full URLs, and distinguish a current defect from an unmerged dependency.

## Browser Eval

8. Does the change preserve the boundary between benchmark-owned task definitions/scoring and harness-owned provider execution/reporting? Are CLI entry points thin and all supported callers using the same shared behavior, without provider-specific acceptance rules or help that changes what the provider is being evaluated on?
9. Do scored answers come from retained native evidence, and do results, denominators, timing populations and report claims follow the selected track contract? Are retries and corrections preserved, artifacts verified, and incomplete or uncertified cohorts excluded where certification is required? Are measured outputs, credentials and run-local material kept outside Git? Could a change silently rewrite frozen results or mix report targets?
10. Do the affected report views agree with the underlying evidence and each other, including generated languages, filters, highlights and failure details? Do the applicable behavior and release checks exercise those public boundaries, including evidence drilldown and hosted navigation when changed?
